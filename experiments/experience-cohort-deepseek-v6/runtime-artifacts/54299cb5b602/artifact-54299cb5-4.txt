# Evidence Expected by SLSA Provenance and NIST SSDF for Software Supply-Chain Integrity

## Overview

This Artifact identifies the distinct categories of evidence that the **SLSA provenance specification (v1.2)** and the **NIST Secure Software Development Framework (SSDF) SP 800-218 (v1.1)** each expect for software supply-chain integrity. The frameworks differ in type and granularity: SLSA defines concrete, machine-verifiable cryptographic attestations tied to a build artifact; NIST SSDF defines broad organizational practices with high-level and low-level artifacts serving as evidence of conformance.

---

## A. SLSA Provenance (slsa.dev, v1.2)

SLSA evidence is organized around a single core artifact: **the provenance attestation** — a signed, in-toto Statement with `predicateType: "https://slsa.dev/provenance/v1"`.

### 1. Core Provenance Fields (Evidence Content)

**REQUIRED at SLSA Build L1:**
- **`buildDefinition`**: The input to the build.
  - **`buildType`** (TypeURI): Identifies the build template (e.g., a GitHub Actions workflow type). MUST resolve to a human-readable specification.
  - **`externalParameters`** (object): Untrusted parameters set by the user/tenant (e.g., source repository URI, ref, entry point). MUST be complete and fully enumerated at SLSA Build L3; best effort at L1–L2. Verifiers SHOULD reject unrecognized fields.
  - **`internalParameters`** (object, OPTIONAL): Trusted parameters set by the build platform. Not verified downstream.
  - **`resolvedDependencies`** (array of ResourceDescriptor, best effort through L3): Artifacts fetched during the build. Each entry includes `uri`, `digest` (sha256, sha512, gitCommit, etc.), `name`, `downloadLocation`, `mediaType`, `content`, `annotations`.
- **`runDetails`**: Execution metadata.
  - **`builder.id`** (TypeURI, REQUIRED): Identifies the trusted build platform and its transitive closure. Is the sole determiner of SLSA Build level.
  - **`builder.builderDependencies`**: Platform dependencies that affect provenance generation.
  - **`builder.version`**: Map of platform component versions.
  - **`metadata.invocationId`**, **`startedOn`**, **`finishedOn`**: Build invocation identity and timestamps.
  - **`byproducts`**: Additional artifacts for debugging/incident response (e.g., logs, build configuration digests).

### 2. Provenance Integrity Evidence by SLSA Level

| Level | Completeness | Authenticity | Accuracy |
|-------|--------------|--------------|----------|
| **L1** | Provenance exists; identifies output by cryptographic digest (`subject`). Best-effort completeness. | None required. | None required. |
| **L2** | SHOULD be complete. Some external parameters may not be fully captured. resolvedDependencies is best effort. | **Digital signature** from a private key accessible only to the build platform's control plane. Consumers MUST verify the signature. Tenant MUST NOT generate provenance fields (except `subject` and non-required fields). Control-plane generation with tenant-tampering deterrents. | Provenance MUST be obtained from the build platform, not tenant-controlled steps. |
| **L3** | External parameters MUST be fully enumerated. resolvedDependencies is best effort. | Same as L2. | **Unforgeable**: signing keys in a secure management system, inaccessible to user-defined build steps. Every field generated or verified by trusted control plane. **Isolated**: ephemeral environments, no cross-build interference, no cache poisoning, no secret access by builds. |

### 3. Verification Evidence (Verifier's Side)

Per the SLSA verifying-artifacts specification, verification SHOULD check:
1. **Envelope signature** against a pre-configured root of trust (map of public key identity + `builder.id` → SLSA Build Level).
2. **`subject` digest** matches the artifact under inspection.
3. **`predicateType`** equals `https://slsa.dev/provenance/v1`.
4. **`builder.id`** is in the trusted roots of trust.
5. **Expectations match**: builder identity, canonical source repository, `buildType`, and `externalParameters` all conform to expected values. Unrecognized `externalParameters` SHOULD cause failure.
6. **(Optional) Recursive dependency verification** via `resolvedDependencies`; Verification Summary Attestations (VSAs) may record prior results.

**Source URL:** https://slsa.dev/spec/v1.2/build-provenance, https://slsa.dev/spec/v1.2/build-requirements, https://slsa.dev/spec/v1.2/verifying-artifacts

## B. NIST SSDF (SP 800-218, v1.1)

The SSDF defines an **artifact** as "a piece of evidence" [NISTIR 7692] and evidence as "grounds for belief or disbelief; data on which to base proof or to establish truth or falsehood" [SP 800-160 Vol. 1]. It distinguishes two tiers:

- **Low-level artifacts**: threat models, log entries, source code files, vulnerability scan reports, testing results, telemetry, risk-based mitigation decisions — generated manually or automatically, maintained by the producer.
- **High-level artifacts**: summaries of secure development practices derived from low-level artifacts (e.g., a publicly accessible document describing methodology, procedures, and processes).

### 1. Practices Directly Requiring Evidence of Supply-Chain Integrity

The SSDF organizes practices into four groups: **Prepare the Organization (PO)**, **Protect the Software (PS)**, **Produce Well-Secured Software (PW)**, and **Respond to Vulnerabilities (RV)**. The following practices are directly mapped to supply-chain integrity evidence (linked to EO 14028 Section 4e clauses):

#### a. Provenance Data (PS.3.2)
**"Collect, safeguard, maintain, and share provenance data for all components of each software release (e.g., in a software bill of materials [SBOM])."**
- **Expected evidence**: SBOMs for every release. Provenance data must be integrity-protected, updated when any component changes, shared with acquirers (preferably standards-based formats), and made available to operational/response teams. Recipients must be able to verify provenance data integrity.
- **EO 14028 mapping**: 4e(vi) (maintain provenance), 4e(vii) (SBOM), 4e(ix), 4e(x).
- **References**: SP 800-53 SR-4 (Provenance), SR-3 (Supply Chain Controls).

#### b. Software Integrity Verification (PS.2.1)
**"Make software integrity verification information available to software purchasers and consumers."**
- **Expected evidence**: Cryptographic hashes for release files posted on well-secured websites. Established certificate authority for code signing. Consumers can verify the software they acquire is legitimate and untampered.
- **EO 14028 mapping**: 4e(iii), 4e(ix), 4e(x).

#### c. Secure Archival of Releases (PS.3.1)
**"Securely archive the necessary files and supporting data (e.g., integrity verification information, provenance data) to be retained for each software release."**
- **Expected evidence**: Release files, associated images, integrity verification information, and provenance data stored with read-only access in secure repositories. Integrity/provenance data kept separate from release files.

#### d. Third-Party Security Requirements (PO.1.3)
**"Communicate requirements to all third parties who will provide commercial software components."**
- **Expected evidence**: Requirements in acquisition documents/contracts. Third-party attestation of compliance. **Provenance data and integrity verification mechanisms** required from third parties for all components. Processes documented for addressing non-compliance.

#### e. Toolchain Artifacts (PO.3.2, PO.3.3)
**PO.3.2**: Follow security practices to deploy and maintain tools/toolchains. **PO.3.3**: **"Configure tools to generate artifacts of their support of secure software development practices as defined by the organization."**
- **Expected evidence**: Tool-generated records (workflow tracking, issue tracking, value stream mapping). Security and retention policies for artifact data. Regularly verify integrity and provenance of each tool.
- **EO 14028 mapping**: 4e(ii) (artifacts from 4e(i)), 4e(iii), 4e(v), 4e(vi).

#### f. Component Integrity and Provenance Verification (PW.4.1, PW.4.4, PW.4.5)
- **PW.4.1**: Acquire and maintain well-secured components from reputable sources; evaluate security posture; track inventory.
- **PW.4.4**: **Verify components comply with requirements throughout their life cycles** — monitor for new vulnerabilities, confirm continued maintenance, verify provenance and integrity as versions change.
- **PW.4.5**: **"Verify the integrity and check the provenance of all in-house and third-party software components before reusing them for the organization's own software."**
- **Expected evidence**: Component inventory (SBOM). Intake gate decisions. Continuous re-verification records. Provenance verification results.
- **EO 14028 mapping**: 4e(iii), 4e(vi), 4e(x).

#### g. Secure Development Environments (PO.5.1, PO.5.2)
**"Separate and protect each environment involved in software development"** and **"Secure and harden development endpoints."**
- **Expected evidence**: Administratively separate build environments. Multi-factor authentication. Audit logs of trust relationships. Encryption for data. Monitoring/alerting records.
- **EO 14028 mapping**: 4e(i)(A)–(F), 4e(ii).

### 2. Attestation as Evidence (EO 14028 4e(ix))
The SSDF (via NIST's EO 14028 guidance) expects a **conformance statement** (first-party attestation) from the software producer covering:
- Producer name and product description.
- Statement that the producer follows applicable SSDF practices.
- Point of contact who can provide **artifacts generated by secure software development activities** related to 4e(i), 4e(iii), and 4e(iv).
- High-level artifacts preferred over low-level artifacts for procurement.

## C. Comparative Summary

| Dimension | SLSA (v1.2) | NIST SSDF (v1.1) |
|-----------|-------------|-------------------|
| **Evidence type** | Single signed provenance attestation (cryptographic, machine-verifiable) | Broad range: SBOMs, hashes, signatures, scan reports, logs, threat models, conformance statements |
| **Granularity** | Per-build, per-artifact | Organization-level practices spanning the SDLC |
| **Verification model** | Consumer verifies signature + expectations against roots of trust | Producer self-attests; purchaser may request high-level artifacts |
| **Provenance definition** | Build-specific: `buildDefinition` + `runDetails` with cryptographic digests | "Chronology of origin, development, ownership, location, and changes" [SP 800-53] |
| **Integrity mechanism** | Digital signature on in-toto attestation envelope, transparency logs recommended | Cryptographic hashes, code signing, protected repositories, SBOM integrity protection |
| **Levels/gradation** | Three Build levels (L1: exists, L2: authentic, L3: unforgeable + isolated) | Risk-based; all applicable practices expected, not tiered |
| **Key evidence artifact** | SLSA Provenance (JSON, in-toto Statement) | SBOM + conformance attestation + tool-generated artifacts |
| **Trust model** | Trust the build platform (`builder.id`); verify the artifact | Trust the producer's attestation; verify through artifacts on request |
