# Evidence Expected by SLSA Provenance and NIST SSDF for Software Supply-Chain Integrity

## Analyst's Refinement of Collector Artifact [artifact-54299cb5-4]

This Artifact identifies, compares, and distinguishes the evidence each framework expects. The analysis is verified against primary specifications read directly.

---

## A. SLSA Provenance (slsa.dev/spec/v1.2)

SLSA defines a single, machine-verifiable evidence type: the **signed in-toto provenance attestation** with `predicateType: "https://slsa.dev/provenance/v1"`. The predicate version is major v1 (current minor v1.2); minor changes do not alter the predicateType URI.

### Evidence Content (Provenance Fields)

**`buildDefinition`** — the input to the build:
- **`buildType`** (TypeURI, REQUIRED at L1): Identifies the build template. MUST resolve to human-readable specification.
- **`externalParameters`** (object, REQUIRED at L1): Untrusted parameters from the user/tenant (e.g., source repo, ref). MUST be fully enumerated at L3; best effort at L1–L2. Verifiers SHOULD reject unrecognized fields.
- **`internalParameters`** (object, OPTIONAL): Trusted platform-set parameters, not verified downstream.
- **`resolvedDependencies`** (array of ResourceDescriptor): Artifacts fetched during build, each with `uri`, `digest` (sha256, sha512, gitCommit, etc.), and optional `name`, `downloadLocation`, `annotations`. Completeness is best effort through L3.

**`runDetails`** — execution metadata:
- **`builder.id`** (TypeURI, REQUIRED at L1): Identifies the trusted build platform; is the sole determiner of SLSA Build level. Must be distinct per operating mode.
- **`builder.builderDependencies`** and **`builder.version`**: Platform dependencies and component versions.
- **`metadata.invocationId`**, **`startedOn`**, **`finishedOn`**: Invocation identity and timestamps.
- **`byproducts`**: Supplementary artifacts for debugging/incident response (e.g., logs, evaluated build config digests).

### Evidence Integrity by SLSA Build Level

| Requirement | L1 | L2 | L3 |
|---|---|---|---|
| **Provenance Exists** | Generated, identifies output by cryptographic digest. Best-effort completeness. | Same as L1. | Same as L1. |
| **Provenance Authentic** | None. | MUST be digitally signed by a key accessible only to the platform's control plane. Consumer MUST verify signature. Tenant MUST NOT generate provenance fields (except `subject` and non-required fields). Completeness SHOULD be complete. | Same as L2. |
| **Provenance Unforgeable** | None. | None. | Signing keys in secure management, inaccessible to user-defined build steps. Every field generated or verified by trusted control plane. External parameters MUST be fully enumerated. |
| **Isolation Strength** | None. | Hosted platform (not individual workstation). | Isolated: ephemeral environments, no cross-build interference, no cache poisoning, no secret access by builds. |

### Verification Evidence (Verifier Side)

Per the verifying-artifacts specification, verification MUST check:
1. Envelope signature against pre-configured roots of trust (public key identity + `builder.id` → SLSA Build level).
2. `subject` digest matches the artifact.
3. `predicateType` equals `https://slsa.dev/provenance/v1`.
4. `builder.id` is in trusted roots of trust.
5. Expected `buildType`, canonical source repository, and `externalParameters` match. Unrecognized `externalParameters` SHOULD cause failure.
6. (Optional) Recursive `resolvedDependencies` verification; Verification Summary Attestations (VSAs) may cache prior results.

**Key analytical point:** SLSA evidence is per-build and per-artifact. The provenance attestation _is_ the evidence. Trust is placed in the build platform (`builder.id`), not the producer's self-attestation.

## B. NIST SSDF (SP 800-218 v1.1)

The SSDF defines **artifact** as "a piece of evidence" [NISTIR 7692] and **evidence** as "grounds for belief or disbelief; data on which to base proof or to establish truth or falsehood" [SP 800-160 Vol. 1]. Evidence is broader and more varied than SLSA's single attestation model.

### Two Tiers of Artifacts (per EO 14028 Section 4e Guidance)

- **Low-level artifacts**: threat models, logs, source files, vulnerability scan reports, test results, telemetry, risk-based mitigation decisions — generated manually or automatically, maintained by the producer.
- **High-level artifacts**: summaries of secure development practices derived from low-level artifacts (e.g., a publicly accessible document describing methodology, procedures, and processes). NIST recommends purchasers request high-level artifacts for EO 14028 compliance.

### Practices Directly Requiring Supply-Chain Integrity Evidence

**PS.3.2 — Collect, safeguard, maintain, and share provenance data for all components of each software release.**
- Expected evidence: SBOMs for every release; integrity-protected provenance data; updated when components change; shared with acquirers in standards-based formats; verifiable by recipients.
- EO 14028 mapping: 4e(vi) (provenance), 4e(vii) (SBOM), 4e(ix), 4e(x).

**PS.2.1 — Make software integrity verification information available.**
- Expected evidence: Cryptographic hashes for release files on well-secured websites; code signing certificates; mechanisms for consumers to verify software is legitimate and untampered.
- EO 14028 mapping: 4e(iii), 4e(ix), 4e(x).

**PS.3.1 — Securely archive releases and supporting data.**
- Expected evidence: Release files, images, integrity verification data, and provenance data in secure repositories with read-only access. Integrity/provenance data kept separate from release files.

**PO.1.3 — Communicate security requirements to third-party component suppliers.**
- Expected evidence: Requirements in contracts/acquisition documents; third-party attestation of compliance; provenance data and integrity verification mechanisms required from third parties.
- EO 14028 mapping: 4e(vi), 4e(ix).

**PO.3.2 / PO.3.3 — Secure toolchains and configure tools to generate artifacts.**
- Expected evidence: Tool-generated records (workflow tracking, issue tracking, value stream mapping); security and retention policies for artifact data; regular integrity and provenance verification of each tool.
- EO 14028 mapping: 4e(ii), 4e(iii), 4e(v), 4e(vi).

**PW.4.1 / PW.4.4 / PW.4.5 — Verify component integrity and provenance throughout the lifecycle.**
- Expected evidence: Component inventory (SBOM); intake gate decisions; continuous re-verification records; provenance verification results.
- EO 14028 mapping: 4e(iii), 4e(vi), 4e(x).

**PO.5.1 / PO.5.2 — Separate and protect development environments; secure endpoints.**
- Expected evidence: Administratively separate build environments; MFA; audit logs of trust relationships; encryption; monitoring/alerting records.
- EO 14028 mapping: 4e(i)(A)–(F), 4e(ii).

### Attestation as Evidence (EO 14028 Section 4e(ix))

The SSDF expects a **first-party conformance attestation** from the software producer containing:
- Producer name and product description.
- Statement that the producer follows applicable SSDF practices.
- Point of contact who can provide artifacts from 4e(i), 4e(iii), and 4e(iv) activities.

First-party (self-) attestation is recommended unless risk dictates second- or third-party assessment. High-level artifacts are preferred over low-level artifacts for procurement.

## C. Comparative Analysis

| Dimension | SLSA v1.2 | NIST SSDF v1.1 |
|---|---|---|
| **Evidence type** | One signed cryptographic attestation (in-toto Statement) | Broad spectrum: SBOMs, hashes, signatures, scan reports, logs, threat models, conformance statements |
| **Granularity** | Per-build, per-artifact | Organization-level, spanning the full SDLC |
| **Verification model** | Consumer verifies signature + expectations against pre-configured roots of trust | Producer self-attests conformity; purchaser may request artifacts |
| **Provenance definition** | Build-specific: `buildDefinition` + `runDetails` with cryptographic digests | "Chronology of the origin, development, ownership, location, and changes to a system or system component" [SP 800-53] — far broader scope |
| **Integrity mechanism** | Digital signature on attestation envelope; transparency logs recommended | Cryptographic hashes, code signing, protected repositories, SBOM integrity protection |
| **Levels** | Three Build levels (L1: exists, L2: authentic + hosted, L3: unforgeable + isolated) | Risk-based; all applicable practices expected; not tiered |
| **Key deliverable** | SLSA Provenance (JSON, in-toto Statement) | SBOM + conformance attestation + tool-generated artifacts |
| **Trust anchor** | Build platform (`builder.id`); verify the artifact | Producer's attestation; verify through artifacts on request |

### Critical Distinctions

1. **SLSA provenance is narrowly scoped** to the build process: it answers "how was this artifact produced?" SSDF provenance includes the full chronology of origin, development, ownership, and changes — a superset.

2. **SLSA evidence is cryptographic and automatable**; SSDF evidence includes narrative, documentary, and organizational forms that require human judgment.

3. **SLSA places trust in the build platform**, not the producer. The SSDF places trust in the producer's first-party attestation, with the option to escalate to second- or third-party assessment based on risk.

4. **SLSA's three levels are prescriptive and verifiable by machine.** The SSDF is a risk-based framework — practices are recommended, not tiered, and conformance is demonstrated through attestation and artifacts rather than automated verification.
