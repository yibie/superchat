# Provenance Facts in SPDX 3.0.1 and CycloneDX 1.7 — Analyst Assessment

**Role:** analyst  
**Standards examined:** SPDX 3.0.1 (ISO/IEC 5962:2021), CycloneDX v1.7 (ECMA-424, 2nd ed., Dec 2025)  
**Complementary frameworks consulted:** SLSA v1.0, in-toto attestations, Sigstore  
**Date:** 2026-08-05

---

## 1. What Provenance Facts Each Standard Can Represent

### 1.1 SPDX 3.0.1 — Provenance-Carrying Properties

SPDX 3.0.1 represents provenance through the Core, Software, Build, and Security profiles. Key facts verified against the specification at `spdx.github.io/spdx-spec/v3.0.1/`:

**Origin and distribution identity**
- `originatedBy` (Core/Artifact): identifies from where or whom the Element originally came. Range: Agent (Person, Organization, SoftwareAgent). [Evidence: spdx.github.io/spdx-spec/v3.0.1/model/Core/Properties/originatedBy/]
- `suppliedBy` (Core/Artifact): identifies the actual distribution source; may differ from originator. Also applies to VulnAssessmentRelationship. [Evidence: spdx.github.io/spdx-spec/v3.0.1/model/Core/Properties/suppliedBy/]
- `createdBy` and `createdUsing` (Core/CreationInfo): who created the SPDX element and with which tool(s).

**Temporal facts**
- `builtTime`, `releaseTime`, `validUntilTime` on Artifact; `created` on CreationInfo; `startTime`/`endTime` on LifecycleScopedRelationship.

**Integrity**
- `verifiedUsing` (Core/Artifact): array of IntegrityMethod — cryptographic hashes and PackageVerificationCode.
- `Hash` class (algorithm + hashValue); `ExternalMap.verifiedUsing` for externally defined Elements.

**Build provenance (Build Profile)**
- `Build` class: `buildType` (IRI of toolchain), `buildId`, `buildStartTime`, `buildEndTime`, `configSourceUri`, `configSourceDigest`, `configSourceEntrypoint`, `environment` (name-value pairs), `parameter` (name-value pairs).
- Required relationships: `hasInput`, `hasOutput`, `invokedBy` (Agent). Optional: `hasHost`, `configures`, `ancestorOf`, `descendantOf`, `usesTool`. All scoped to `build` LifecycleScopeType. [Evidence: spdx.github.io/spdx-spec/v3.0.1/model/Build/Build/]

**Relationships and completeness**
- Relationship vocabulary: DEPENDS_ON, CONTAINS, GENERATES, ANCESTOR_OF, VARIANT_OF, PATCH_FOR, etc.
- `RelationshipCompleteness`: `complete`, `incomplete`, `noAssertion`.

**Lifecycle and identity**
- `sbomType` (design, source, build, deployed, etc.); `primaryPurpose`/`additionalPurpose` (application, framework, library, etc.).
- `ExternalIdentifier`: typed identifiers (packageUrl, cpe22, cpe23, gitoid, swhid). `ExternalRef`: typed external references.

### 1.2 CycloneDX 1.7 (ECMA-424) — Provenance-Carrying Properties

CycloneDX defines provenance explicitly as "the chain of custody and origin of a software component … incorporating the point of origin through distribution as well as derivatives." Key facts verified against ECMA-424 2nd ed.:

**Component-level provenance fields**
- `supplier`: Organization providing the component (manufacturer, distributor, repackager). Includes name, URL(s), contact(s).
- `manufacturer`: Organization that created the component.
- `author`: Individual or organization responsible for creating the component.
- `publisher`: Entity that published the component (may differ from supplier/author).
- `group`: Namespace for the component.

**Identity and locators**
- `purl` (Package URL), `swid` (ISO/IEC 19770-2:2015), `cpe`, `omniborId`, `swhid`.
- `bom-ref`: internal unique reference; BOM-Link (`urn:cdx:…`) for cross-document references.

**Integrity (Hashes)**
- Algorithms: MD5, SHA-1, SHA-256, SHA-384, SHA-512, SHA3-256/384/512, BLAKE2b-256/384/512, BLAKE3, Streebog-256/512.

**Pedigree (§4.8)**
- `pedigree` data structure describes lineage: `ancestors`, `descendants`, `variants`, `commits`, `patches`, `notes`. Models forks, modifications, and complex supply chain scenarios. [Evidence: ECMA-424 2nd ed. §4.8; schema/bom-1.7.proto Pedigree message]

**Formulation (MBOM, §6.13)**
- `formulation` array: describes how any referencable object was created, assembled, deployed, tested, or certified.
- Modeled as `formulas` (declared and observed), each composed of `workflows`, `tasks`, and `steps`.
- Covers: software build pipelines, deployment processes, AI/ML model training, cryptographic key generation, third-party audits.

**Citations**
- Structured attributions identifying which entity (tool, person, organization, process) supplied specific pieces of information, linked via JSON Pointers, with timestamps.

**Declarations and Attestations (CDXA)**
- `declarations`: conformance claims against standards with `attestations`, `claims`, `counter-claims`, `evidence`, `counter-evidence`, `conformance` score (0–1), `confidence`, and `signatories` (digital and analog).
- Evidence carries: author, reviewer, created/expires timestamps, propertyName, description, data, and external references.

**Enveloped signatures**
- `signature` array using JSON Signature Format (JSF): in-document signing.

**BOM identity**
- `serialNumber` (RFC 4122 UUID) + `version` (integer); `timestamp` for BOM creation.

## 2. Comparative Provenance Coverage

| Provenance Fact | SPDX 3.0.1 | CycloneDX 1.7 |
|---|---|---|
| Originator / original author | `originatedBy` | `author`, `manufacturer` |
| Supplier / distributor | `suppliedBy` | `supplier` |
| Build process identity | Build Profile (Build class, buildType) | Formulation (declared + observed) |
| Build inputs/outputs | `hasInput` / `hasOutput` relationships | Formulation workflows/tasks/steps |
| Build environment | `environment` (name-value pairs) | Implicit in formulation tasks |
| Build invocation agent | `invokedBy` (Agent) | Formulation task attribution |
| Cryptographic integrity | `verifiedUsing` (Hash, IntegrityMethod) | `hashes` on components/services/tools |
| Temporal facts | `builtTime`, `releaseTime`, `validUntilTime` | `timestamp` on BOM; formulation task timestamps |
| Modification lineage | Relationship types (ANCESTOR_OF, etc.) | `pedigree` (ancestors, descendants, variants, commits, patches) |
| Enveloped signing | External (not embedded) | `signature` array (JSF, in-document) |
| Attestation/evidence | Annotation; Security profile VEX | CDXA declarations, claims, evidence, signatories |
| Conformance claims | Not native | CDXA declarations with conformance scores |
| Lifecycle phase | `sbomType`, `LifecycleScopeType` | `lifecycles` (design through decommission) |
| Completeness assertion | `RelationshipCompleteness` | `compositions` (complete, incomplete, etc.) |
| Component identity | `ExternalIdentifier` (purl, cpe, swhid, gitoid) | `purl`, `swid`, `cpe`, `omniborId`, `swhid` |
| AI/ML model provenance | AI Profile (AIPackage, hyperparameters, training data) | ML-BOM (model cards, datasets, training formulation) |

## 3. Supply-Chain Questions Outside Both Specifications

These are not specification defects; they reflect questions for which SBOM/provenance formats are not the appropriate instrument. Other standards (SLSA, in-toto, Sigstore, Reproducible Builds) address these.

### 3.1 Build Integrity and Tampering Resistance
Neither format cryptographically proves that a binary was produced from a specific source by an uncompromised build system. A compromised CI pipeline can produce a technically valid SBOM or CycloneDX formulation that omits or misrepresents injected malicious code. SLSA provenance (in-toto attestations) was explicitly designed to answer "who built this, how, and from where?" with signed, verifiable evidence from a trusted control plane. [Evidence: slsa.dev/spec/v1.0/provenance — "the build platform…is trusted to faithfully run the build and record the provenance"; slsa.dev/spec/v1.0/threats-overview — attack E: "Compromise build process"]

### 3.2 Reproducibility Verification
Neither specification requires or enforces reproducible builds. An attacker who compromises the build environment can inject backdoors; the provenance record will faithfully show the clean source and official builder. Reproducible builds — rebuilding independently and comparing output hashes — remain outside both scopes. SLSA v1.0 makes hermetic and reproducible builds recommended, not required, even at Build L3. [Evidence: ostering.com analysis; SLSA v1.0 requirements]

### 3.3 Runtime vs. Build-Time Discrepancy
SBOMs generated at build time do not capture components installed at runtime, side-loaded modules, dynamically resolved dependencies, or post-deployment modifications. Neither format mandates continuous reconciliation between build-time inventory and deployed artifacts.

### 3.4 Behavioral Trustworthiness
Knowing "what is inside" does not predict what software will do when executed. A package with a clean dependency tree and valid provenance can still perform privilege escalation, credential access, data exfiltration, or persistence. Both standards are composition-oriented; neither addresses behavioral analysis or runtime capability verification.

### 3.5 Intent and Malice Detection
Provenance verifies origin, not intent. An attacker can register a package under a deceptive name, publish it properly, and generate a valid SBOM/BOM — the trust model is subverted without breaking any provenance chain. As SLSA explicitly states: "SLSA does not directly address this threat." [Evidence: slsa.dev/spec/v1.0/threats-overview, threat H]

### 3.6 Transitive Trust Inheritance
Neither specification provides a mechanism to automatically inherit trust or assurance across transitive dependencies. SLSA notes explicitly: provenance does not prove code quality, vendor intent, or automatically extend assurance across every transitive dependency.

### 3.7 AI/ML Model Authorship Provenance
SPDX 3.0 (AI Profile) and CycloneDX (ML-BOM) can describe models and datasets, but neither captures which specific model version, system prompt, or training run produced a given code block. AI Bills of Materials remain non-standardized in this regard.

### 3.8 Agentic/Untracked Supply-Chain Nodes
Current SBOM workflows do not model MCP server calls, agent-to-agent delegations, or AI-agent tool invocations as supply-chain steps. Autonomous dependency modifications escape SBOM capture if generation happens only at fixed build points. This is an emerging gap as AI coding agents become supply-chain actors.

### 3.9 Governance and Decision Intelligence
Both specifications provide data (the "what"), but neither provides a governance layer for interpreting changes across SBOMs over time, producing explainable risk decisions, or reconciling SBOM, VEX, provenance, and deployment records into a unified trust evaluation. This is a system-integration concern, not a format concern.

### 3.10 Signature Verification Mandate
CycloneDX carries JSF signatures natively; SPDX 3.0 typically requires an external signing envelope. Neither specification mandates signature verification at consumption — tools commonly ingest unsigned SBOMs without complaint. This is an implementation enforcement gap, not a specification gap per se.

## 4. Complementary Standards (Evidence-Based)

| Standard | Question Answered | Relationship to SPDX/CycloneDX |
|---|---|---|
| SLSA / in-toto attestations | "How was it built, by whom, from what source?" | Complements SBOM; build integrity not covered by SPDX/CDX |
| Sigstore (cosign, Rekor) | "Is the artifact signature verifiable against a transparency log?" | Keyless signing; binds artifact digests to CI identities |
| VEX (CSAF, CycloneDX VEX) | "Is this vulnerable component actually exploitable in context?" | Filters vulnerability noise; both SPDX and CDX can carry VEX |
| SCAI (Supply Chain Attribute Integrity) | "What attributes apply to this build step?" | Augments build provenance with compiler flags, etc. |
| Reproducible Builds | "Does rebuild produce bitwise-identical output?" | Detects build tampering; outside SBOM scope |

---

## 5. Key Analytic Findings

1. **SPDX and CycloneDX have substantially converged on provenance.** SPDX 3.0's Build Profile and CycloneDX 1.7's Formulation both now address build process description — a domain previously exclusive to SLSA/in-toto. The collector artifact correctly identifies this convergence.

2. **The critical boundary is signed, verifiable attestation vs. descriptive metadata.** Both standards can describe what happened during a build, but neither natively provides the cryptographically verifiable, control-plane-signed attestation that SLSA provenance does. CycloneDX's JSF signatures partially close this gap but lack the trusted control-plane model of SLSA L2+.

3. **Pedigree in CycloneDX is richer than SPDX for modification history.** CycloneDX's pedigree structure (ancestors, descendants, variants, commits, patches) has no direct SPDX equivalent beyond generic relationship types. This gives CycloneDX an advantage for complex supply chains involving forks, patches, and modifications.

4. **Build integrity (SLSA's domain) remains the largest gap.** As the ostering.com analysis states: "Provenance proves origin, not innocence. It records which commit and process produced the artefact; it does not vouch for the commit, the integrity of the build, or the safety of the code."

5. **Emerging gaps around AI agents and dynamic supply chains** are not addressed by either standard and represent a frontier where current specifications will need evolution.
