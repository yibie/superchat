# Provenance Facts Representable in SPDX and CycloneDX — and What Remains Outside

**Role:** collector  
**Source specifications:** SPDX 3.0.1 (ISO/IEC 5962:2021), CycloneDX v1.7 (ECMA-424, 2nd ed., Dec 2025)  
**Date:** 2026-08-05

---

## 1. Provenance Facts SPDX Can Represent

SPDX 3.0.1 defines provenance through the Core, Software, Build, and Security profiles. Key provenance-carrying properties and classes, drawn directly from the specification:

### Origin and Supplier Identification
- **originatedBy** (Core/Artifact): Identifies from where or whom the Element originally came. Range: Agent (Person, Organization, SoftwareAgent).  
- **suppliedBy** (Core/Artifact): Identifies the actual distribution source; may differ from the originator. Range: Agent.  
- **createdBy** (Core/CreationInfo): Who created the SPDX Element.  
- **createdUsing** (Core/CreationInfo): Tool(s) used in creation.  

### Temporal Facts
- **builtTime** (Core/Artifact): When the artifact was built.  
- **releaseTime** (Core/Artifact): When the artifact was released.  
- **created** (Core/CreationInfo): When the SPDX data was created.  
- **validUntilTime** (Core/Artifact): Expiry of the artifact's validity.  
- **startTime / endTime** (Core/LifecycleScopedRelationship): Scoped lifecycle windows.

### Integrity and Verification
- **verifiedUsing** (Core/Artifact): IntegrityMethod array — cryptographic hashes (SHA-256, SHA-512, etc.) and PackageVerificationCode (SPDX 2.x compat).  
- **Hash** (Core): algorithm + hashValue.  
- **ExternalMap.verifiedUsing**: Integrity check for externally defined Elements.  
- **contentIdentifier** (Software): Package URL, SWID, gitoid, SWHID, CPE.  

### Build Provenance (Build Profile)
- **Build** class with: buildType (IRI of toolchain/platform), buildId (locally unique), buildStartTime, buildEndTime, configSourceUri, configSourceDigest, configSourceEntrypoint, environment (name-value pairs), parameter (name-value pairs).  
- Relationships: **hasInput**, **hasOutput**, **invokedBy** (Agent), **hasHost**, **configures**, **ancestorOf/descendantOf**, **usesTool** — all scoped to `build` LifecycleScopeType.  

### Relationships
- SPDX Relationship vocabulary includes: DEPENDS_ON, CONTAINS, GENERATES, ANCESTOR_OF, VARIANT_OF, PATCH_FOR, and many others.  
- **RelationshipCompleteness** can mark relationships as `complete`, `incomplete`, or `noAssertion`.

### Lifecycle and Purpose
- **sbomType** (Software/Sbom): design, source, build, deployed, etc.  
- **primaryPurpose** / **additionalPurpose** (Software/Package): application, framework, library, operating-system, etc.  
- **LifecycleScopeType**: design, build, testing, deployment, etc.  

### Identity and External References
- **ExternalIdentifier**: typed identifiers (packageUrl, cpe22, cpe23, gitoid, swhid).  
- **ExternalRef**: typed references to external resources (security advisory, fix, documentation, etc.).  

### Security/Provenance Intersection
- **suppliedBy** on VulnAssessmentRelationship.  
- Vulnerability timestamps (publishedTime, modifiedTime, withdrawnTime).

## 2. Provenance Facts CycloneDX Can Represent

CycloneDX v1.7 (ECMA-424) defines provenance explicitly as "the chain of custody and origin of a software component … incorporating the point of origin through distribution as well as derivatives." The specification provides:

### Component-Level Provenance Fields
- **supplier**: Organization providing the component (manufacturer, distributor, repackager). Includes name, URL(s), contact(s).  
- **manufacturer**: Organization that created the component.  
- **author**: Individual or organization responsible for creating the component.  
- **publisher**: Entity that published the component (may differ from supplier/author).  
- **group**: Namespace for the component, often the producing organization or project.  

### Identity and Locators
- **purl** (Package URL): Standardized ecosystem identifier pinpointing the registry/repository of origin.  
- **swid** (ISO/IEC 19770-2:2015): Globally unique software identity tag with tagId, name, version, and XML payload.  
- **cpe**: Common Platform Enumeration.  
- **omniborId, swhid**: Additional identifiers.  
- **bom-ref**: Internal unique reference for cross-referencing within a BOM; BOM-Link (urn:cdx:…) for cross-document references.  

### Integrity (Hashes)
- **hashes** on components, services, and tools: MD5, SHA-1, SHA-256, SHA-384, SHA-512, SHA3-256/384/512, BLAKE2b-256/384/512, BLAKE3, Streebog-256/512.  

### Pedigree and Modification History
- **pedigree** (defined in §4.8): Data describing the lineage and/or process by which software was created or altered. Includes commits, patches, diffs, and the identities of who authored and committed modifications.  

### Formulation (Manufacturing Bill of Materials — MBOM)
- **formulation** array: Describes how any referencable object was created, assembled, deployed, tested, or certified.  
- Modeled as: **formulas** (declared and observed), each composed of **workflows**, **tasks**, and **steps**.  
- Supports software build pipelines, deployment processes, AI/ML model training, cryptographic key generation, third-party audits.  

### Citations
- Structured attributions identifying which entity (tool, person, organization, process) supplied specific pieces of information, linked via JSON Pointers, with timestamps.  

### Declarations and Attestations (CDXA)
- **declarations**: Conformance claims against standards.  
- Each declaration includes: **attestations**, **claims**, **counter-claims**, **evidence**, **counter-evidence**, **conformance** score (0–1), **confidence**, and **signatories** (digital and analog).  
- Evidence carries: author, reviewer, created/expires timestamps, propertyName (per CycloneDX Property Taxonomy), description, data, and external references.  
- **mitigationStrategies** for non-conformance.  

### External References
- Typed external references: vcs, issue-tracker, build-system, documentation, distribution, formulation, security-contact, rfc-9116, and many more.  

### Lifecycle and Composition Completeness
- **lifecycles** in metadata: design, pre-build, build, post-build, operations, discovery, decommission.  
- **compositions**: aggregate completeness (complete, incomplete, incomplete_first_party_only, incomplete_third_party_only, unknown).  

### Enveloped Signatures
- **signature** array using JSON Signature Format (JSF) — in-document signing, unlike SPDX which typically needs an external signing envelope.  

### BOM Identity and Versioning
- **serialNumber** (RFC 4122 UUID) + **version** (integer) = BOM identity.  
- **timestamp** for BOM creation.

## 3. Supply-Chain Questions That Remain Outside Both Specifications

Neither SPDX nor CycloneDX are designed to answer the following classes of supply-chain questions. These are not gaps in the sense of specification defects; they are questions for which other standards (SLSA, in-toto, Sigstore) or complementary practices exist.

### A. Build Integrity and Tampering Detection
Neither format cryptographically proves that the binary was built from a specific source commit by an uncompromised build system. A compromised CI pipeline can produce a clean-looking SBOM or a valid CycloneDX formulation that omits malicious insertions. SLSA provenance (in-toto attestations) was created expressly to fill this gap — it answers "Who built this, how, and from where?" rather than "What is inside?"

### B. Reproducibility Verification
Neither specification requires or enforces reproducible builds. An attacker who compromises the build environment can inject backdoors; the provenance record will faithfully show the clean source and official builder. Reproducible builds — rebuilding independently and comparing output hashes — are outside the scope of SPDX and CycloneDX.

### C. Runtime vs. Build-Time Discrepancy
SBOMs generated at build time do not capture components installed at runtime, side-loaded modules, dynamically resolved dependencies, or post-deployment modifications. Neither format mandates continuous reconciliation between build-time inventory and deployed/running artifacts.

### D. Behavioral Trustworthiness
Knowing "what is inside" does not predict what software will do when executed. A package with a clean dependency tree and valid provenance can still perform privilege escalation, credential access, data exfiltration, or persistence. Both SPDX and CycloneDX are composition-oriented; neither addresses behavioral analysis or runtime capability verification.

### E. Intent and Malice Detection
Provenance verifies origin, not intent. An attacker can register a package under a hallucinated name (as in AI-package-hallucination attacks), publish it properly, and generate a valid SBOM/BOM — the trust model is subverted without breaking any provenance chain. Neither format distinguishes between a legitimate author and a malicious one.

### F. AI/ML Model Authorship Provenance
SPDX 3.0 (AI Profile) and CycloneDX (ML-BOM) can describe models and datasets, but neither captures which specific model version, system prompt, or training run produced a given code block. AI Bills of Materials remain non-standardized.

### G. Agentic/Untracked Supply-Chain Nodes
Current SBOM workflows do not model MCP server calls, agent-to-agent delegations, or AI-agent tool invocations as supply-chain steps. Autonomous dependency modifications (e.g., an AI agent editing a requirements file) escape SBOM capture if generation happens only at fixed build points.

### H. In-Document vs. External Signing
CycloneDX carries JSF signatures natively; SPDX 3.0 typically requires an external signing envelope or detached signature. This means SPDX consumers must separately manage signature verification infrastructure. Neither specification *mandates* signature verification at consumption — tools like OWASP Dependency-Track will ingest unsigned SBOMs without complaint.

### I. Transitive Trust Inheritance
Neither specification provides a mechanism to automatically inherit trust or assurance across transitive dependencies. SLSA explicitly notes this boundary: provenance does not prove code quality, vendor intent, or automatically extend assurance across every transitive dependency.

### J. Governance and Decision Intelligence
Both specifications provide data (the "what"), but neither provides a governance layer for interpreting changes across SBOMs over time, producing explainable/defensible risk decisions, or reconciling SBOM, VEX, provenance, and deployment records into a unified trust evaluation.

## 4. Complementary Standards (In Brief)

- **SLSA / in-toto attestations**: Build integrity, tamper-resistant provenance. Answers "how was it built?"  
- **Sigstore (cosign)**: Keyless signing, transparency logs. Binds artifact digests to CI identities.  
- **VEX (CSAF, CycloneDX VEX)**: Exploitability context — filters vulnerability noise.  
- **SCAI (Supply Chain Attribute Integrity)**: Attributes about build steps (e.g., compiler flags).  
- **Reproducible Builds**: Independent rebuild verification.
