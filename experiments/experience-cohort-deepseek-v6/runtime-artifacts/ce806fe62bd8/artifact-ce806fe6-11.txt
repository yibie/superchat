# Safe vs. Idempotent HTTP Methods and Automated Retries — Analysis Per RFC 9110

## Source

RFC 9110 ("HTTP Semantics"), Standards Track, June 2022. Authors: R. Fielding (Adobe), M. Nottingham (Fastly), J. Reschke (greenbytes).  
Primary URL: https://www.rfc-editor.org/rfc/rfc9110.html

---

## 1. The Distinction

RFC 9110 defines two orthogonal method properties in Section 9.2. They are not synonyms; they answer different questions.

### 1.1 Safe Methods (Section 9.2.1) — "Will this request change anything?"

> "Request methods are considered 'safe' if their defined semantics are essentially read-only; i.e., the client does not request, and does not expect, any state change on the origin server as a result of applying a safe method to a target resource."

**Evidence (direct from RFC 9110):** The RFC states the purpose explicitly: "The purpose of distinguishing between safe and unsafe methods is to allow automated retrieval processes (spiders) and cache performance optimization (pre-fetching) to work without fear of causing harm."

**Key evidence-based observations:**

- Safety is about the **client's intent and expectation**, not a server-side guarantee. The RFC acknowledges servers may have incidental side effects (logging, analytics, incrementing counters).
- Safe methods defined: GET (§9.3.1), HEAD (§9.3.2), OPTIONS (§9.3.7), TRACE (§9.3.8).

**Inference:** Safety is fundamentally a *contract of non-interference*. It licenses automated agents (crawlers, pre-fetchers, link checkers) to traverse URIs without understanding their semantics. Without this property, the web could not be safely crawled.

### 1.2 Idempotent Methods (Section 9.2.2) — "What happens if I send this twice?"

> "A request method is considered 'idempotent' if the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request."

**Evidence (direct):** The RFC further clarifies: "idempotency refers only to the intended effect on the server of the request; it does not include any side effects that might occur from logging, billing, or similar ancillary operations."

**Evidence-based observations:**

- All safe methods are idempotent by definition (they have no intended state-changing effect, so doing nothing N times = doing nothing once).
- Additionally idempotent but NOT safe: PUT (§9.3.4), DELETE (§9.3.5). PUT replaces state — a second identical PUT produces the same end state. DELETE removes the association — subsequent DELETEs have no further effect (possibly returning 404).
- Not idempotent: POST (§9.3.3) and CONNECT (§9.3.6).

**Inference:** The critical nuance is that idempotency concerns the *intended effect* — not response equality. Two PUT requests may return different responses (e.g., different ETags or timestamps) yet still be idempotent because the server-side resource state converges to the same result.

### 1.3 The Relationship

The subset relationship is strict: **Safe ⊂ Idempotent**. All safe methods are idempotent; PUT and DELETE are idempotent but not safe.

| Method | Safe | Idempotent |
|---|---|---|
| GET, HEAD, OPTIONS, TRACE | Yes | Yes |
| PUT, DELETE | No | Yes |
| POST, CONNECT | No | No |

**Inference:** This nested structure means idempotency is the *broader* retry-relevant category. If a method is safe, it inherits idempotency's retry permission automatically; but idempotent-unsafe methods (PUT, DELETE) also enjoy retry permission despite being state-changing.

## 2. Implications for Automated Retries

### 2.1 The Core Retry Rule (Section 9.2.2)

This is the most operationally consequential passage. Direct evidence:

> "A client MAY automatically retry a request with an idempotent method in the event of an underlying connection failure before it is able to determine whether the request was processed by the server (or the response was lost). However, a client MUST NOT automatically retry a request with a non-idempotent method, unless it has some means to know that the request semantics are actually idempotent, regardless of the method, or some means to detect that the original request was never applied."

Additionally, Section 2.4 (Error Handling) cross-references: "Some requests can be automatically retried by a client in the event of an underlying connection failure, as described in Section 9.2.2."

### 2.2 Analysis of the Retry Rule

The rule contains several elements worth distinguishing:

**(a) The permission (MAY):** Clients MAY retry idempotent-method requests. This is permissive, not mandatory. It grants license; it does not compel retry behavior.

**(b) The prohibition (MUST NOT):** Clients MUST NOT automatically retry non-idempotent requests. This is a hard constraint, the strongest requirement language in the RFC taxonomy (per BCP 14 / RFC 2119). The rationale is clear: automatic retry of a non-idempotent POST could produce duplicate side effects — double-charging a payment, creating duplicate resources.

**(c) The temporal boundary:** The retry permission applies only "before it is able to determine whether the request was processed." If the client received a complete HTTP response (any status code, including errors), it knows the request was processed and should not auto-retry regardless of idempotency. The ambiguity window is: connection dropped before any response, or the response was lost in transit.

**(d) The escape clauses (two explicit exceptions):**

1. **Known idempotency regardless of method:** The client has out-of-band knowledge that a specific POST request is factually idempotent (e.g., the server advertises idempotency-key support, or the client understands the resource semantics sufficiently).

2. **Detected non-application:** The client can confirm the original request was never applied (e.g., by checking resource state via a subsequent GET and finding no change).

**Inference:** These escape clauses are deliberately narrow. They require *positive knowledge*, not probabilistic assumptions. An HTTP client library should not infer idempotency; it must be told.

### 2.3 Why the Distinction Matters: Design Rationale

**Evidence (Section 3.1):** "One design goal of HTTP is to separate resource identification from request semantics, which is made possible by vesting the request semantics in the request method." A resource cannot treat a request in a manner inconsistent with the method's defined semantics.

**Inference:** The safe/idempotent taxonomy is what makes this separation work at scale. Because the method label carries semantic guarantees, intermediaries — proxies, caches, load balancers, CDNs — can make retry decisions without understanding the application logic behind each URI. A proxy can retry a failed PUT without knowing whether the resource represents a shopping cart, a document, or a configuration setting. This is a fundamental architectural property: the method is the contract, decoupled from the resource.

### 2.4 Practical Examples (Inference from the rules above)

- **GET /users/42** — connection fails before response → MAY auto-retry. No state change risk.
- **PUT /users/42** (body: `{"name":"Alice"}`) — connection fails → MAY auto-retry. Two identical PUTs = same final state for user 42.
- **DELETE /users/42** — connection fails → MAY auto-retry. First DELETE removes the user; second DELETE is a no-op (likely 404).
- **POST /orders** (body: order details) — connection fails → MUST NOT auto-retry without additional safeguards. Two POSTs could create two orders.

### 2.5 Scope: Clients, Proxies, and Intermediaries

**Inference (from the general applicability language in Sections 2.2 and 9.2.2):** The retry rule binds all HTTP participants acting in a client or forwarding role — user agents, proxies, and gateways alike. A proxy MUST NOT auto-retry a non-idempotent request on behalf of a client; if the proxy cannot obtain a response, it must propagate the failure upstream rather than risk duplicate side effects.

## 3. Boundary Conditions and Clarifications

### 3.1 Idempotency is Semantic, Not Implementational

**Evidence:** The RFC ties idempotency to "defined semantics," not to any particular server's behavior. A server could implement POST idempotently (e.g., via idempotency-key deduplication). Conversely, a server could implement PUT non-idempotently (e.g., an append-only log where each PUT creates a new entry). This does not change the method's *semantic label*.

**Inference:** The method label establishes what clients and intermediaries may *assume* without specific knowledge. Idempotency-key patterns (like Stripe's `Idempotency-Key` header) exist precisely to bridge this gap — they give clients a way to communicate to the server that a given POST *should be* treated as idempotent, thereby satisfying the first escape clause in §9.2.2.

### 3.2 Caching Interaction (Section 9.2.3)

**Evidence:** GET and HEAD responses are cacheable by default (§9.2.3). POST responses are cacheable only with explicit freshness information and a matching Content-Location header. PUT, DELETE, CONNECT, OPTIONS, and TRACE responses are not cacheable.

**Inference:** The caching rules reinforce the semantic taxonomy: safe methods benefit from caching (they retrieve); idempotent-but-unsafe methods invalidate caches (they change state); the non-idempotent POST sits in an intermediate position — its responses are only conditionally cacheable.

---

## 4. Summary

1. **Safety** concerns whether a method requests state change at all (client intent). Safe methods: GET, HEAD, OPTIONS, TRACE.

2. **Idempotency** concerns whether N identical requests have the same intended server effect as one request. Idempotent methods: all safe methods + PUT + DELETE.

3. **The retry contract (§9.2.2):** Clients MAY automatically retry idempotent-method requests on connection failure before the outcome is known. Clients MUST NOT automatically retry non-idempotent requests (notably POST) absent specific knowledge of idempotency or confirmed non-application.

4. **Architectural significance:** These properties enable HTTP intermediaries to reason about request safety without application-specific knowledge, underpinning the web's scalability, cacheability, and fault-tolerance.
