## Consolidated Answer: How Production Systems Make Retried Side Effects Idempotent, and Where Those Techniques Fail

### The Foundation

Exactly-once message delivery across an unreliable asynchronous network is mathematically impossible (Two Generals' Problem; FLP, JACM 1985). Production systems therefore compose **at-least-once delivery with idempotent processing**: the message may arrive many times, but the observable side effect lands once. This is an engineering approximation, not a formal guarantee.

### Technique 1: Idempotency Keys (HTTP Layer)

**How it works.** The client generates a unique value (UUID v4/v7) per logical operation and sends it as an `Idempotency-Key` header. The server atomically claims the key by inserting a row with a UNIQUE constraint, executes the business operation, stores the response, and returns the cached response on retry. Stripe, Adyen, PayPal, and most payment APIs use this pattern. It is in the process of IETF standardization (draft-ietf-httpapi-idempotency-key-header-07).

**Where it fails:**

1. **TOCTOU race (check-then-act).** Two retries arrive simultaneously; both SELECT find no key; both proceed to charge. Remedy: INSERT-first with ON CONFLICT, not SELECT-then-INSERT.

2. **Zombie PENDING lock.** The key is written as PENDING, then the process crashes (OOM, pod eviction, deploy). Every subsequent retry sees PENDING and returns 409 Conflict permanently. Remedy: lease-based recovery with a background completer that reclaims abandoned keys after a grace period.

3. **Request-body mismatch.** Client reuses the same key with a different payload ($200 vs $500). Without fingerprinting, the server silently returns the wrong cached response. Remedy: store a canonical hash of the request body and reject mismatches with 422.

4. **TTL expiry before retry window closes.** Stripe v1 retains keys 24h; v2 extends to 30d. A retry after expiry is treated as a fresh request and produces a duplicate. The TTL must exceed the longest legitimate retry path.

5. **Clock-skew TTL expiry.** When application-server and storage clocks diverge (common in containers), a key the application considers valid may already be expired in Redis. Remedy: delegate TTL evaluation entirely to the storage layer (SET NX EX) and add a skew buffer.

6. **Cross-region replication lag.** In active-active multi-region deployments, a retry routed to a different region may see no key if async replication hasn't caught up. Remedy: sticky routing by key hash, or synchronous replication stores (Spanner, CockroachDB).

7. **Non-idempotent downstream APIs.** When a foreign service lacks idempotency support and the failure is indeterminate (timeout, connection reset), you cannot safely retry. Remedy: mark the operation as permanently failed; reconciliation is the only fallback.

### Technique 2: Atomic Phases and Recovery Points

**How it works.** Multi-step workflows are decomposed into atomic phases — SERIALIZABLE database transactions whose boundaries sit between external calls. Each phase writes a `recovery_point` label (e.g., `started` → `ride_created` → `charge_created` → `finished`). A retry reads the cursor and resumes at the next unfinished phase. Foreign API idempotency keys are derived deterministically from internal keys. Brandur Leach's Rocket Rides (2017) is the canonical reference implementation.

**Where it fails:**

- **Schema version mismatch across deploys.** v1 stores responses in one schema, v2 in another; a retry during rollout reads a `response_body` the new parser cannot decode. Requires a `schema_version` column and backward-compatible deserialization.
- **Completer grace-period misconfiguration.** Too short and it races live requests; too long and abandoned work accumulates.
- **Foreign API lacks idempotency.** Indeterminate failures at the external boundary remain irrecoverable without manual reconciliation.

### Technique 3: Kafka Idempotent Producer + Transactions

**How it works.** Each producer gets a Producer ID (PID). Messages carry a monotonically increasing sequence number per (PID, partition). The broker deduplicates: any message with sequence number ≤ last committed is discarded. From Kafka 3.0 (KIP-679), `enable.idempotence=true` by default with `acks=all`. Transactions extend this across partitions using a `TransactionalId` and producer epoch for zombie fencing.

**Where it fails:**

1. **Single-session scope.** Without a `transactional.id`, idempotence is limited to one producer session. A producer restart gets a new PID and duplicates can occur across sessions.
2. **OutOfOrderSequenceException.** A sequence gap (data loss in producer-broker path) is a fatal error; the producer must be closed and recreated.
3. **Single-replica topics.** With replication factor 1, a power failure after ack but before disk flush loses acknowledged messages.
4. **Consumer isolation.** Consumers must use `isolation.level=read_committed` to skip aborted-transaction messages. The default `read_uncommitted` exposes phantom data.

### Technique 4: Transactional Outbox

**How it works.** The application writes the business row and an outbox event row in a single database transaction. A separate poller (or CDC tool like Debezium) publishes to the broker with at-least-once delivery. This eliminates the dual-write problem.

**Where it fails:** Duplicate publication on poller crash/restart (consumer-side idempotency still mandatory), ordering violations across partitions, outbox table growth during broker outages, and replay complexity when downstream consumers are non-idempotent.

### Technique 5: DynamoDB Conditional Writes

**How it works.** `PutItem` with `ConditionExpression="attribute_not_exists(id)"` ensures single insert. `TransactWriteItems` supports a `ClientRequestToken` for idempotent transactions within a fixed 10-minute window.

**Where it fails:** The 10-minute `ClientRequestToken` window is fixed and non-configurable. Operations exceeding this window lose idempotency entirely — a hard design constraint.

### Technique 6: Temporal Durable Execution

**How it works.** Workflow code is replayed deterministically from event history. Idempotency keys are generated in the workflow body (deterministic across replays), not inside activities. `SideEffect`/`MutableSideEffect` record non-deterministic results in event history.

**Where it fails:** Keys generated inside activities change on every retry, defeating deduplication. Non-deterministic workflow code (e.g., `math.random()` outside SideEffect) causes replay divergence. Compensating transactions in Saga patterns must themselves be idempotent — a timeout on a refund API followed by retry can produce a double refund.

## Cross-Cutting Conclusions

### Layering is Necessary

No single mechanism suffices. Production systems compose: HTTP middleware deduplication (network retries), database-layer deduplication (concurrent in-process retries), and external API idempotency keys (after-commit failures). Drop any layer and a duplicate window remains.

### The Idempotency Store Is a Distributed System

The key store itself is subject to replication lag, clock skew, eviction, and partition. When it fails, the choice is binary: fail closed (reject all mutating requests — standard for payments) or fail open (accept unprotected requests and reconcile later).

### Caching Policy: Deterministic Outcomes Only

Stripe v1 cached 500 errors permanently, forcing clients to mint fresh keys. v2 re-executes on 5xx. The modern rule: cache success and deterministic client errors (4xx), do not cache transient/unknown outcomes (5xx, timeouts). This is a business-policy decision.

### Five Failure Categories

All techniques fail across five categories: **concurrency races**, **crash-recovery gaps**, **temporal boundary violations** (TTL expiry, clock skew), **spatial boundary violations** (cross-region replication lag), and **semantic boundary violations** (non-idempotent downstream APIs). Every production system must address all five.

### The Residual Window

The FLP result guarantees that no protocol eliminates the failure window entirely. The engineering question is not "how do we achieve perfect idempotency" but "how small is the residual window, and what is the cost of closing it further?" Stripe's answer — at $1T payment volume — is a 24h–30d idempotency window with synchronous replication, atomic claims, lease-based recovery, and deterministic key derivation for foreign APIs. Even that has a ~3-second cross-region soft-duplicate window acknowledged in their documentation.
