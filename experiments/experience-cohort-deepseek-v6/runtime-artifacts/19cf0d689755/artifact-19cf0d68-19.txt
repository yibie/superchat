# Production Idempotency for Retried Side Effects: Techniques and Failure Modes

## Foundational Constraint

Exactly-once delivery across an unreliable network is mathematically impossible — proven by the Two Generals' Problem (Akkoyunlu, Ekanadham, Huber, 1975). Production systems therefore compose **at-least-once delivery with idempotent processing**: the message may arrive many times, but the side effect lands once. This artifact surveys the primary techniques and catalogues where each fails.

---

## Technique 1: Idempotency Keys (Client-Generated, Server-Stored)

**The pattern.** The client generates a unique identifier (UUID v4/v7) per logical operation and sends it in an `Idempotency-Key` header. The server atomically claims the key and executes the business work in the same database transaction. On retry, the server returns the stored response without re-executing. Stripe, PayPal, and most payment APIs use this approach. Sources: [Stripe docs](https://docs.stripe.com/api/idempotent_requests), [Brandur Leach's reference implementation](https://brandur.org/idempotency-keys), [Stripe blog](https://stripe.com/blog/idempotency).

**Core correctness rule.** The idempotency-key insert and the business mutation must execute in a single ACID transaction. The database's unique constraint on `(user_id, idempotency_key)` is the safety mechanism. `INSERT … ON CONFLICT DO NOTHING` is the atomic primitive; `SELECT`-then-`INSERT` is a TOCTOU race and demonstrably produces double-charges under concurrent retries [FlowVerify](https://www.flowverify.co/blog/idempotency-failure-modes-production).

### Failure Modes

1. **Concurrent-request race (check-then-act).** Two retries arrive within the same millisecond. Both `SELECT` find no key; both proceed to charge. The remedy is atomic insert-first semantics. Redis `SETNX` alone is insufficient unless the key and business write share a transaction boundary — otherwise a process crash between Redis-key-claim and Postgres-payment-commit opens a window for double execution [BackendBytes](https://backendbytes.com/articles/idempotency-patterns-distributed-systems/).

2. **Partial commit / zombie lock.** The key is marked `PENDING` or `processing`, then the pod is OOM-killed or evicted before completing. Every subsequent retry sees `PENDING` and returns `409 Conflict` forever — the payment is stuck. The fix is a **lease with expiry**: the `locked_at` timestamp is a lease; a reaper or retry checks staleness and reclaims abandoned keys. Stripe's completer process pushes orphaned keys to `finished` after a grace period (~5 minutes in the reference implementation) [sujeet.pro](https://sujeet.pro/articles/stripe-idempotency-reliability).

3. **Request-body mismatch.** A client reuses the same key with a different payload (e.g., $200 vs. $500). Without a request-fingerprint check, the server silently returns the cached response for the wrong operation. Stripe stores `request_params` as JSONB and returns `422` on mismatch. Fingerprint canonicalisation is itself a trap: including volatile fields (timestamps, request IDs) causes valid retries to be rejected [Tech News Today](https://technewstoday.info/why-an-idempotency-key-isnt-an-idempotency-guarantee/).

4. **TTL expiry before retry window closes.** Keys held for 24 hours (Stripe's default). A retry that arrives after the key is pruned creates a fresh execution. TTL must exceed the longest legitimate retry path. At 10K req/s, each additional day of TTL costs ~415 GB. Real-world TTLs: Stripe 24h (v2 extended to 30d), DynamoDB TransactWriteItems 10 minutes, Temporal activities bounded by workflow retention [DistributedRequest](https://www.distributedrequest.com/backend-implementation-storage-patterns/idempotency-key-storage-ttl-management/).

5. **Clock-skew TTL expiry.** When application-server and storage clocks diverge (common in containerised environments), a key the application considers valid is already expired in Redis. The check returns "not found" and the operation re-executes. Mitigation: delegate TTL evaluation entirely to the storage layer via `SET NX EX` and add a skew buffer [Java Code Geeks](https://www.javacodegeeks.com/2026/06/idempotency-keys-are-harder-than-they-look-the-5-failure-modes-nobody-talks-about.html).

6. **Cross-region replication lag.** In active-active multi-region deployments, a retry routed to a different region may see no key if replication hasn't caught up. Cloudflare KV's eventual consistency can produce this; Stripe acknowledges ~3-second windows where double-processing is theoretically possible. Mitigations: sticky routing by key hash, DynamoDB Global Tables with strong-consistency reads, or accept a soft dedup window [botneve.com](https://botneve.com/automation-fundamentals/idempotency-key-design-patterns-distributed-systems/).

7. **Non-idempotent foreign APIs.** When a downstream service doesn't support idempotency keys, indeterminate failures (timeout, connection reset) cannot be safely retried because you don't know whether the side effect already happened. Stripe's rule: mark the operation as permanently failed when the foreign API lacks idempotency and the failure is indeterminate [Brandur](https://brandur.org/idempotency-keys).

## Technique 2: Atomic Phases and Recovery Points (Stripe's Internal Pattern)

**The pattern.** For multi-step workflows that include foreign-state mutations, the request is decomposed into atomic phases — `SERIALIZABLE` database transactions bounded between external calls. Each phase ends by writing a `recovery_point` label (`started` → `ride_created` → `charge_created` → `finished`). A retry reads the recovery point and resumes at the next unfinished phase. Stripe's Rocket Rides reference implementation and internal DocDB both use this [sujeet.pro](https://sujeet.pro/articles/stripe-idempotency-reliability), [Brandur](https://brandur.org/idempotency-keys).

**Key rule.** Commit local state *before* initiating any foreign-state mutation. Once you've crossed your boundary, you can't roll back; you can only record intent and retry idempotently.

**Critical interaction.** The foreign API's own idempotency key is derived deterministically from your internal key (e.g., `rocket-rides-atomic-#{internal_key.id}`). This ensures that even if your service crashes after calling Stripe, a retry sends the same derived key and Stripe replays its cached response [Brandur](https://brandur.org/idempotency-keys).

### Failure Modes

- **Schema version mismatch across deploys.** v1 stores responses in one schema, v2 in another. A retry during rollout reads a `response_body` the new parser can't decode. Fix: `schema_version` column plus a deserializer that handles every shipped version [BackendBytes](https://backendbytes.com/articles/idempotency-patterns-distributed-systems/).
- **Completer grace-period misconfiguration.** Too short and the completer races a still-live request; too long and abandoned work piles up [sujeet.pro](https://sujeet.pro/articles/stripe-idempotency-reliability).

## Technique 3: Kafka Idempotent Producer and Transactions

**The pattern.** Kafka assigns each producer a Producer ID (PID) and the producer attaches a monotonically increasing sequence number per partition. The broker deduplicates by `(PID, partition, sequence_number)` and rejects messages with a sequence number ≤ the last committed. This eliminates duplicates from producer retries within a single session. Transactions extend this to atomic writes across multiple partitions using a TransactionalId and an epoch to fence zombie producers [KIP-98](https://cwiki.apache.org/confluence/display/KAFKA/KIP-98+-+Exactly+Once+Delivery+and+Transactional+Messaging), [Confluent docs](https://docs.confluent.io/kafka/design/delivery-semantics.html).

From Kafka 3.0, `enable.idempotence` defaults to `true` with `acks=all`, `retries=Integer.MAX_VALUE`, and `max.inflight.requests.per.connection=5` [KIP-185](https://cwiki.apache.org/confluence/display/KAFKA/KIP-185).

### Failure Modes

1. **Single-session scope.** Without a `transactional.id`, idempotence is limited to one producer session. A producer restart gets a new PID and duplicates can occur across sessions [KIP-98](https://cwiki.apache.org/confluence/display/KAFKA/KIP-98).

2. **`OutOfOrderSequenceException`.** If a sequence gap is detected (indicating data loss in the producer-broker path), the producer enters a fatal error state. Continuing to send can produce out-of-order delivery. The producer must be closed and recreated [KafkaProducer javadoc](https://kafka.apache.org/42/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html).

3. **Single-replica topics.** Kafka's exactly-once guarantee requires `acks=all` and `min.insync.replicas ≥ 1`. With replication factor 1, a power failure after ack but before disk flush causes acknowledged-message loss [KIP-185](https://cwiki.apache.org/confluence/display/KAFKA/KIP-185).

4. **Transactional consumer isolation.** Consumers must use `isolation.level=read_committed` to skip messages from aborted transactions. With `read_uncommitted` (the default), aborted-transaction messages are visible and can cause phantom processing [Confluent docs](https://docs.confluent.io/kafka/design/delivery-semantics.html).

5. **PendingTransactionException on partition reassignment.** When partitions move between consumer-group members with transactional producers, the new owner may see pending transactional offsets from a previous generation. The consumer must back off and wait for the transaction timeout to expire [KIP-447](https://cwiki.apache.org/confluence/display/KAFKA/KIP-447).

## Technique 4: Transactional Outbox Pattern

**The pattern.** Instead of writing to the database and publishing to a message broker in two separate operations, the application writes the business row *and* an outbox event row in a single database transaction. A separate poller (or CDC tool like Debezium) reads the outbox and publishes to the broker with at-least-once delivery. This eliminates the dual-write problem [AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html), [Confluent](https://www.confluent.io/blog/dual-write-problem/).

### Failure Modes

1. **Duplicate publication.** If the poller crashes after publishing but before deleting/marking the outbox row, the event is published again. Consumer-side idempotency is mandatory — use a unique constraint on the event ID or a deduplication set. The outbox guarantees at-least-once delivery, not exactly-once [Confluent](https://www.confluent.io/blog/dual-write-problem/).

2. **Ordering violations.** Events for different aggregates may be published out of order relative to business-logic expectations. Kafka guarantees ordering only within a partition [Md Sanwar Hossain](https://mdsanwarhossain.me/blog-outbox-pattern-debezium.html).

3. **Outbox table growth.** During a broker outage, outbox rows accumulate indefinitely. Monitoring for backlog depth, publish lag, and retry rates is essential [DEV Community](https://dev.to/morpheus-vera/why-distributed-transactions-fail-and-how-the-outbox-pattern-helps-1id4).

4. **Replay complexity.** If consumers fail and projections become corrupted, replaying outbox events may re-trigger side effects (notifications, external API calls) that are not idempotent [DEV Community](https://dev.to/morpheus-vera/why-distributed-transactions-fail-and-how-the-outbox-pattern-helps-1id4).

## Technique 5: DynamoDB Conditional Writes / Atomic Reservation

**The pattern.** Use `ConditionExpression="attribute_not_exists(id)"` on `PutItem` to ensure a record is only inserted once. Combined with a TTL attribute, this provides time-bounded idempotency for serverless workloads (S3 → Lambda → DynamoDB pipelines). DynamoDB's `TransactWriteItems` also supports an optional `ClientRequestToken` for idempotent transactions with a 10-minute window [AWS docs](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html), [AWS Well-Architected](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_idempotent.html).

### Failure Modes

- The 10-minute `ClientRequestToken` window is fixed and non-configurable. Operations exceeding this window lose idempotency.
- `IdempotentParameterMismatch` exception on parameter change within the window requires client-side handling.

## Technique 6: Temporal/Cadence Durable Execution

**The pattern.** Workflow code is replayed deterministically from event history. Activities (side-effecting operations) are retried with at-least-once semantics. Idempotency is achieved by: (a) generating stable idempotency keys in the workflow body (not inside activities — workflow replays are deterministic, so the key stays the same across retries), (b) using `SideEffect`/`MutableSideEffect` to record non-deterministic results in event history so they are not re-generated on replay, and (c) configuring at-most-once activity execution where idempotency cannot be achieved [Temporal docs](https://docs.temporal.io/develop/go/workflows/side-effects), [Temporal blog](https://temporal.io/blog/idempotency-and-durable-execution).

### Failure Modes

- **Key generated inside activity instead of workflow.** UUID generated in the activity changes on every retry, defeating deduplication entirely [Antigravity Lab](https://antigravitylab.net/en/articles/integrations/antigravity-temporal-durable-workflow-field-notes).
- **Non-deterministic workflow code.** If workflow code is not deterministic (e.g., uses `math.random()` outside a SideEffect), replay diverges from the original execution path, causing non-determinism errors [Temporal safe-deployments docs](https://docs.temporal.io/develop/safe-deployments).
- **Compensation idempotency.** In Saga patterns, compensating activities (refund, release inventory) must themselves be idempotent. A timeout on the refund API followed by retry can produce a double refund [Antigravity Lab](https://antigravitylab.net/en/articles/integrations/antigravity-temporal-durable-workflow-field-notes).

## Cross-Cutting Themes

**Layering is necessary, not optional.** No single mechanism suffices. Production systems compose: HTTP middleware deduplication (network retries), database-layer deduplication (concurrent in-process retries), and external API idempotency keys (after-commit failures). Drop any layer and a window for duplicate side effects remains [BackendBytes](https://backendbytes.com/articles/idempotency-patterns-distributed-systems/).

**Storage failure modes mirror the problem they solve.** The idempotency store is itself a distributed system subject to replication lag, clock skew, eviction, and partition. When the idempotency store is unavailable, the system faces a business decision: fail closed (reject all mutating requests) or fail open (accept unprotected requests and reconcile later). For payments, fail closed is standard [Tech News Today](https://technewstoday.info/why-an-idempotency-key-isnt-an-idempotency-guarantee/).

**Caching only success.** Stripe v1 cached 500 errors permanently, forcing clients to mint fresh keys. v2 re-executes on 5xx. The modern rule: cache deterministic outcomes (success, 4xx client errors), do not cache transient/unknown outcomes (5xx, timeouts). A `PENDING` key returns `409 Conflict` rather than blocking, preventing client retry storms [sujeet.pro](https://sujeet.pro/articles/stripe-idempotency-reliability).

**The idempotency key is not the guarantee — the design around it is.** The key is necessary but insufficient. The guarantee requires: atomic claim (insert-first, not check-then-insert), payload fingerprinting, lease-based PENDING handling, TTL exceeding the retry window, and a mapped boundary for non-idempotent external calls [Tech News Today](https://technewstoday.info/why-an-idempotency-key-isnt-an-idempotency-guarantee/), [FlowVerify](https://www.flowverify.co/blog/idempotency-failure-modes-production).
