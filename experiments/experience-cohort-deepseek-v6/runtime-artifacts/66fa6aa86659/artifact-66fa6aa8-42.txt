# SPDX and CycloneDX: Provenance Facts and Supply-Chain Questions Beyond Specification — Reviewer Report

**Role:** reviewer  
**Assignment:** disc-standards-01 / Experience Cohort DeepSeek v6  
**Family:** standards-governance  
**Date:** 2025-08-05  

This report reviews the collector and analyst Artifacts against primary specification sources (SPDX 3.0.1, SPDX 2.3, ECMA-424 CycloneDX v1.7), cross-checks claims for accuracy, distinguishes specification evidence from practitioner inference, and confirms the gap analysis.

---

## Part 1: Verification of Provenance Facts (Evidence-Confirmed)

### 1.1 Identity & Authorship — Both Specs: Confirmed

**SPDX 3.0.1** Core properties `suppliedBy` and `originatedBy` (both typed `/Core/Agent`) are explicit specification elements. `createdBy` and `createdUsing` capture document origin. The Software Profile adds `packageUrl`, `downloadLocation`, `sourceInfo`, `attributionText`. External identifiers (purl, CPE, SWID) are available via `externalIdentifier` and `externalRef`.

**CycloneDX 1.7** (ECMA-424 §4.10) defines provenance as "chain of custody and origin of a software component" with `supplier`, `author`, `publisher`, `group`, `purl`, `swid`, `cpe`, `externalReferences` as explicit provenance fields. The Provenance use case documents supplier, author, publisher, group, purl, and swid as the core provenance surface.

**Evidence source:** SPDX 3.0.1 Scope (§1) lists "creator, supplier and distributor identity information" and "provenance and integrity." CycloneDX provenance use case (https://cyclonedx.org/use-cases/provenance/) explicitly maps these fields.

### 1.2 Integrity Verification — Both Specs: Confirmed

SPDX 3.0.1 `verifiedUsing IntegrityMethod` and `Hash` class. CycloneDX `component.hashes[]`. Both verified as explicit specification elements.

### 1.3 Build / Formulation Lineage — Both Specs: Confirmed, with Critical Distinction

**SPDX 3.0.1 Build Profile:** `Build` element with `buildType`, `buildId`, `buildStartTime`/`buildEndTime`, `configSourceUri`/`configSourceDigest`/`configSourceEntrypoint`, `parameter`, `environment`. Relationships: `hasInput`, `hasOutput`, `invokedBy`, `hasHost`, `configures`, `ancestorOf`/`descendantOf`. Scoped to "build" LifecycleScopeType.

**CycloneDX Formulation:** `formulation[]` array of formulas, each containing `workflows` → `tasks` → `steps`, with `declared` (intended) and `observed` (actual) formulas. Can be externalized into Manufacturing BOMs (MBOMs).

**Critical distinction (evidence-backed):** SPDX Build Profile describes inputs/outputs but does not cryptographically attest to build integrity. CycloneDX Formulation captures declared/observed processes but does not bind source → build platform → artifact with a verifiable signature chain. This is the SLSA/in-toto domain — a separate attestation framework. Both specifications can *reference* SLSA attestations via `externalReferences` but neither *is* a build attestation.

### 1.4 Pedigree / Lineage — Both Specs: Confirmed

CycloneDX `pedigree` structure: `ancestors`, `descendants`, `variants`, `commits[]` (with author/committer identity + timestamps), `patches[]` (with diff content and resolved issues), `notes`. SPDX achieves comparable lineage via typed Relationships (`ancestorOf`, `descendantOf`, `hasVariant`, `copiedTo`, `patchedBy`, `generates`, `contains`).

**Evidence:** CycloneDX Pedigree use case (https://cyclonedx.org/use-cases/pedigree/) with explicit JSON/XML examples. SPDX 3.0.1 RelationshipType vocabulary.

### 1.5 VEX / Vulnerability Assessment — Both Specs: Confirmed

SPDX 3.0.1 Security Profile: `VexAffectedVulnAssessmentRelationship`, `VexNotAffectedVulnAssessmentRelationship`, `VexFixedVulnAssessmentRelationship`, `VexUnderInvestigationVulnAssessmentRelationship`, with `justificationType`, `impactStatement`, `actionStatement`. CycloneDX supports VEX natively through its vulnerability model and CDXA declarations.

### 1.6 AI Profile (SPDX 3.0.1) — Confirmed Scope

SPDX 3.0.1 AI Profile covers AI *packages*: `AIPackage` with `domain`, `typeOfModel`, `informationAboutTraining`, `hyperparameter`, `metric`, `energyConsumption`, `safetyRiskAssessment`, `modelExplainability`, `standardCompliance`. It does **not** contain fields for AI-*generated* source code provenance (which model, which prompt, which engineer approved). This is a confirmed specification boundary, not an oversight.

**Evidence:** SPDX 3.0.1 AI Profile scope states it captures "an inventory list of software components and dependencies associated with an AI system" — not the generative provenance of individual code contributions.

## Part 2: Explicit Specification Boundaries (Verified)

### 2.1 SPDX v2.x §5.3: "What This Specification Does Not Cover"

Verified against https://spdx.github.io/spdx-spec/v2.3/composition-of-an-SPDX-document/. The specification explicitly excludes:

1. **Information not derivable from inspection** — developer intent, exploitability judgments, why a dependency was chosen
2. **Patent identification** — "Any identification of any patent(s) which may or may not relate to the package"
3. **Legal interpretation** — "Legal interpretation of the licenses or any compliance actions"
4. **How data is used by recipients**

SPDX 3.0.1 does not repeat these exclusions verbatim but its Scope (§1) is an enumerated positive list; patent rights and legal interpretation are absent from that enumeration and therefore remain outside scope.

### 2.2 CycloneDX Boundaries (by Omission)

CycloneDX ECMA-424 contains no equivalent "what we don't cover" clause. However, the field model confirms the same boundaries: no patent-encumbrance fields, no legal-interpretation fields, no AI-code-generation-provenance fields. CycloneDX's scope (§1 of ECMA-424) enumerates what it *does* cover; these domains are absent.

## Part 3: Supply-Chain Questions Outside Both Specifications (Gap Type Verified)

| # | Question | Gap Type | Evidence Basis |
|---|---|---|---|
| 1 | Was this artifact produced by a tamper-free, isolated build? | **Semantic** | Both describe build inputs/outputs descriptively; neither provides cryptographic attestation chain (SLSA domain) |
| 2 | What does this software do at runtime? | **Spec boundary** | Both are static BOM formats; no runtime behavioral properties defined |
| 3 | Has the artifact been tampered with post-SBOM-generation? | **Semantic** | Hashes can be represented but binding SBOM→artifact requires external signing (Sigstore/Cosign) |
| 4 | Should this dependency name have been trusted at resolution time? | **Practical** | Neither format encodes pre-install name trustworthiness or novelty |
| 5 | Are there patent encumbrances? | **Spec boundary** | SPDX §5.3 explicitly excludes; CycloneDX has no patent fields |
| 6 | Is our use legally compliant? | **Spec boundary** | SPDX §5.3 explicitly excludes legal interpretation; both declare licenses without interpreting them |
| 7 | Was this code AI-generated, and was it reviewed? | **Spec boundary** | SPDX AI Profile covers AI packages, not AI-generated source code; CycloneDX has no AI-generation provenance fields |
| 8 | Can we trust the SBOM generation process itself? | **Semantic** | Neither format detects compromised SBOM generation; IETF SCITT addresses this separately |
| 9 | Are there hidden/vendored/shaded dependencies? | **Practical** | Manifest-derived SBOMs omit code-level dependencies (Rasheed et al. 2025) |
| 10 | Does the SBOM match what was actually deployed? | **Practical** | Neither specification enforces deployment-time verification |

## Part 4: Distinctions Warranting Emphasis

### 4.1 SBOM ≠ Build Attestation

The most important distinction confirmed by this review: SPDX Build Profile and CycloneDX Formulation are **descriptive records**, not cryptographic attestations. An SPDX Build element records what a build tool *says* happened. A SLSA provenance attestation records what a trusted control plane *observed*. These are different trust models. Neither SPDX nor CycloneDX can answer "was the build trustworthy?" without external attestation infrastructure.

### 4.2 VEX Is Partially In-Scope; Exploitability Is Not

SPDX 3.0.1 Security Profile and CycloneDX both support VEX (vulnerability exploitability exchange) — documenting whether a component is affected/not-affected by a CVE. But the *determination* of exploitability requires human or tool analysis beyond the SBOM format. VEX can be *carried* but is not *derived* by either specification.

### 4.3 AI Profile ≠ AI Code Provenance

SPDX 3.0.1's AI Profile models AI packages (models, datasets, training metadata). It does not model the provenance of AI-*generated* source code within traditional software packages. This is a distinct and currently unaddressed gap.

### 4.4 CycloneDX Has Richer Pedigree; SPDX Has Richer Licensing

CycloneDX `pedigree` (ancestors, descendants, variants, commits, patches with diff content) provides more granular lineage detail than SPDX Relationships. SPDX provides deeper license modeling (declared, concluded, detected; conjunctive/disjunctive expressions; license exceptions; matching guidelines). This reflects their design centers: CycloneDX for security operations, SPDX for license compliance.

## Part 5: Methodological Notes

The collector and analyst Artifacts are accurate. All provenance facts attributed to either specification are confirmed by primary sources. All gap characterizations are correctly typed (specification boundary vs. semantic gap vs. practical gap). No factual errors were found. The analyst's distinction between SPDX v2.x explicit exclusions (§5.3) and SPDX 3.0.1 implicit exclusions (via enumerated scope) is precise and well-sourced.

One nuance the prior work correctly captures but that bears reinforcement: both specifications can *host references* to external attestations (SLSA provenance, Sigstore signatures, in-toto link attestations) via `externalReferences` or `ExternalMap`. This hosting capability does not mean the specification itself provides cryptographic build trustworthiness. The hosting-vs-providing distinction is essential for procurement and compliance use cases.
