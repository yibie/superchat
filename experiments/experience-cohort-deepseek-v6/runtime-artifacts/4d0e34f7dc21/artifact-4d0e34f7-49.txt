# Conditions Required for Deterministic Replay in Event-Sourced Systems When Schemas Evolve

## Primary Research & Official Specifications

Deterministic replay — the guarantee that replaying the same event sequence always reconstructs byte-identical state — is the foundational property enabling audit, time-travel debugging, projection rebuilds, and crash recovery in event-sourced systems. When schemas evolve, this guarantee faces additional requirements beyond the baseline replay conditions. This analysis synthesizes primary sources including the Akka Data Integrity Specification, Apache Pekko documentation, Gregory Young's _Versioning in an Event Sourced System_, the empirical study of Overeem et al. (2021) covering 19 systems and 25 engineers, and multiple framework-level specifications (Axon, Protean, Hexalith, Marten).

---

## Part I: Baseline Conditions for Deterministic Replay (Schema-Static)

Before addressing schema evolution, deterministic replay requires these foundational conditions:

### 1. Pure Event Handlers (No Side Effects, No External Calls)

The Akka specification defines `DATA-ES-EVENT-HANDLER-PURE`: "Event handlers perform no side effects and no external calls, so replay produces state without emitting new commands or messages" [Akka Data Integrity Catalog](https://doc.akka.io/reference/specify/catalog/data-integrity.html). Any I/O (database reads, HTTP calls, message publishing) inside the state-transition function makes replay non-deterministic because external state may differ between replays.

The noddde framework rationale is explicit: "If evolve handlers could access infrastructure (databases, APIs, time), event replay becomes non-deterministic… Replaying this event tomorrow would produce a different state because the exchange rate changed" [Why Are Evolve Handlers Pure?](https://noddde.dev/docs/design-decisions/why-pure-apply-handlers). The fix: capture all external data in the event payload at decision time, not at replay time.

### 2. No Dependence on Wall-Clock Time or Randomness

`DATA-ES-REPLAY-DETERMINISTIC`: "Replaying the same event sequence twice yields byte-identical entity state with no dependence on wall-clock time or randomness" [Akka Data Integrity Catalog](https://doc.akka.io/reference/specify/catalog/data-integrity.html). Time must be captured in the event payload or passed as an explicit parameter. `new Date()` or `Math.random()` inside a reducer breaks determinism.

### 3. Event Immutability After Persist

`DATA-ES-EVENT-IMMUTABLE-AFTER-PERSIST`: "Persisted events are never mutated or deleted in place; corrections are expressed as new compensating events" [Akka Data Integrity Catalog](https://doc.akka.io/reference/specify/catalog/data-integrity.html). Overeem et al. (2021) found three degrees of immutability in practice: **strict** (8/19 systems), **cut-off moments** with backups (3/19), and **mutable** (8/19), noting that mutable stores sacrifice audit trail completeness [Overeem et al., JSS 2021](https://doi.org/10.1016/j.jss.2021.110970).

### 4. Event Order Preservation

`DATA-ES-EVENT-ORDER-PRESERVED`: "Events are replayed in their original persisted sequence order" [Akka Data Integrity Catalog](https://doc.akka.io/reference/specify/catalog/data-integrity.html). The event log is append-only and sequence numbers are contiguous (`DATA-ES-SEQUENCE-NUMBER-CONTIGUOUS`).

### 5. Total Event Handler Coverage

`DATA-ES-EVENT-HANDLER-TOTAL`: "Every event type the entity can emit has a corresponding event handler, so no persisted event fails to apply on replay" [Akka Data Integrity Catalog](https://doc.akka.io/reference/specify/catalog/data-integrity.html). Hexalith enforces this as an error-first contract: an `UnknownEventException` is thrown rather than silently skipping, because "skipping unknown events produces incorrect aggregate state" [Hexalith Event Versioning](https://github.com/Hexalith/Hexalith.EventStore/blob/main/docs/concepts/event-versioning.md).

### 6. Separation of Decide and Evolve (Decider Pattern)

The functional event-sourcing Decider pattern (Jérémie Chassaing) separates `decide(command, state) → events` from `evolve(state, event) → new state`. The `evolve` function must be pure; the `decide` function may access infrastructure but must be deterministic given its explicit inputs. As Kevin Webber notes, "during replay, the host rebuilds state through `apply` and suppresses action execution" — the Mealy-machine output (side-effect declarations) must be separated from the Moore-machine state transition [Mealy Machines and Event Sourcing](https://kevinwebber.ca/blog/mealy-machines-and-event-sourcing/).

## Part II: Additional Conditions When Schemas Evolve

Schema evolution introduces new requirements because "events are immutable and usually never deleted — the way schema evolution is handled differs from how one would go about it in a mutable database setting" [Akka Schema Evolution](https://doc.akka.io/libraries/akka-core/current/persistence-schema-evolution.html).

### 7. Old Events Must Remain Deserializable (Backward Compatibility)

`DATA-SCHEMA-OLD-EVENTS-DESERIALIZE`: "Events serialized under a prior schema version still deserialize successfully after the current schema change" [Akka Data Integrity Catalog](https://doc.akka.io/reference/specify/catalog/data-integrity.html). This is **mandatory**. Gregory Young states: "A new version of an event must be convertible from the old version of the event. If not, it is not a new version of the event but rather a new event" [Versioning in an Event Sourced System](https://leanpub.com/esversioning/read).

The practical rules from Protean documentation are:
- **New fields must have defaults.** "Never mark new fields as required=True on an existing event type" — always provide a default that preserves pre-change behavior [Protean Event Versioning](https://docs.proteanhq.com/patterns/event-versioning-and-evolution/).
- **Old fields are never removed.** They may be deprecated but must remain deserializable.
- **Field semantics never change.** A field's meaning is permanent; if the meaning changes, create a new field or event type.
- **Breaking changes create new event types.** Renaming types, restructuring payloads, or changing field types requires versioning [Protean Evolving Events](https://docs.proteanhq.com/guides/evolving-events/).

### 8. Upcaster Coverage: Every Historical Version Must Have a Path to Current

`DATA-SCHEMA-UPCASTER-COVERAGE`: "Every historical event schema version has an upcasting path to the current version, with no version left unmapped" [Akka Data Integrity Catalog](https://doc.akka.io/reference/specify/catalog/data-integrity.html).

Upcasting transforms old event payloads to the latest version at read time, before handlers see them. This keeps handlers simple — they always receive the current schema. The Axon framework formalizes this: "Upcasters are classes that take one input event of revision `x` and output zero or more new events of revision `x + 1`… processed in a chain" [Axon Event Versioning](http://docs.axoniq.io/axon-framework-reference/4.11/events/event-versioning/). Protean validates upcaster chains at init-time: gaps, cycles, or duplicate edges raise `ConfigurationError` [Protean Evolving Events](https://docs.proteanhq.com/guides/evolving-events/).

Greg Young warns against the "Double Publish" approach (writing both old and new versions): it works in stable distributed systems but "will fail when you need to replay a projection" because "a matching version 3 of the event will not be received if we ignore the version 2" [Leanpub: Basic Type Based Versioning](https://leanpub.com/read/esversioning/leanpub-auto-basic-type-based-versioning).

### 9. Version Tagging

`DATA-SCHEMA-VERSION-TAGGED`: "Every serialized event carries a schema or type version marker enabling the correct upcaster to be selected on read" [Akka Data Integrity Catalog](https://doc.akka.io/reference/specify/catalog/data-integrity.html). Without version markers, the system cannot distinguish v1 from v2 payloads at deserialization time.

Akka recommends `SerializerWithStringManifest`, where the manifest is a string identifier of the event type and version used to route deserialization [Akka Schema Evolution](https://doc.akka.io/libraries/akka-core/current/persistence-schema-evolution.html).

### 10. No Breaking Type Changes Without Upcasters

`DATA-SCHEMA-NO-BREAKING-TYPE-CHANGE`: "A field's serialized type is not changed incompatibly (such as string to integer) without an upcaster bridging the old form" [Akka Data Integrity Catalog](https://doc.akka.io/reference/specify/catalog/data-integrity.html).

Protean's compatibility matrix formalizes this: renaming a field **and** changing its type is a breaking change requiring an upcaster even when `renamed_from` is declared [Protean Event Versioning](https://docs.proteanhq.com/patterns/event-versioning-and-evolution/).

### 11. Serialization Format Compatibility

Schema evolution properties depend on the serialization format:
- **IDL-based** (Protobuf, Thrift, Avro): field renames are "free" because field names are not stored; renaming requires no code changes beyond the field definition. Protobuf fields are identified by number, not name [Akka Schema Evolution](https://doc.akka.io/libraries/akka-core/current/persistence-schema-evolution.html).
- **Weak schema** (JSON/XML with tolerant mapping): readers map by field name, ignore unknown fields, and supply defaults for missing fields. Gregory Young advocates this: "you are no longer allowed to rename something… and there will often be programmatic checks to ensure what you expect to be in the message after the mapping is in fact present" [Versioning in an Event Sourced System](https://leanpub.com/esversioning/read).
- **Strong/type-based schema**: Young warns this "leads to the inevitable conclusion that all consumers must be updated to understand the schema before a producer is" [Leanpub](https://leanpub.com/read/esversioning/leanpub-auto-basic-type-based-versioning).

### 12. Snapshot Compatibility with Schema Evolution

`DATA-SCHEMA-OLD-EVENTS-DESERIALIZE` applies to snapshots too: "A snapshot written under a prior state schema version still restores correctly after the schema has evolved." The snapshot + subsequent replay must produce the same state as full replay (`DATA-SNAPSHOT-MATCHES-REPLAY`) [Akka Data Integrity Catalog](https://doc.akka.io/reference/specify/catalog/data-integrity.html).

### 13. Idempotent Projections

`DATA-VIEW-IDEMPOTENT-UPDATE`: "Reprocessing the same source event into a view produces the same view row without double-counting" [Akka Data Integrity Catalog](https://doc.akka.io/reference/specify/catalog/data-integrity.html). When schemas evolve, projections replaying from the beginning may reprocess already-seen events — idempotency by tracked offset or event ID is required.

## Part III: Five Empirically Established Schema Evolution Techniques

Overeem et al. (2021) identify five tactics from 19 production systems [Overeem et al., JSS 2021, §7](https://ar5iv.labs.arxiv.org/html/2104.01146):

| Technique | Systems Using | Key Property |
|---|---|---|
| **Versioned Events** | 2 | Simplicity; application logic pollution risk |
| **Weak Schema** | (newly identified) | No new versions needed; renames forbidden |
| **Upcasting** | 12 | No logic pollution; strict immutability preserved |
| **In-Place Transformation** | 5 | Ad-hoc; breaks immutability |
| **Copy-and-Transform** | 14 | Creates new stream; most flexible |

The authors advise: "systems should start out using versioned events and weak schema, while later evolving to upcasting and even copy-and-transform techniques."

## Part IV: Summary of Conditions

| # | Condition | Source |
|---|---|---|
| C1 | Event handlers are pure (no I/O, no side effects) | Akka DATA-ES-EVENT-HANDLER-PURE |
| C2 | No wall-clock time or randomness in state transition | Akka DATA-ES-REPLAY-DETERMINISTIC |
| C3 | Events immutable after persist | Akka DATA-ES-EVENT-IMMUTABLE-AFTER-PERSIST |
| C4 | Events replayed in original sequence order | Akka DATA-ES-EVENT-ORDER-PRESERVED |
| C5 | Every event type has a handler (total coverage) | Akka DATA-ES-EVENT-HANDLER-TOTAL |
| C6 | Decide and evolve functions separated | Decider Pattern (Chassaing) |
| C7 | Old events remain deserializable (backward compatible) | Akka DATA-SCHEMA-OLD-EVENTS-DESERIALIZE |
| C8 | Every historical version has an upcasting path | Akka DATA-SCHEMA-UPCASTER-COVERAGE |
| C9 | Every serialized event carries version marker | Akka DATA-SCHEMA-VERSION-TAGGED |
| C10 | No incompatible type changes without upcasters | Akka DATA-SCHEMA-NO-BREAKING-TYPE-CHANGE |
| C11 | Serialization format supports required evolution style | Akka / Young / Protean |
| C12 | Snapshots remain compatible with evolved schemas | Akka DATA-SNAPSHOT-MATCHES-REPLAY |
| C13 | Projections are idempotent (offset-tracked) | Akka DATA-VIEW-IDEMPOTENT-UPDATE |
