## 2. Source Verification Against Primary Evidence

### 2.1 Chen et al. (2026), arXiv:2604.03070 — Verified

Direct reading confirms the paper (accepted at ASE 2026) sampled 17,022 skills from 170,226 on SkillsMP, using stratified random sampling with four-phase methodology. The key statistics are substantiated: 73.5% of leakage attributable to debug logging (1,007/1,371), 89.6% exploitability, and fork persistence defeating remediation (107 upstream repos, 50+ forks). The 76.3% cross-modal (NL+PL) requirement is corroborated. **No misrepresentation found.**

**Qualification:** The study is bounded to the SkillsMP marketplace (Claude Code skills). Generalizability to LangChain, CrewAI, or AutoGen ecosystems is an open question, as the analyst correctly notes.

### 2.2 AWS Security Blog (2026-07-08) — Verified

Direct reading confirms: (a) the foundational design principle "assume system prompts will be leaked," (b) canary-token detection with Unicode normalization (Lambda-deployable code provided), (c) semantic similarity detection via cosine similarity against embeddings, (d) sandwich defense pattern, and (e) the explicit statement that system prompt leakage "doesn't currently have a remediation that fully eliminates the issue." The blog cites OWASP LLM07 and provides deployable code. **No misrepresentation.**

### 2.3 Tianpan.co (2026-06-03) — Verified

The core narrative — three independent, defensible decisions composing into undetected disclosure — is a first-party technical postmortem, not peer-reviewed research. The blog provides architectural detail that maps to documented OWASP patterns. The claim that "prompt extraction succeeds ~60% of the time across enterprise AI assessments" appears without a citation and should be treated as author experience, not systematically measured data. The analyst correctly notes that higher figures (84–92%) from Das & Amini (2025) measure different contexts. **Narrative is credible; statistical claims are unsourced and should be flagged accordingly.**

### 2.4 Tianpan.co (2026-07-02) — Verified

The "five persistence layers" model and the tool-boundary-as-chokepoint argument are substantiated. The GitGuardian "28.65 million new secrets" statistic is a secondary citation; the original report was not independently verified. The public disclosure about malicious PR titles causing three vendors' coding agents to post environment variables is a secondary reference within the article and not independently corroborated. The Chen et al. finding of 83 malicious skills with deliberate exfiltration logic provides partial corroboration. **Core architectural argument is sound; secondary statistics should carry lower weight.**

### 2.5 OWASP LLM07:2025 — Verified

Direct reading confirms: "the system prompt should not be considered a secret, nor should it be used as a security control." The framing is that the risk is not prompt disclosure per se but what the prompt contains (credentials, permission structures, etc.). The analyst correctly notes a gap: OWASP LLM07 does not explicitly address the case where the prompt text itself (competitive architecture, refusal policy, retrieval pipeline) is proprietary IP, not merely a container for other secrets. The AWS Security Blog partially fills this gap by referring to system prompts as "proprietary information" and "intellectual property." **OWASP guidance is correct but incomplete on this dimension.**

### 2.6 OWASP LLMSVS v2.0 — Verified

§5.10 requires (L1–L3): "Ensure that client-facing responses from LLM interactions do not expose raw provider errors, stack traces, or other detailed diagnostics that could leak prompts, credentials, or internal implementation details. Present generic or sanitized messages to end users while retaining structured server-side logging for operations and security monitoring, without writing secrets or full sensitive prompts to untrusted or broadly accessible logs." **Verified verbatim. The collector's paraphrase is accurate.** §5.7 (canary tokens, L3) and §8.2 (logging and alerting for prompt leak events, L2–L3) are also confirmed.

## 3. Analytical Evaluation

### 3.1 Points of Agreement

Both artifacts converge on a well-supported consensus:

- **Three structurally distinct failure classes:** configuration composition (prompts in audit feeds), credential fan-out through context windows, and the EU AI Act Art. 12 / GDPR Art. 17 trilemma.
- **The tool boundary is the critical chokepoint** for credential leakage. Once content enters the context window, it fans out to multiple persistence layers, some outside operator control.
- **Field-level sensitivity classification at origin with default-deny** is the architectural defense against composition failures.
- **Pseudonymization at log capture** resolves the regulatory collision between mandatory logging and mandatory erasure.
- **"Assume system prompts will leak"** is the consensus design principle from OWASP, AWS, and AgentPatterns.

### 3.2 Residual Tensions

**Tension 1: Content-free vs. tiered retention.** The Data443 position (metadata-only, content: false) and the NemoRouter position (tiered: zero → metadata → PII-redacted → full) represent a genuine operational trade-off. The metadata-only approach is compliance-optimal but forecloses prompt-content debugging. Tiered retention enables debugging under the "PII-redacted" tier but assumes the redactor catches everything — an assumption the Tianpan analysis explicitly challenges for system prompts (structural prior of "product copy" bypasses regex/ML redactors). **Recommendation:** default to content: false with a documented, time-bounded, justification-required exception process for debugging. Do not rely on "PII-redacted" as a safe tier for prompt content.

**Tension 2: Hash-chain evidence vs. auditor expectations.** The claim that auditors accept SHA-256 hash chains as evidence of decision integrity is plausible but unverified from auditor-side sources. If an auditor demands the actual prompt content that produced a specific decision, the hash chain alone is insufficient. **Recommendation:** operators should validate auditor expectations during control design, not during an audit.

**Tension 3: Token-based vs. cryptographic-erasure pseudonymization.** Both satisfy Art. 12/Art. 17 collision. Token-based is operationally simpler but adds a mapping store to the attack surface. Cryptographic erasure eliminates the mapping store but requires per-record encryption infrastructure. **Recommendation:** token-based for most deployments; cryptographic erasure for high-assurance environments or where the mapping store itself would be a high-value target.

### 3.3 Gap: Fork Persistence Taxonomy

Neither artifact fully develops the fork-persistence finding from Chen et al. This is a distinct failure mode: upstream remediation provides no security guarantee in fork-based distribution models. The mitigation (short-lived credentials) is mentioned but not linked back to this specific problem. This is a supply-chain governance issue distinct from technical logging controls.

## 4. Final Mitigation Framework (Layered Defense)

The evidence supports a four-layer model, organized by where the control operates:

| Layer | When | Controls | Primary Threats Addressed |
|-------|------|----------|--------------------------|
| **L0 — Design-time** | Before code | Never store secrets in prompts (OWASP LLM07); externalize auth to deterministic systems; prompt-as-versioned-artifact with review discipline | All prompt-content leakage; confused deputy |
| **L1 — Write-time** | Tool boundary | Egress redaction (regex + entropy scanning); placeholder dereferencing; transport-layer injection (SPIFFE); field-level sensitivity tags at definition | Credential fan-out to traces, caches, memory, evals |
| **L2 — Capture-time** | Log boundary | Pseudonymization; metadata-only + hash-chain logging (content: false default); client-side redaction before trace ingestion; tiered retention by purpose | Compliance trilemma (Art. 12/17); audit-surface exposure |
| **L3 — Output-time** | Response boundary | Canary tokens + semantic similarity detection; structured schema validation; red-team audit surfaces (not just model interface) | Prompt leakage through model responses; bypass detection |

**Cross-cutting:** Short-lived credentials (lifetime < session lifetime) make any leaked credential inert upon discovery. This does not prevent leaks but caps blast radius and is independently recommended by all major sources.

## 5. Regulatory Alignment

| Framework | Key Requirement | Primary Mitigation |
|-----------|----------------|-------------------|
| SOC 2 (CC6/CC7) | Logical access monitoring, system operations | Metadata-only hash-chained audit log; field-level sensitivity tags |
| HIPAA §164.312(b) | Audit controls for ePHI systems | Pseudonymization at log capture; content: false; BAA with observability vendor |
| GDPR Art. 5(1)(c), 17, 25 | Data minimization, erasure, privacy by design | Metadata-only logging; per-subject encryption with cryptographic erasure |
| PCI DSS Req. 3, 10 | Protect stored PAN; audit log content | Content: false — PAN never enters log store |
| EU AI Act Art. 12 | Automatic logging for high-risk AI | Pseudonymized hash-chain logs; 6-month minimum retention |
| ISO 42001 / NIST 800-53 AU-3, AU-10 | Audit record content and integrity | SHA-256 hash chain with tamper detection |
| OWASP LLMSVS §5.10 | No secrets or full sensitive prompts in broadly accessible logs | Content: false; structured server-side logging only |
