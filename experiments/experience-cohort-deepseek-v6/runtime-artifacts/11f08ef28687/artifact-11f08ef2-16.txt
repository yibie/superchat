# Content-Addressed Storage: Guarantees and Limitations for Long-Lived Artifact Provenance

**Role:** collector  
**Family:** software-systems  
**Sources:** primary specifications (SLSA v1.0–v1.1, in-toto attestation v1, SWHID ISO/IEC 18670:2025, C2PA 1.3), production systems (Git, IPFS, GitLab Artifact Registry, Software Heritage), and research literature (USENIX FAST, VLDB, Springer Quantum Information Processing).

---

## 1. Core Guarantees

### 1.1 Integrity Verification (Tamper-Evidence)

Content-addressed storage (CAS) derives the storage address from a cryptographic hash of the content itself. Because `address = H(content)`, every read can self-verify: hash the bytes received and compare against the requested address. A mismatch detects corruption or tampering regardless of the untrustedness of the transport, server, or medium.

**Source:** T34ch Tech, "Content-Addressed Storage from First Principles." https://t34ch.tech/articles/content-addressed-storage/

This guarantee underpins multiple production provenance frameworks:

- **in-toto attestation v1**: The `subject` field binds an attestation to artifacts using a `DigestSet` — a map of algorithm names (e.g., `sha256`) to hex-encoded hash values. Subjects "are assumed to be immutable, i.e. the artifacts identified by the subject SHOULD NOT change." Two DigestSets match when every algorithm in the consumer's set is present with identical value in the producer's set. **Source:** https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md

- **SLSA provenance v1.1**: Artifacts in `subject`, `resolvedDependencies`, and `byproducts` are identified by `ResourceDescriptor` objects containing `digest` fields, with `sha256` as the canonical algorithm. Verification step 2 requires that "statement's `subject` matches the digest of the artifact in question." **Source:** https://slsa.dev/spec/v1.1/provenance

- **C2PA 1.3**: Hard bindings are cryptographic content hashes that "enable the validator to ensure that (a) this manifest belongs with this asset and (b) that the asset has not been modified." Externally hosted assertion data uses `hashed_uri` references where "the data's integrity is protected by the `hash` field." **Source:** https://spec.c2pa.org/specifications/specifications/1.3/specs/C2PA_Specification.html

### 1.2 Immutability by Construction

Because any content change produces a different hash, "modification" of CAS data is impossible — only creation of new data with a new address occurs. GitLab's Artifact Registry explicitly states: "Content-addressable storage keeps artifacts immutable. Once we store content at a hash-based location, any modification produces a different hash and thus a different storage location, preventing tampering." **Source:** https://gitlab.com/gitlab-org/ops/artifact-registry/-/blob/main/docs/adr/008_content_addressable_storage.md

This property is structural, not policy-based. There is no write-permission concept for CAS blobs because there is no "overwrite" operation.

### 1.3 Structural Deduplication

Because identical content produces identical addresses, deduplication is a consequence of the addressing scheme rather than a separate subsystem. GitLab's Artifact Registry notes: "If the destination path already exists, the blob is a duplicate and no new object is written. No database coordination is needed for the deduplication check itself." This enables cross-repository blob mounting (OCI `mount` operation) and shared storage of identical artifacts across projects within a namespace.

**Source:** https://gitlab.com/gitlab-org/ops/artifact-registry/-/blob/main/docs/adr/008_content_addressable_storage.md

### 1.4 Trustless Distribution

Because any consumer can independently verify content against its address, CAS enables content distribution from untrusted intermediaries. The trust is transferred from infrastructure operators to the hash function. This is foundational to CDN-based distribution (immutable blobs achieve very high cache hit rates), peer-to-peer networks (IPFS), and air-gapped verification scenarios.

### 1.5 Decentralized Identifier Computation (Intrinsic Identifiers)

The SWHID standard (ISO/IEC 18670:2025) demonstrates that CAS-based identifiers are *intrinsic*: "they can be computed using cryptographically strong functions directly from the digital objects they refer to, by anyone that has access to a copy of those objects. This enables decentralised and independent verification of integrity, without relying on a registry or a central authority." The SWHID core identifier is a SHA-1 hash over a canonical serialization (Merkle DAG), and the scheme includes a version prefix (`swh:1:`) enabling hash algorithm migration. **Source:** https://www.iso.org/standard/89985.html; https://docs.softwareheritage.org/devel/swh-model/persistent-identifiers.html

### 1.6 Merkle-DAG Composition

CAS identifiers compose into Merkle trees/DAGs where a root hash commits to an entire tree of artifacts. This is how Git commits reference entire repository states, how IPFS CIDs address directory hierarchies, and how SLSA provenance chains can be recursively verified. The in-toto specification treats linked attestations as forming "a hypergraph where the nodes are artifacts and the hyperedges are attestations," enabling predicate-agnostic graph processing. **Source:** https://slsa.dev/spec/v1.1/attestation-model

## 2. Limitations

### 2.1 Authenticity Is Not Provided

A content address verifies *what* the data is, not *who* created it. CAS alone cannot distinguish between an artifact authored by a trusted party and one authored by an adversary — both produce valid hashes. Authenticity requires a separate digital signature layer. T34ch Tech notes: "CAS and digital signatures are complementary. CAS gives you 'this is the data.' Signatures give you 'this person created the data.'" https://t34ch.tech/articles/content-addressed-storage/

The SLSA framework bridges this gap by requiring DSSE envelopes with signatures over in-toto Statements. The `builder.id` and public key infrastructure establish *who* produced a provenance attestation, while the `subject` digest binds the attestation to artifact content.

### 2.2 Availability Is Not Guaranteed

CAS prevents undetected modification but does not prevent deletion. A storage node can delete any block. When a CAS address is requested, the absence of data is detectable, but detection does not restore availability. Redundancy, replication, and pinning policies (as in IPFS) are necessary infrastructure complements.

This limitation is documented in practice: GitLab's Artifact Registry notes that "database-storage divergence" can occur — "a crash between the storage write and database commit leaves an orphaned object in `objects/` that no database record references." The system "maintains two sources of truth: blob records in the database and objects in storage. These can diverge." **Source:** https://gitlab.com/gitlab-org/ops/artifact-registry/-/blob/main/docs/adr/008_content_addressable_storage.md

### 2.3 Garbage Collection Is a Correctness-Critical Challenge

CAS is append-only; unreferenced blocks accumulate indefinitely. Garbage collection (GC) is necessary but dangerous. The T34ch article describes two approaches:

- **Reference counting**: Simple and incremental, but fails on cycles (though CAS DAGs are naturally acyclic).
- **Mark-and-sweep**: Handles cycles but requires full DAG traversal — potentially hours for terabyte-scale stores.

**The GC race** is the critical distributed-systems problem: if Node A builds a new tree referencing a block on Node B while Node B concurrently runs GC, Node B may delete blocks Node A's new tree needs. Solutions include GC grace periods, two-phase GC (mark/wait/sweep), and explicit pinning (IPFS). **Source:** https://t34ch.tech/articles/content-addressed-storage/

HCI's HYDRAstor research (USENIX FAST '13) formalizes this: "block resurrection through duplicate elimination must be traced by the deletion algorithm" and epochs with "undelete markers" are required to safely allow concurrent writes during deletion. **Source:** https://www.usenix.org/system/files/conference/fast13/fast13-final91.pdf

GitLab's Artifact Registry similarly notes: "Bugs in reference tracking can cause premature garbage collection (data loss) or blobs that are never collected (storage leaks). This is a correctness-critical component." https://gitlab.com/gitlab-org/ops/artifact-registry/-/blob/main/docs/adr/008_content_addressable_storage.md

### 2.4 Confidentiality and Confirmation Attacks

Because `address = H(content)`, anyone who knows the content can compute the address and confirm its presence in a store. This is a *confirmation attack*: an observer who knows a content address can check whether specific data exists. Encryption before hashing mitigates this, but at the cost of deduplication (different keys produce different ciphertexts).

### 2.5 Hash Function Brittleness and Migration Cost

The entire CAS trust model collapses if the hash function is broken. SHA-1 was demonstrated vulnerable (SHAttered, 2017). Git's multi-year migration from SHA-1 to SHA-256 illustrates the operational cost. SWHID addresses this through an explicit version field (`swh:1:` → `swh:2:`) enabling algorithm migration while maintaining backward compatibility.

**Quantum threats**: While SHA-256 remains practically secure (Grover's algorithm provides only a √N speedup, giving 2^128 quantum security for collision resistance), research demonstrates quantum collision attacks on reduced-round SHA-256 (39 of 64 rounds). Hosoyamada and Sasaki (2021) showed quantum attacks reaching 38–39 steps for SHA-256/SHA-512, and a 2025 Springer paper demonstrated a quantum technique converting semi-free-start collisions to full two-block collisions on 39-round SHA-256 with time complexity 2^124/√S. **Source:** https://link.springer.com/article/10.1007/s11128-025-05024-w

The National Academies note that "SHA256... is not expected to be threatened by quantum computing" for preimage resistance, but the long-term (30+ year) horizon for artifact preservation suggests hash algorithm agility — as built into SWHID, Iroh's self-describing CIDs, and the in-toto DigestSet supporting multiple simultaneous algorithms — is essential. **Source:** https://www.nationalacademies.org/read/25196/chapter/6

### 2.6 No In-Place Mutation or Human-Readable Names

CAS forbids in-place updates. Every change produces a new address. Human-meaningful naming requires a mutable pointer layer (Git refs, IPNS, DNSLink, package registry indices), which itself becomes a source of complexity for consistency, conflict resolution, and access control. Every CAS system must solve the naming problem separately.

### 2.7 Archive-Aware Hashing: The Web Archiving Problem

Research by Aturban et al. (2023, PLOS ONE) demonstrates that conventional cryptographic hashing fails for archived web content: 88.45% of mementos from 17 public web archives produced multiple unique hash values across 39 downloads over 442 days. Causes include: evolving replay-time JavaScript injection, timestamp embedding in HTML comments, content-encoding differences across archiving tools, and URL rewriting. This points to a need for "archive-aware hashing functions" where conventional CAS hashing is insufficient. **Source:** https://pdfs.semanticscholar.org/3072/4e78dffa8f187b0b756f755282ea06850543.pdf

### 2.8 The Canonicalization Dependency

CAS integrity depends on a canonical byte representation. If the same logical content can have multiple valid serializations (e.g., JSON key ordering, XML whitespace, CBOR vs JSON), identical logical artifacts produce different hashes. in-toto addresses this by using Canonical JSON for metadata objects. Software Heritage's SWHID uses a precise "manifest" serialization per object type (e.g., `"blob" + SP + length + NUL + content` for file contents).

### 2.9 Cross-Namespace Deduplication Tradeoffs

GitLab's Artifact Registry deliberately scopes deduplication to individual namespaces (not instance-wide), trading storage efficiency (~36% overhead compared to instance-wide dedup for container images) for security isolation, predictable performance, and cost attribution. This demonstrates that CAS deduplication is not automatically global — operational and security boundaries constrain it. **Source:** https://gitlab.com/gitlab-org/ops/artifact-registry/-/blob/main/docs/adr/008_content_addressable_storage.md

## 3. Summary: What CAS Provides and Does Not Provide for Provenance

| Property | Provided by CAS? | Required Complement |
|---|---|---|
| Integrity (tamper detection) | **Yes** — hash verification on every read | — |
| Immutability | **Yes** — structural, no overwrite possible | — |
| Deduplication | **Yes** — automatic within storage scope | — |
| Trustless distribution | **Yes** — verify without trusting intermediary | — |
| Decentralized identifier computation | **Yes** — intrinsic to content | Canonical serialization spec |
| Authenticity (authorship) | **No** | Digital signatures (DSSE, Sigstore, GPG) |
| Availability | **No** | Replication, pinning, redundancy |
| Confidentiality | **No** | Encryption (at cost of dedup) |
| Human-readable naming | **No** | Mutable pointer layer (refs, IPNS, DNS) |
| Safe garbage collection | **No** — requires careful design | Reference counting, mark-and-sweep, pinning |
| Hash algorithm agility | **No** — must be designed in | Versioned identifiers (SWHID, multihash) |
| Bit-level reproducibility across formats | **No** — requires canonicalization | Canonical serialization rules |

CAS provides the foundational integrity and immutability guarantees that provenance systems require. It does not, by itself, establish *who* produced an artifact, *whether* an artifact remains available, or *what name* a human should use to find it. Long-lived artifact provenance requires CAS as a substrate, complemented by digital signatures for authenticity, replication for availability, and mutable naming layers for usability — all within a framework (such as SLSA + in-toto + Sigstore) that specifies how these pieces compose.
