# Rollback-Journal vs. WAL Mode in SQLite: Reader/Writer Behavior and Crash Recovery

## 1. Fundamental Mechanism

**Rollback Journal (default DELETE mode):** Before modifying the database file, SQLite copies original unchanged pages into a separate rollback journal file (`-journal`). Changes are then written directly into the database. COMMIT occurs when the rollback journal is deleted. On crash or ROLLBACK, original pages are replayed from the journal into the database, reverting to the pre-transaction state. *(wal.html §2; atomiccommit.html §1, §3.5)*

**WAL (Write-Ahead Log):** Original content is preserved in the database file; changes are appended to a separate WAL file (`-wal`). COMMIT occurs when a special commit record is appended to the WAL — without writing to the database file. Later, a "checkpoint" operation transfers committed transactions from the WAL back into the database. *(wal.html §2)*

Key structural difference: rollback journal has two primitive operations (reading, writing); WAL has three (reading, writing, checkpointing). *(wal.html §2.1)*

## 2. Reader/Writer Behavior

### 2.1 Rollback-Journal Mode

- **Writers block readers.** Before any changes are flushed from the writer's private memory to the database file on disk, all readers must be temporarily expelled to grant the writer exclusive access. Readers are locked out until the transaction is fully written, synced, and committed. *(isolation.html, "Isolation And Concurrency")*
- **Multiple readers can coexist** via shared locks. A writer escalates through RESERVED → PENDING → EXCLUSIVE locks. PENDING prevents new readers from joining while existing readers drain, preventing writer starvation. *(atomiccommit.html §3.4, §3.8)*
- **Single writer only.** Only one connection may hold a RESERVED lock at a time. *(atomiccommit.html §3.4)*
- **Isolation: serializable** (achieved by actually serializing writes). Readers see only committed transactions — this holds except in shared-cache mode with `read_uncommitted` enabled. *(isolation.html)*

### 2.2 WAL Mode

- **Readers do NOT block writers; writers do NOT block readers.** Writing appends to the WAL file, leaving the database file untouched. Readers operate from the original database while writers simultaneously commit to the WAL. *(wal.html §1, §2.2)*
- **Snapshot isolation.** When a read transaction begins, the reader records the last valid commit record in the WAL as its "end mark." This end mark is immutable for the transaction's duration, ensuring the reader sees the database as it existed at a single point in time. Committed writes after the read transaction starts are invisible to that reader. *(wal.html §2.2; isolation.html)*
- **Single writer.** Only one connection may hold the exclusive `WAL_WRITE_LOCK` at a time. *(walformat.html §2.3.1)*
- **`SQLITE_BUSY_SNAPSHOT`** on read→write upgrade: if a reader attempts to upgrade to a writer after another connection has committed, the attempt fails because the reader's snapshot is no longer the latest version. The reader must ROLLBACK and BEGIN a new transaction (or use `BEGIN IMMEDIATE` from the start). *(isolation.html)*
- **Checkpoint runs concurrently with readers**, but must stop at pages past any reader's end mark to avoid overwriting content the reader is using. Long-running readers can therefore prevent checkpoint completion. *(wal.html §2.2)*
- **Continuous shared lock.** All WAL connections hold `SQLITE_LOCK_SHARED` continuously while attached, including outside transactions — unlike rollback mode where shared locks are released between transactions. *(walformat.html §2.3.1)*

## 3. Crash Recovery Guarantees

### 3.1 Rollback-Journal Mode

Recovery is based on file existence:

1. If a crash/power loss occurs mid-transaction, the rollback journal remains on disk (a "hot journal").
2. The next process to open the database detects the hot journal.
3. That process obtains an exclusive lock and replays original page content from the journal back into the database.
4. The hot journal is then deleted (or truncated/zeroed, depending on `journal_mode` variant: DELETE, TRUNCATE, PERSIST).
5. The database is restored to its pre-transaction state.

*(atomiccommit.html §4.2–§4.6; tempfiles.html §2.1)*

**Key guarantees:**

- **Atomicity.** The transaction either committed entirely (journal deleted) or not at all (journal present → rollback). The commit instant is the deletion of the journal file, which appears atomic from a user-process perspective. *(atomiccommit.html §3.11)*
- **Two-phase journal flush.** Page data is flushed to the journal first, then the journal header (recording the page count) is flushed in a separate sync. If power is lost between these two flushes, the header shows zero pages — no rollback occurs, and the database remains as-is. This is safe because no database pages were yet modified. *(atomiccommit.html §6.2; §3.7)*
- **OFF/MEMORY journal modes disable crash recovery.** OFF omits the journal entirely; MEMORY stores it only in RAM. Both risk corruption on crash. *(tempfiles.html §2.1)*
- **Hot journal must remain with its database file.** Moving or renaming either file will cause recovery to fail, potentially leaving the database inconsistent. *(atomiccommit.html §9.5)*

### 3.2 WAL Mode

Recovery rebuilds the WAL-index from the WAL file:

1. The first thread to connect to a WAL-mode database runs recovery.
2. Recovery does a single pass over the WAL file from beginning to end, verifying checksums on each frame.
3. The scan stops at end-of-file or at the first invalid checksum.
4. `mxFrame` is set to the index of the last valid commit frame (a frame with a non-zero "size of database" value in bytes 4–7 of the frame header).
5. `nBackfill` is initialized to zero, since recovery cannot know how many frames were previously checkpointed. All valid WAL content will be re-checkpointed as needed.

*(walformat.html §3)*

**Key guarantees:**

- **Atomicity (roll-forward semantics).** Only complete, checksum-verified commit frames survive recovery. A partially written commit frame (from a crash mid-write) fails checksum validation and is discarded. The database is effectively rolled forward to the last valid commit. *(walformat.html §3 — evidence for checksum/discard mechanism; the "roll-forward" characterization is inference from the described behavior: nBackfill=0 plus valid commit frames in the WAL means committed-but-uncheckpointed transactions are replayed forward.)*
- **Exclusive recovery lock.** During recovery, exclusive locks are held on `WAL_WRITE_LOCK`, `WAL_CKPT_LOCK`, `WAL_RECOVER_LOCK`, and `WAL_READ_LOCK(1–4)`. Only `WAL_READ_LOCK(0)` is left unlocked, preventing any other thread from writing or reading WAL content until recovery completes. *(walformat.html §3)*
- **The shm (wal-index) file is not needed for recovery.** It contains no database content and is truncated/rebuilt by the first client to connect. It is never fsync()-ed. *(walformat.html §1.3)*
- **Crash during checkpoint is safe.** *(Inference: if a crash occurs during checkpoint, the WAL file still holds the complete committed transactions. Recovery sets nBackfill=0, so any partially checkpointed pages will be re-applied from the WAL. This follows from walformat.html §3: nBackfill reset to zero on recovery, combined with checksum-verified commit frames in the WAL.)*
- **Critical constraint:** The WAL file is part of the database's persistent state. Separating a database from its WAL file may lose committed transactions or corrupt the database. The only safe way to remove a WAL file is to open and cleanly close the database via `sqlite3_close()`. *(wal.html §4)*

## 4. Comparison Summary

| Aspect | Rollback Journal | WAL |
|---|---|---|
| **Write mechanism** | Copy original pages to journal, write changes to DB | Append changes to WAL file, DB unchanged |
| **COMMIT moment** | Deletion of rollback journal | Append of commit record to WAL |
| **Reader/writer concurrency** | Writers block readers; serialized | Concurrent; readers and writers operate simultaneously |
| **Isolation level** | Serializable (via write serialization) | Snapshot isolation |
| **Crash recovery** | Rollback: replay original pages from journal to DB | Roll-forward: replay committed frames from WAL; discard partial frames via checksum |
| **Recovery indicator** | Presence of hot journal file | WAL file with valid commit frames |
| **Key vulnerability** | Hot journal must not be moved/renamed | WAL file must not be separated from DB |
| **Write I/O per changed page** | Two (journal + DB) | One (WAL only); also sequential I/O |
| **Durability mechanism** | Two-phase journal flush + DB sync | WAL fsync (depends on `PRAGMA synchronous`) |
| **Cross-machine support** | Works | Does NOT work (requires shared memory for wal-index) |
| **Mode persistence** | Not persistent; reverts to DELETE on reopen | Persistent across reopens |
| **Backwards compatibility** | All SQLite versions | SQLite ≥ 3.7.0 (2010-07-21); DB header version bytes 18–19 set to 2 |

## 5. Notable Limitations

- **WAL and network filesystems.** WAL does not work over network filesystems because the wal-index requires shared memory accessible to all processes on the same host. *(wal.html §1)*
- **WAL and multi-database transactions.** Transactions involving multiple ATTACHed databases are atomic per-database but not atomic across all databases as a set in WAL mode. *(wal.html §1; tempfiles.html §2.4)*
- **WAL read-only access** (≥ 3.22.0, 2018-01-22): possible if `-shm` and `-wal` files already exist, or write permission exists on the containing directory, or the `immutable` query parameter is used. *(wal.html §5)*
- **WAL without shared memory:** if `locking_mode=EXCLUSIVE` is set before first access, WAL can operate using heap memory for the wal-index — suitable for single-process use. *(wal.html §8; walformat.html §1.5)*
- **WAL-reset bug (historical):** versions 3.7.0 through 3.51.2 contained a rare data race that could cause corruption during concurrent checkpoint and WAL-reset operations. Fixed in 3.51.3 (2026-03-13). *(wal.html §11)*
- **`SQLITE_BUSY` in WAL mode:** despite general non-blocking behavior, readers may get `SQLITE_BUSY` during (a) recovery, (b) cleanup when the last connection closes, or (c) when another connection holds exclusive locking mode. *(wal.html §9)*
- **Checkpoint starvation:** continuous overlapping readers can prevent any checkpoint from completing, causing unbounded WAL file growth. Mitigation: ensure "reader gaps" or use `SQLITE_CHECKPOINT_RESTART`/`TRUNCATE`. *(wal.html §6)*
- **Rollback journal variants (DELETE, TRUNCATE, PERSIST):** these differ only in how the journal file is invalidated after commit — deletion, truncation to zero, or header zeroing — but share the same concurrency and recovery model. *(tempfiles.html §2.1)*
