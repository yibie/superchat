# Rollback-Journal vs. WAL Mode in SQLite: Reader/Writer Behavior and Crash Recovery

## 1. Fundamental Mechanism

**Rollback Journal (default, DELETE mode):** Before modifying the database file, SQLite writes a copy of the original unchanged pages into a separate rollback journal file (`-journal`). Changes are then written directly into the database file. COMMIT occurs when the rollback journal is deleted. On crash or explicit ROLLBACK, the original pages are played back from the journal into the database to revert to the pre-transaction state. (Evidence: wal.html §2; atomiccommit.html §1, §3.5)

**WAL (Write-Ahead Log):** This inverts the rollback approach. Original content is preserved in the database file; changes are appended to a separate WAL file (`-wal`). COMMIT occurs when a special commit record is appended to the WAL — without writing to the original database file. Later, a "checkpoint" operation transfers committed transactions from the WAL back into the database. (Evidence: wal.html §2)

Key structural difference: rollback journal has two primitive operations (reading, writing); WAL has three (reading, writing, checkpointing). (Evidence: wal.html §2.1)

## 2. Reader/Writer Behavior

### 2.1 Rollback-Journal Mode

- **Writers block readers.** Before any changes are flushed from the writer's private memory to the database file on disk, all readers must be temporarily expelled to grant the writer exclusive access. Readers are locked out until the transaction is fully written, synced, and committed. (Evidence: isolation.html, "Isolation And Concurrency" section)

- **Multiple readers can coexist** via shared locks. A writer must escalate through RESERVED → PENDING → EXCLUSIVE locks. The PENDING lock prevents new readers from joining while existing readers drain, preventing writer starvation. (Evidence: atomiccommit.html §3.4, §3.8)

- **Single writer only.** Only one connection may hold a RESERVED lock at a time. (Evidence: atomiccommit.html §3.4)

- **Readers see only committed transactions.** Readers are prohibited from seeing incomplete transactions by being locked out during writes. This provides serializable isolation through actual serialization of writes. (Evidence: isolation.html)

### 2.2 WAL Mode

- **Readers do NOT block writers, writers do NOT block readers.** Writing merely appends to the WAL file, leaving the original database file untouched. Readers continue operating from the original unaltered database while writers simultaneously commit into the WAL. (Evidence: wal.html §1, §2.2)

- **Snapshot isolation.** When a read transaction begins, the reader records the last valid commit record in the WAL as its "end mark." This end mark is immutable for the transaction's duration, ensuring the reader sees the database as it existed at a single point in time. Committed writes that occur after the read transaction starts are invisible to that reader. (Evidence: wal.html §2.2; isolation.html)

- **Single writer.** Only one connection may hold the exclusive WAL_WRITE_LOCK at a time, so only one writer can append to the WAL. (Evidence: walformat.html §2.3.1)

- **SQLITE_BUSY_SNAPSHOT on read→write escalation.** If a reader attempts to upgrade to a writer after another connection has committed, the attempt fails with SQLITE_BUSY_SNAPSHOT because the reader's snapshot is no longer the latest version. The reader must ROLLBACK and BEGIN a new transaction. (Evidence: isolation.html)

- **Checkpoint can run concurrently with readers**, but must stop at pages past any reader's end mark to avoid overwriting content the reader is using. Long-running readers can therefore prevent checkpoint completion. (Evidence: wal.html §2.2)

- **Continuous shared lock.** All WAL connections hold SQLITE_LOCK_SHARED continuously while attached, including outside transactions. This differs from rollback mode, where shared locks are released between transactions. (Evidence: walformat.html §2.3.1)

## 3. Crash Recovery Guarantees

### 3.1 Rollback-Journal Mode

The recovery mechanism is based on file existence:

1. If a crash/power loss occurs mid-transaction, the rollback journal remains on disk (the "hot journal").
2. The next process to open the database detects the hot journal.
3. That process obtains an exclusive lock and replays the original page content from the journal back into the database.
4. The hot journal is then deleted (or truncated/zeroed, depending on journal_mode variant: DELETE, TRUNCATE, PERSIST).
5. The database is restored to its pre-transaction state as if the aborted transaction never began.

(Evidence: atomiccommit.html §4.2–§4.6; tempfiles.html §2.1)

**Key guarantees:**
- **Atomicity:** The transaction either committed entirely (journal deleted) or not at all (journal present → rollback). The commit instant is the deletion of the journal file, which appears atomic from a user-process perspective. (Evidence: atomiccommit.html §3.11)
- **Two-phase journal flush** ensures integrity: page data is flushed to the journal first, then the journal header (recording page count) is flushed in a separate sector. If power is lost between these two flushes, the header shows zero pages, and no rollback occurs (the database remains as-is, which is safe since no database pages were yet modified). (Evidence: atomiccommit.html §6.2)
- **OFF/MEMORY journal modes** disable crash recovery. OFF omits the journal entirely; MEMORY stores it only in RAM. Both risk corruption on crash. (Evidence: tempfiles.html §2.1)
- **Hot journal must remain with its database file.** If either file is moved or renamed, recovery will fail and the database may be left inconsistent. (Evidence: atomiccommit.html §9.5)

### 3.2 WAL Mode

Recovery is based on rebuilding the WAL-index from the WAL file:

1. The first thread to connect to a WAL-mode database runs recovery.
2. Recovery does a single pass over the WAL file from beginning to end, verifying checksums on each frame.
3. The scan stops at end-of-file or at the first invalid checksum.
4. `mxFrame` is set to the index of the last valid commit frame (a frame with a non-zero "size of database" value in bytes 4–7 of the frame header).
5. `nBackfill` is initialized to zero, since recovery cannot know how many frames were previously checkpointed. This means all valid WAL content will be re-checkpointed as needed.

(Evidence: walformat.html §3)

**Key guarantees:**
- **Atomicity:** Only complete, checksum-verified commit frames survive recovery. A partially written commit frame (e.g., from a crash mid-write) fails checksum validation and is discarded. The database is effectively rolled forward to the last valid commit. (Evidence: walformat.html §3; inferred from the checksum-verification and commit-frame detection logic)
- **Exclusive recovery lock.** During recovery, exclusive locks are held on WAL_WRITE_LOCK, WAL_CKPT_LOCK, WAL_RECOVER_LOCK, and WAL_READ_LOCK(1–4). Only WAL_READ_LOCK(0) is left unlocked. This prevents any other thread from writing or reading WAL content until recovery completes. (Evidence: walformat.html §3)
- **The shm (wal-index) file is not needed for recovery.** It contains no database content and is truncated/rebuilt by the first client to connect. It is never fsync()-ed. (Evidence: walformat.html §1.3)
- **Crash during checkpoint is safe.** If a crash occurs while a checkpoint is transferring WAL content to the database, the WAL file still holds the complete committed transactions. Recovery will set nBackfill=0, and any partially checkpointed pages will be re-applied. (Inference from recovery logic: nBackfill reset to zero on recovery, combined with checksum-verified commit frames in the WAL.)

**Important caveat:** The WAL file is part of the database's persistent state. If a database file is separated from its WAL file, committed transactions may be lost or the database may become corrupted. The only safe way to remove a WAL file is to open and cleanly close the database via sqlite3_close(). (Evidence: wal.html §4)

## 4. Comparison Summary

| Aspect | Rollback Journal | WAL |
|---|---|---|
| **Write mechanism** | Copy original pages to journal, write changes to DB | Append changes to WAL file, DB unchanged |
| **COMMIT moment** | Deletion of rollback journal | Append of commit record to WAL |
| **Reader/writer concurrency** | Writers block readers; serialized | Concurrent; readers see snapshot |
| **Isolation level** | Serializable (via write serialization) | Snapshot isolation |
| **Crash recovery** | Rollback: replay original pages from journal to DB | Roll-forward: replay committed frames from WAL; discard partial frames via checksum |
| **Recovery indicator** | Presence of hot journal file | WAL file with valid commit frames |
| **Key vulnerability** | Hot journal must not be moved/renamed | WAL file must not be separated from DB |
| **Durability guarantee** | Two-phase journal flush + DB sync | Single write to WAL (fsync depends on PRAGMA synchronous) |
| **Performance profile** | Two writes per changed page (journal + DB); better for very large transactions | One write per changed page (WAL only); sequential I/O; faster in most scenarios |
| **Cross-machine** | Works | Does NOT work (requires shared memory for wal-index) |
| **Persistence of mode** | Not persistent; reverts to DELETE on reopen | Persistent across reopens |
| **Backwards compatibility** | All SQLite versions | SQLite ≥ 3.7.0 (2010-07-21); DB header version bytes set to 2 |

## 5. Edge Cases and Limitations (from official docs)

- **WAL mode and network filesystems:** WAL does not work over network filesystems because the wal-index requires shared memory accessible to all processes on the same host. (Evidence: wal.html §1)
- **WAL and multi-database transactions:** Transactions involving multiple ATTACHed databases are atomic per-database but not atomic across all databases as a set in WAL mode. (Evidence: wal.html §1)
- **WAL mode read-only access:** Since SQLite 3.22.0 (2018-01-22), read-only WAL databases can be opened if the -shm and -wal files already exist, or write permission exists on the containing directory, or the immutable query parameter is used. (Evidence: wal.html §5)
- **WAL without shared memory:** If locking_mode=EXCLUSIVE is set before first access, WAL can operate without shared memory, using heap memory for the wal-index. This is suitable for single-process use. (Evidence: wal.html §8)
- **WAL-reset bug (historical):** Versions 3.7.0 through 3.51.2 contained a rare data race that could cause corruption during concurrent checkpoint and WAL-reset operations. Fixed in 3.51.3 (2026-03-13). (Evidence: wal.html §11)
- **SQLITE_BUSY in WAL mode:** Despite the general non-blocking property, readers may get SQLITE_BUSY during (a) recovery after a crash, (b) cleanup when the last connection closes, or (c) when another connection holds exclusive locking mode. (Evidence: wal.html §9)
- **Checkpoint starvation:** Continuous overlapping readers can prevent any checkpoint from completing, causing unbounded WAL file growth. Mitigation: ensure "reader gaps" or use SQLITE_CHECKPOINT_RESTART/TRUNCATE. (Evidence: wal.html §6)
