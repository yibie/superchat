## Concepts

### Session

since: K1
source: `CONTEXT.md:44`; `superchat-runtime.el:1508@superchat-runtime-submit`; `superchat-db.el:126@superchat-db--ensure-schema-1`; `superchat-tape.el:416@superchat-tape-append-event`; `superchat.el:1416@superchat--restore-session-runtime-configuration`

A Session is a durable, string-identified logical context that outlives any single request. Every Tape row carries a `session_id` NOT NULL column, `superchat-tape-append-event` refuses an event without a non-empty `:session-id`, and Runtime mints an ephemeral one (`superchat-runtime--new-id "session"`) when a submitted Request omits it. A Session also carries configuration — capability, topology, authority policy, workspace binding — which is not stored as mutable state but replayed from Tape by `superchat--restore-session-runtime-configuration`.

A Session EditorWorkspace is the process-local live Emacs resource scope keyed by a stable Session ID.  Its state is `unmaterialized`, `open`, `closing`, `retained`, or `closed`.  One private classifier grants ownership only when both the owned marker and Session marker are exact buffer-local, valid metadata.  Inherited defaults and dynamic bindings are unowned; partial or malformed local metadata is rejected by the public owner query and cannot enter enumeration, role reuse, ibuffer grouping, validation, or the close set.  The state registry stores no buffer inventory.  A role lookup reuses a matching live owned buffer, while unmarked and borrowed buffers remain outside its close set.

The EditorWorkspace owns this marker-derived membership, its close state, and the dedicated exact Session View rollover action. Rollover changes one validated session-view buffer to a fresh Session; it is not a general buffer transfer or a whole-workspace close. Runtime owns Run cancellation and execution quiescence but has no editor ownership or close path; the durable Artifact Workspace remains a separate model. The rollover action below preserves the exact View name rather than renaming it from the new Session ID. A tab's Session parameter is a presentation link to the close action rather than buffer-ownership evidence; headless allocation and explicit closure do not need a Session tab.

The legacy `superchat-editor-workspace-buffer` interface remains buffer-only.  The additive `superchat-editor-workspace-acquire-buffer` operation returns the plain process-local plist `(:buffer BUFFER :newly-acquired BOOLEAN)`, computing freshness inside the same authority-owned lookup/create transaction.  This value is not a lease, attestation, token, registry entry, or kill capability.  Its exact rollback operation is fresh-only and idempotent: reuse is an unconditional no-op, identity mismatch has no effect, and a query or hook `error`/`quit` that leaves the exact fresh buffer live publishes `retained` so marker-derived enumeration and public Session-close retry remain available.  It never closes the whole Session.

Given an explicit existing authoritative root, the EditorWorkspace can return a built-in transient project and ask `project-buffers` for a read view.  Nil root produces no project, and the adapter performs no project discovery, persistence, or directory creation.  Project membership may include buffers borrowed by several Sessions and never grants close authority.  Its ibuffer adapter returns a standard Session-labelled predicate group whose evaluation reads the candidate buffer's live ownership markers, so a retained owned survivor remains visible without a cached membership list.

### Turn

since: K1
source: `superchat-core.el:21@superchat-turn`; `superchat-core.el:44@superchat-turn-new`; `superchat-core.el:91@superchat-core--parse-input`; `superchat-core.el:136@superchat-core-prepare-turn`; `superchat-parser.el:10@superchat-parser--file-ref-regexp`; `superchat-parser.el:34@superchat-parser-model-switch`; `test/test-core-pipeline.el:36@pipeline/body-lookalikes-do-not-route-model-or-file`; `test/test-core-pipeline.el:194@pipeline/skill-precedes-command`; `CONTEXT.md:83`

A Turn is the concrete cl-struct `superchat-turn` holding one request's whole preparation state: read-only `id` and `session-id`, the raw `inbound` text, the parsed `clean-input`, and the derived `skill`, `preset`, `command`, `context-files`, `system-prompt`, `prompt`, `tools`, and `state`. `superchat-turn-new` creates one per request. The `@model` and `#file[:range]` forms are command-head syntax: both recognizers are anchored to the absolute start of the string they inspect, and the file recognizer reads `clean-input` after preceding head syntax has been consumed, so identical `@`/`#` text later in a pasted body remains ordinary content. `superchat-core--parse-input` also gives a leading `>skill` precedence over `/command`, skipping the command step once `skill` is set, and `superchat-core-prepare-turn` runs the result through a pure parse-then-hook pipeline that populates prompt and system-prompt without recording or sending anything.

### Preset and Agent Profile

since: K1
source: `superchat-preset.el:22@superchat-preset`; `superchat-preset.el:22@superchat-preset`; `superchat-preset.el:81@superchat-preset-agent-p`; `superchat-preset.el:355@superchat-preset-from-plist`; `superchat-skills.el:148@superchat-skills-load`; `superchat-skills.el:493@superchat-skills-build-prompt`; `superchat-skills.el:522@superchat-skills-invoke`; `superchat-prompt-hooks.el:164@superchat-prompt-hook--file-inline`; `superchat-dispatcher.el:515@superchat-send-input`; `test/test-cmd-dispatch.el:1479@skill/file-context-survives-final-runtime-request-for-all-presets`

A Preset is the cl-struct `superchat-preset`: a portable configuration bundle with read-only `name` and `profile-id` slots, a `type` of `prompt`, `agent`, `plan`, or `workflow`, an explicit `capability`, a `skill-body`, and optional tool/model/limit overrides. A Preset whose type is `agent` is an Agent Profile (`superchat-preset-agent-p`), and `profile-id` — not the user-facing lookup name — is its stable identity. A Skill is one source of Presets: `superchat-skills-load` parses a markdown file's YAML frontmatter into a `superchat-preset`, and the dispatcher reaches it through `superchat-skills-invoke` on `>skill` input. Invocation decorates the Turn's already-prepared prompt rather than rebuilding from `clean-input`: a prompt Preset wraps that prompt with its skill body, while agent and plan Presets preserve it as the user prompt and apply their body through the system prompt. File inline text or metadata added by prompt hooks therefore survives into the final Request on all three paths.

### Capability and Topology

since: K1
source: `superchat-runtime.el:1485@superchat-runtime--validate-profile-capability`; `superchat-runtime.el:1508@superchat-runtime-submit`; `superchat-runtime.el:1365@superchat-runtime--validate-request`; `superchat.el:1388@superchat--apply-topology-overlay`; `CONTEXT.md:28`; `CONTEXT.md:34`

Capability and Topology are two independent coordinates a Run is submitted with. Capability names the purpose of the work (defaulting to `"chat"`) and is fixed by an Agent Profile: `superchat-runtime--validate-profile-capability` signals when a Request's capability conflicts with the Profile's. Topology names the organization of participants and is a closed set — `single`, `team`, `subagent`, `workflow` — rejected at validation if unknown. They do not define each other: the team overlay in `superchat--apply-topology-overlay` adds team tools and a topology briefing without touching capability.

### Tape Entry

since: K1
source: `superchat-tape.el:416@superchat-tape-append-event`; `superchat-tape.el:307@superchat-tape--row-event`; `superchat-tape.el:341@superchat-tape-replay-events`; `superchat-db.el:126@superchat-db--ensure-schema-1`; `superchat-db.el:367@superchat-db-tape-append`; `superchat-tape.el:98@superchat-tape--redact`; `test/test-tape-events.el:244@tape-event/compaction-anchor-is-not-replayed-as-runtime-event`; `CONTEXT.md:88`

A Tape Entry is one immutable, ordered Fact. `superchat-tape-append-event` is the only Runtime-event door into the store; it assigns a logical `event_id` and `recorded_at`, redacts conventionally secret fields, size-limits payloads, and writes a single INSERT into the `tape` table, whose numeric AUTOINCREMENT `id` is the storage cursor. The persistence path is append-only: `superchat-db.el` issues INSERTs against `tape` and no UPDATE or DELETE of a tape row. Entries carry an envelope of optional identity keys — turn, run, actor, profile, workspace, correlation, causation, parent-run, team, audience, sensitivity. Runtime replay admits only rows whose metadata carries `event_type` or `event_id`; schema-only material rows, including typed compaction Anchors, remain available through the material/Context View paths but are not Runtime events.

An Anchor is itself a Tape Entry (legacy kind `"anchor"`) that marks and distills earlier Entries while keeping enough provenance to return to them. `superchat-tape-append-compaction-anchor` writes a typed anchor carrying `source_ids` and refuses any source id that is not already a row in the same Session, and `superchat-view-expand-anchor` reads those ids back to recover the raw Entries. ### Context View

since: K3
source: `superchat-tape-view.el:1077@superchat-view-assemble`; `superchat-tape-view.el:1051@superchat-view--continuity-unknown-envelope`; `superchat-prompt-hooks.el:338@superchat-prompt-hook--conversation-history`; `superchat-prompt-hooks.el:409@add-hook/superchat-build-prompt-functions`; `superchat-tape-view.el:557@superchat-view--continuity-select-records`; `superchat-tape-view.el:385@superchat-view--continuity-policy`; `superchat-tape-view.el:798@superchat-view--continuity-assemble`; `superchat-runtime.el:1165@superchat-runtime--terminal-event-type`; `superchat-tape-view.el:1469@superchat-view--continuity-cancelled-run-ids`; `superchat-llm.el:535@superchat--llm-context-budget-chars`; `superchat-prompt-hooks.el:338@superchat-prompt-hook--conversation-history`; `superchat-prompt-hooks.el:338@superchat-prompt-hook--conversation-history`; `superchat-compact.el:230@superchat-compact--context-budget`; `test/test-tape-view.el:383@view/assemble-oversized-newest-fact-keeps-older-material`; `test/test-tape-view.el:2138@view/assemble-cancelled-run-is-omitted-but-explicit-recallable`; `test/test-compact.el:668@compact/cancelled-source-invalidates-summary-and-offers-recompact`; `test/test-llm-backend.el:426@test-context-budget-derives-only-from-trusted-window`

A Context View is the rebuildable, purpose-scoped selection of Tape Entries handed to the model, materialized as a `"context-continuity-v0"` envelope plist. It carries `:status` (satisfied/partial/empty/unknown/blocked), a rendered `:prompt`, a `:scope` naming the session, purpose, lineage and selection policy, `:items`, a `:disclosure` split into covered / represented / omitted / recallable, and a `:receipt`. `superchat-view-assemble` builds it and `superchat-prompt-hook--conversation-history`, registered on `superchat-build-prompt-functions`, prepends it to the prompt and attaches the whole envelope to Turn state for audit. Its default prompt selection excludes material whose durable Runtime provenance belongs to a Run sealed by `run.cancelled`; this is a View choice, not a Tape mutation. When the latest typed compaction Anchor has any source from such a cancelled Run, the View invalidates the entire summary, falls back to raw material after excluding cancelled rows, and does not silently reuse an older Anchor. This is a safe degradation: the cancelled input/answer rows and the `run.cancelled` ledger row remain intact in the append-only Tape, exact sources remain recoverable through an explicit recall/expand-style read path, and the UI offers `可 /compact 重新压缩`. The whole-summary invalidation is disclosed as a recoverable `cancelled` omission. It never writes to Tape. Runs in the same Session intentionally share this Context View, so an ordinary Run may receive user material from an in-flight workflow Run. The owner-keyed regions used by the transcript renderer are a rendering-ownership boundary only; they do not promise Context View or prompt isolation (`test/test-cmd-dispatch.el:1395@workflow/original-view-input-cancellation-is-terminal-and-local`, `test/test-cmd-dispatch.el:1414@workflow/original-view-input-failure-is-terminal-and-local`).

Three facts govern what it selects and how much of it there is.  **The budget is derived per Turn, not fixed.**  `superchat--llm-context-budget-chars` (`superchat-llm.el:535@superchat--llm-context-budget-chars`) returns `superchat-context-max-chars` verbatim when the user set it to an integer, consulting no capability at all; otherwise it derives a budget **only** when the window capability's `:source` is `override` or `lm-studio-runtime`, floored at 0, and falls back to a fixed 40000 characters for every other source — including llm.el's own static table.  The result lives only in Turn state as `:context-max-chars` (`superchat-prompt-hooks.el:338@superchat-prompt-hook--conversation-history`, `superchat-prompt-hooks.el:338@superchat-prompt-hook--conversation-history`); it never reaches the Request Plan, the Run entry, the receipt or the Tape.  Compaction **prefers** that stored value, read back through `superchat--current-turn` (`superchat-compact.el:230@superchat-compact--context-budget`), so `/compact` is sized by the budget of the `/compact` Turn itself; the token-recovery path always passes a target model and therefore always re-derives its own.

**Selection is a three-way per-record rule**, applied newest-first (`superchat-tape-view.el:557@superchat-view--continuity-select-records`), after the cancellation exclusion: a material record whose durable `run_id` is named by a `run.cancelled` terminal is excluded and disclosed `cancelled`, but the scan continues; a record whose rendered line alone exceeds a positive character budget is skipped and disclosed `oversized` while the scan continues; a `model-interpretation` record that fits alone but not in what is left is skipped and disclosed `budget`; and an ordinary record that fits alone but not in what is left **terminates** the selection.  Only the third case ends the scan, which is why a single oversized recent fact no longer empties the whole View.  Assemble's entry budget is `superchat-context-message-count` with nil meaning unlimited (`superchat-tape-view.el:798@superchat-view--continuity-assemble`), while the recall builders keep a default of 50 and do not apply the default cancellation filter to an explicit selector.

**The policy identifier no longer describes the selection.**  The string is still the literal `"continuity-v0/recent-first"` (`superchat-tape-view.el:385@superchat-view--continuity-policy`), but a skipped record leaves a hole, so the result is not a suffix; the selection function's own docstring has already been rewritten to the three-way rule, and every Context View envelope builder now publishes `:selection-policy-version 1`.

### Effect

since: K1
source: `superchat-authority.el:284@superchat-authority--effect`; `superchat-authority.el:399@superchat-authority--decision-for-effect`; `superchat-authority.el:348@superchat-authority-resolve-effects`; `superchat-authority.el:561@superchat-authority--effective-decision`; `superchat-tools.el:1731@superchat-register-tool`

An Effect is the pure descriptor `(:effect KIND :resource RESOURCE [:scope SCOPE])` that says what a tool call will do. The base policy recognizes `local-read`, `local-write`, `process-exec`, `runtime-exec`, `external-read`, `external-write`, and `unknown`; this is not a validated closed schema, because a plugin resolver may emit another kind and `superchat-authority--decision-for-effect` maps it to `defer`. ### Authority Decision

since: K1
source: `superchat-authority.el:141@superchat-authority--decision-rank`; `superchat-authority.el:399@superchat-authority--decision-for-effect`; `superchat-authority.el:386@superchat-authority-compose-decisions`; `superchat-authority.el:514@superchat-authority--policy-decision`; `superchat-authority.el:561@superchat-authority--effective-decision`; `superchat-authority.el:639@superchat-authority--experience-block-reason`; `superchat-authority.el:77@superchat-authority-known-policies`; `superchat-agent-loop.el:60@superchat--agent-effective-guardrails`

An Authority Decision uses four ranked verdicts — `deny` (3), `ask` (2), `allow` (1), `defer` (0). ### Workspace Artifact

since: K3
source: `superchat-workspace.el:127@superchat-workspace-bind`; `superchat-workspace.el:151@superchat-workspace--artifact-id`; `superchat-workspace.el:824@superchat-workspace--check-revision`; `superchat-workspace.el:839@superchat-workspace-write`; `superchat-workspace.el:609@superchat-workspace--require-artifact-readable`; `superchat-tools.el:1256@superchat-llm-tools-reload`; `superchat-tools.el:1040@superchat-tool-workspace-publish`; `superchat-workflow.el:911@superchat-research-workflow--artifact-view`

A Workspace is a logical, id-addressed registry that Runs bind to (`superchat-workspace-bind`), and an Artifact is one revisioned, addressable unit of shared content inside it. Each Artifact has a generated `artifact-id`, an adapter (marker-backed buffer region, or a generated/durable file), a content hash, and a revision. The revision check therefore guards **two narrow paths, not every path**. A non-tool write, a same-Run read, and any edit made through a buffer tool are all outside both guards.

The token holds that call's adaptive first-answer wait and separate hard wall-clock timer. The wait grows from the configured base according to the serialized prompt-and-tools estimate but cannot exceed `superchat-response-timeout-hard-limit`; the hard timer is armed once for that transport call. Provider reasoning deltas and tool-call/tool-result markers carry the token through `superchat-llm--notify-activity` to the distribution adapter. The standard owner-backed extension operation neither consults nor reschedules the hard timer. It cancels and reactivates the wait at its later deadline so Emacs reorders `timer-list`; changing only its trigger time is forbidden because an overdue queue-head wait can starve the hard timer behind it. The View's latest allocated owner order is an irreversible high-water mark: only that owner may publish an initial or recovery-rearmed wait, even when some compatibility path has cleared both public timer slots, so an older recovery can never republish into an empty View slot. Owner-backed cancellation compare-clears that slot only when both its owner and timer still match.

Pause is a View-local Action Contract over one identity-bound pending slot, not a retargetable current-Run switch. At the Stage 5 checkpoint, `superchat--llm-generate-answer` may populate the slot only when the requested pause Run ID equals the current transport owner's registered Run ID; the pending record carries that Run ID, the exact transport owner token, the attempt reason, and the continuation. The pause boundary validates the target, record Run ID, and exact owner token before cancelling only that owner's wait through the compare-clear helper. `superchat-resume` performs no steer and invokes no continuation unless the pause target, the pending record's coherent Run/owner identity, and a Runtime-live Run all identify the same Run. Cancel and terminal cleanup compare-clear pause state by the supplied Run ID: a foreign Run cannot clear the pending owner's record, while the pending owner's terminal clears its own state. The resume safety timer captures the same Run ID and can cancel only that live Run while its own timer slot is still current. Pause/resume state cleanup owns no transport timer at all, including its no-argument form. Runtime's legacy no-owner timer cleanup is a distinct path and requires both an absent published owner and an exact match between the target Run ID and the View's `active-run-id`. ### One window capability, two different trust rules

since: K3
source: `superchat-llm.el:535@superchat--llm-context-budget-chars`; `superchat-llm.el:535@superchat--llm-context-budget-chars`; `superchat-llm.el:593@superchat--llm-serialized-attempt`; `superchat-llm.el:615@superchat--llm-estimate-context-tokens`; `superchat-llm.el:1670@superchat--llm-generate-answer`; `superchat-llm.el:1670@superchat--llm-generate-answer`; `test/test-llm-backend.el:1901@test-llm-context-estimator-does-not-trust-generic-word-count`; `test/test-llm-backend.el:1992@test-llm-context-preflight-allows-calibrated-wordy-request`; `test/test-llm-backend.el:2034@test-llm-context-budget-preflight-gates-provider`; `test/test-llm-backend.el:2103@test-llm-context-preflight-names-window-and-action-in-chat-response`; `test/test-llm-backend.el:5152@test-llm-context-budget-compacts-and-resumes-same-run`; `test/test-llm-backend.el:5257@test-llm-pause-steer-reestimates-before-provider`

An explicit integer `superchat-context-max-chars` bypasses capability derivation and is returned directly for the Context View budget.  Otherwise, **two independently derived** context-window capabilities are trusted under two different rules, in two places, on purpose — this is not one plist read twice.  The Context View side derives its capability from `(or target-model superchat-llm-model …)` (`superchat-llm.el:535@superchat--llm-context-budget-chars`) and accepts it **only** when the `:source` is `override` or `lm-studio-runtime`, otherwise falling back to a fixed character count (`superchat-llm.el:535@superchat--llm-context-budget-chars`).  The transport derives a second capability from the effective backend's own chat model (`superchat-llm.el:1670@superchat--llm-generate-answer`), and the pre-flight over-budget check accepts its numeric `:limit` whatever the source — the source is read only to be recorded in the attempt details — provided the limit exceeds the output reserve.  Immediately before every provider attempt — after queued steers, final-answer instructions, before-attempt View mutations, or a Context recovery rebuild have changed the prompt — `superchat--llm-estimate-context-tokens` asks the provider request builder for the pending call's matching streaming or non-streaming request shape and JSON-serializes it. If that builder cannot serialize, it falls back to the locally serialized system context, messages and tool evidence, and ultimately the printed prompt; llm.el's generic word counter never participates in the gate. The estimate is `ceil(serialized characters / 2.0)`, enlarged by a 10% safety margin, and is never cached across attempts. Transport compares that fresh input estimate plus the prompt's requested output tokens (or its configured reserve) with the effective model's limit. When it cannot fit, that attempt is always blocked before the provider. A one-shot Context recovery hook may rebuild the prompt and start a new attempt, which receives its own fresh preflight; without successful recovery, the terminal chat response immediately names the estimated input, reserve, model window, and the action to shrink the request or switch models. The two capabilities are not guaranteed to describe the same model. Each rule serves its own job — the budget refuses to size a View against a number it does not trust, the pre-flight refuses to send a prompt it can already tell is too large — but the consequence is that with an llm.el-only window the pre-flight can reject a prompt whose View was sized against the fallback. Recorded as enacted behaviour, not as a defect ruling.

K4 is a pure re-anchor: no sentence of any entry above changed, and every entry keeps the `since:` it had at K3.  What changed is the citation form.  From K4 a citation of an Emacs Lisp line carries, after `@`, the name of the top-level form that contains the line — `superchat-runtime.el:1508@superchat-runtime-submit` — computed by `test/kernel-check.el` (`kernel-check--construct-at`), which reads the cited file with the Lisp reader and takes the form whose extent covers the line: a named `defun`, `defmacro`, `defvar`, `defvar-local`, `defcustom`, `defconst`, `defsubst`, `cl-defun`, `cl-defmacro`, `cl-defstruct`, `cl-defgeneric`, `cl-defmethod`, `ert-deftest` or `define-*` form (its quoted first argument resolved to the symbol) yields its name, an unnamed top-level form yields `HEAD/FIRST-QUOTED-SYMBOL` or bare `HEAD`; a top-level object with no symbol head — a literal string, a vector, a list-headed form — yields its Lisp type name (`string`, `vector`, `cons`) (`test/kernel-check.el:326@kernel-check--form-construct-name`; `test/test-kernel-check.el:763@kernel-check/non-symbol-top-level-objects-get-type-names`), and a line inside no form — a comment, the file header, a blank line — yields nothing.  A short citation `:NNN` still names no file of its own; it inherits the file of the previous complete citation in the same entry, and that inheritance is where all 40 wrong-file references corrected in this revision came from — 21 found by the independent checker review, 18 by the author's scan of every short citation, and one more (line 1590) by the fresh-context review of K4 itself: eight were caught by the range check because the inherited file's line was blank or out of range, and the other 32 landed on real code in another file, invisible to `check`, and were found only by comparing the inherited file against the entry's own `source:` line and the construct the sentence names.  The checker's rule (`kernel-check--validate-reference`): a citation whose file is missing, whose line is out of range, or whose line is blank is an error; an annotated `.el` citation whose line is no longer inside the named form is an error naming both the expected and the actual form; a bare `.el` citation without `@-` is a warning, and `--strict` treats it as an error; an annotated `.el` citation with `@-` declares an empty expected construct, so an empty actual construct passes while a non-empty actual construct is an error whose message includes `declared bare` and the actual construct (`test/kernel-check.el:486@kernel-check--validate-reference`; `test/test-kernel-check.el:488@kernel-check/intentional-bare-citations-validate-and-convert`).  `.md` and `.sh` citations carry no construct; they receive the existence, range and blank-line checks, and a marker on them is an error (`test/kernel-check.el:486@kernel-check--validate-reference`; `test/test-kernel-check.el:668@kernel-check/construct-markers-on-non-el-files-are-errors`).  A citation shaped like the text “x.el:7@” is an error rather than a silently discarded citation (`test/kernel-check.el:982@kernel-check--malformed-citation-regexp`; `test/kernel-check.el:986@kernel-check--citation-specs-or-report`; `test/test-kernel-check.el:638@kernel-check/malformed-annotated-citations-are-errors`).  At K5, the two intentional bare citations in this document carry `@-`: `superchat.el:9@-` for the package header and `superchat-compact.el:226@-` for the excluded-section comment; `check --strict` is the gate and reports no warnings on this file (`test/kernel-check.el:525@kernel-check--check-buffer`; `E-20260829-001`).  The anchor is the form, not the line: a construct check sees drift when a cited line crosses a form boundary or the form is renamed; a shift that stays inside the same form is invisible to it, so a line inserted above a form fails the citation of that form's first line, while a citation deeper in the same form keeps its name and stays green with a line number that is now one off.  The line number therefore remains the reader's guide inside the form; the name is what the checker holds.

`@-` only asserts that the cited line is outside every top-level form; it does not anchor the line's text.  Swapping the two comment lines while keeping their `@-` citations leaves `check --strict` green (`test/kernel-check.el:486@kernel-check--validate-reference`; T1 probe recorded in `E-20260829-001`).

`convert` does not write `@-`; choosing this marker is a `learn` judgment, and a real top-level form whose head is `-` is left unconverted (`test/kernel-check.el:573@kernel-check-convert`; `test/test-kernel-check.el:462@kernel-check/converter-leaves-minus-construct-bare-and-checkable`).

In `pairs`, an `@-` citation is grouped by `file:LINE`, so it does not create a shared construct group (`test/kernel-check.el:646@kernel-check--pair-key`; `test/test-kernel-check.el:376@kernel-check/pairs-does-not-share-reserved-bare-citations`).
