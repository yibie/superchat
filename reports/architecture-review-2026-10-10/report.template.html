01 / THESIS

不该推倒重来，但需要把边界落到操作入口。

真正的问题不是“模块太多”或者“提示词太长”，而是已有的架构原则在不同层的落实程度不一致：执行内核严密，后加的工作状态与调度层相对薄弱。

KEEP / 保留

单一执行权威

Run 的接受、取消、终结归 Runtime；模型工具经过一个执行入口；结果交给原先接受的 Sink。这些是异步系统的核心资产。

CLOSE / 补齐

对象范围与生命周期

Workspace 的请求过滤没有自动变成对象读写约束；功能插件撤销也没有覆盖它的全部工具和 collector。

PROVE / 验证

持久意图到执行的交接

工作等待已落盘，不等于后续 Run 已被接受。先写“已唤醒”、再提交的顺序存在实际失败窗口。

本次比前一轮更进一步：不只提出风险。我用临时数据库和脚本模型复现了跨 Workspace 读写、唤醒提交失败、插件半启用以及字段丢弃。既有回归仍全部得到预期结果——说明缺的是边界测试，而不是所有主干逻辑都失效。

源码事实当前源码直接支持已复现本次隔离探针实测推断机制可推导，未单独实测建议尚未批准或实施
02 / SYSTEM MAP

一个宿主进程，四类不同职责。

这是责任图，不是文件依赖图。上方 Kernel 决定能力如何组合；中间决定一次请求如何执行；下方记录事实并更新读模型。点击节点查看它拥有和不拥有的东西。

组合层 · Scope / Service / Event / InvariantService 提供者是全局的；Scope 控制注册可见性和撤销，不是 Session，也不是权限沙箱。
返回路径：模型流与终态 → Runtime → 接受时的 exact Sink。工具结果回到模型循环；它不是第二个 Run。
Runtime、工具及领域模块追加事实；SQLite 是存储，不负责决定业务含义。

Runtime：只保留一个执行生命周期

拥有 Run 接受、Step 推进、终结、排队与取消。借用 Scope 和 buffer；不因 UI 切换而重新选择结果接收者。它不负责裁定“用户的工作是否真的交付完成”。

superchat-runtime.el · superchat-pipeline.el · superchat-sink.el

请求准备Service lookup组合契约

“可组合单体”，不是“每个框都是可独立卸载的插件”。

superchat.el 仍集中加载大量产品模块；Runtime 仍有对具体实现及适配器回调的依赖。插件层很好地控制注册、替换和可见性，但还没有让所有功能变成独立装卸的部署单元。这在单个 Emacs 包里不必然是坏事：不应该为了纯插件架构把每个函数都变成 Service。

03 / OWNERSHIP & LIFETIMES

复杂度主要来自六种生命周期，而不是六种“Agent”。

这些概念应当保持区分。把它们合并看似简单，通常只会把清理、恢复和授权的错误藏到另一个地方。

对象拥有的权威 / 生命周期不能推出什么
Workspace工作地点、规则、Session 和 Work Record 的归属。跨对话持续存在。目录归属不等于文件访问沙箱，也不自动限制按 id 的对象访问。
Session一段逻辑对话、持久身份、权限配置。可包含多次 Turn 和 Run。不是一件工作，不是当前 buffer，不是一个 Scope。
Work Record跨多次执行的目标、进展、等待和结论；通过 Tape 重建。被标完成不等于交付经验证；可继续不意味着自动续跑。
Turn / Run接受的请求及其具体执行。Runtime 是终态的唯一权威。Run completed 不等于 Work completed；取消不证明外部 Effect 已停止。
Preset Scope一次 View 激活的注册集合；进程内存在，退休后撤销。同名 Preset 不共享同一个 Scope；Run 借用它，不拥有它。
Session Buffer Set确切活 buffer 对象上的 ownership 标记决定关闭权。打开了某个文件或显示在某个 tab，并不取得其关闭权。

值得保留的分离

Preset owner 先要求 Runtime 退休其执行，再撤销注册；Session Buffer Set 决定哪些 buffer 可关闭。执行、注册和资源的权威没有混在一个 cleanup 函数里。

生命周期契约buffer ownership

仍要补齐的连接

“这条记录属于哪个 Workspace”已经存下，但读写记录时没有据此校验；“这个功能已卸载”已经知道，但它的工具仍可能被提供。问题出在对象之间的交接，而非词汇缺失。

Artifact Board 另有用途：持久、带 revision 的交付物登记与传递，不是上述文件 Workspace，也不是活 buffer 清单。旧 workspace_* 工具名仍可能让模型混淆这两种对象；改名应按已接受的迁移范围推进，不能改写历史 Tape。

04 / EXECUTION & FAILURE

正常路径统一了；失败路径的严谨程度仍不对称。

一次普通请求

  1. Producer

    确定 Session、来源和 Sink；以 Envelope 提交。来源 Workspace 路由在入口发生，不由 Runtime 猜测。

  2. Driver → Runtime

    验证 Envelope，先询问准入：处理、排队、steer 或拒绝。不是每次提交都会创建 Run。

  3. Driver

    选择工具，收集有预算的 context fragments，组合 system 与 messages；prepared 路径承担自己的准备责任。

  4. Runtime / Transport

    接受执行、捕获 Scope 与 exact Sink；适配器构造 provider 请求，驱动工具循环。

  5. Tool execution

    固定权限阶段不可被监听器绕过；必要时批准；记录请求、进入与结算事实，再向模型交回结果。

  6. Runtime / UI

    封存 Run / Turn，向原 Sink 投递；下游读模型与审阅屏响应终态，不成为第二个终态权威。

评价：统一的是接受和执行契约；不意味着每个 producer 的历史、规则、预算和工作上下文完全相同。源码

执行中取消

  1. 取消到达

    Runtime 停止后续执行资格；不能靠切换 provider 或 Scope 把旧 Run 带回活动状态。

  2. 检查开放义务

    仍有进入但未结算的 Effect，或未决定的 Approval？有则终态可能是 audit-incomplete，而非伪装成已安全取消。

  3. 封存与 quiesce

    记录终态、释放执行关联并停止延续。Sink 消失也不把结果改投当前选中 buffer。

  4. 迟到事实

    真实迟到的结算可以补记一次，但不能改变 Run 终态、再次投递终态或重新调用模型。

  5. 重启

    会话 reopen 为确认中断的执行补 abandoned 等事实；不是从旧 provider attempt 的位置继续运行。

评价：这部分复杂度有实际作用，应通过回归保护，而不是为缩短 Runtime 删除。生命周期契约 · 重启修复

到点唤醒失败（本次故障注入）

  1. 到期记录

    新建该 Workspace 的对话，选定要继续的 Work Record。

  2. Tape 写入

    依次写 work.woken、清除 work.waiting、写 work.focused。

  3. 故障窗口

    本次在 superchat-send-input 处注入错误，阻止提交。此时尚没有对应的活动 Run。

  4. 重新读 Tape

    记录保留“已唤醒”，waiting 已清空；due-p 返回 nil，不再作为到期等待被扫描。

  5. 实际后果

    工作记录还在，但这次自动唤醒机会已被消费。没有证明任务启动成功，也没有待启动状态供调度器重试。

已复现这是进程内提交错误注入，不是真正断电测试；同一写入顺序暴露的崩溃窗口仍需独立验证。分析与修复方向
05 / TRUST & DATA

必须区分三种“边界”。

注册边界

Scope：谁能看到某个工具、监听器或命令；卸载时撤销哪些注册。

它约束正常组合路径，不约束任意 Lisp 的全局修改。Service provider 仍是全局的。

领域范围

Workspace：哪些规则、会话、工作记录属于这个工作的地方。

请求阶段的过滤已存在；按 id 的工作读写和 timer API 没有全面守住这个范围。

执行权限

Permission level：这个工具调用是允许、询问还是拒绝。

eval_elisp 是完整 Emacs 控制。批准后在宿主执行，不等于有 OS 隔离或可回滚事务。

一次调用经过权限管线，不等于它操作了正确对象。当前 work_record 属于内置工具；管线允许调用后，业务函数仍应校验“调用 Session 与目标记录是否同 Workspace”。这个校验目前缺失。相反，编辑 Workspace 外的普通文件是 W9 接受的行为，不能把它误判成同一种缺陷。

Tape 是事实源，不是整个 Emacs 世界的快照。

状态实际来源恢复能力的界线
对话、Run、工具事实Tape → SQLite可以查证、选择和重建已保存证据；不能据此撤销外部副作用。
模型历史与压缩Tape View、Anchor、存储引用改变选择，不改写过去；缺失引用应呈现 unknown，不凭空补出材料。
待保存清单Tape 的编辑 Run ∩ 活 buffer 标记 ∩ modified 状态不是纯 Tape Projection；杀掉或重新打开 buffer 会改变当前结果。
规则Workspace 磁盘上的 AGENTS.md / 后备文件未保存的规则 buffer 不自动成为新请求规则；用户保存是生效边界。
排队与回调Runtime 进程内 FIFO、闭包、借用 Scope排队事实可持久化，不代表队列闭包可跨重启恢复。
工作等待 / 提醒Tape fold + 进程内 Emacs timers可重新上弦；触发事实到新 Run 的接受仍需可靠交接。

权限阶段eval_elisp待保存清单已有增量 Projection

推断完整 Lisp 与 UI 同处 Emacs 宿主，意味着工具执行的可用性与响应性也是共同风险。Run deadline 不能被宣传成对任意同步代码的独立进程级硬抢占。本次没有执行卡死或资源耗尽探针。

06 / REPRODUCED GAPS

五个缺口，指向三个共同根因。

共同根因：① 范围校验停在上下文准备，而未落到业务操作；② 注册 ownership 与功能 ownership 不一致；③ 把“事实已记下”误当成“后续执行已接管”。以下五项均在隔离数据上复现，不是从旧报告直接抄来的判断。

01

知道记录 id，就能跨 Workspace 读、更新、完成它。

优先：高正常工具链已复现

观察与机制

在 A 建记录；在 B 的脚本模型回合里，传入 A 的 id 调用 read → update → done。模型的下一次请求看到了 A 的目标，A 的进度与结论被 B 改写。

superchat-work--require 只检查记录存在且未完成；read 直接全局按 id 获取。这是当前 API 范围缺口，不需要绕过权限管线。

建议修复位置

在模型操作入口，把调用 Session 的 Workspace 与目标记录的 Workspace 一起校验；将用户明确的全局管理操作与模型操作分开。不能只在列表或 prompt 里过滤。

本次探针主动提供目标 id，未证明模型在正常任务中会自动发现该 id。此风险是单用户应用内的数据与工作范围，不是互联网多租户攻击结论。

证据与回归要求

探针：arch-probe/cross-workspace-record-through-real-tool-loop。应增加跨域 read/update/wait/done/follows、临时会话、错误 id 与同域正常路径的回归；不要把 id 当作授权凭据。

记录 API工具入口探针代码

02

在 B 可以看到并取消 A 的提醒。

优先：高正常工具链已复现

观察与机制

A 创建未来提醒；B 调用 timer_list，provider 后续请求中出现 A 的提醒文字；随后 B 的 timer_cancel 成功取消该提醒。

模型接口复用了全局定时器读取与取消，没有按工具调用 Session 缩小范围。这比“上下文里多带几行”更先需要解决。

建议修复位置

模型的 list/cancel 必须有明确的 Workspace 范围。给用户的全局“稍后”总表则可以跨域，并显示归属。全局管理能力和模型默认能力不必相同。

已有 sql 工具也无 Workspace 参数（源码事实，本次未单独执行 SQL 跨域探针），应纳入同一次操作入口清查。

证据与回归要求

探针：arch-probe/cross-workspace-timer-through-real-tool-loop。验证 pending、fired、cancel 和临时会话；只过滤 list 但不校验 cancel 仍然不完整。

03

“已唤醒”先落盘，提交失败后不再是到期等待。

优先：高提交错误注入已复现

观察与机制

在 superchat-send-input 注入错误，前面的三个工作事件已经落盘。重新读取后，记录有 woken，无 waiting，没有活动 Run，due-p 为 nil。

它防止了一次等待重复触发，却没有保证一次等待最终被 Runtime 接受。记录先行解决防重的一边，但牺牲了失败可恢复性。

建议修复位置

为一次等待到一次执行建立稳定关联；区分待提交、已接受和执行结果。对“确认未接受”重试，对“未知是否接受”先核对，不能盲目补跑外部副作用。

复用 Runtime 的唯一接受权，不另建执行引擎。对 timer task 的先 fired 后启动路径做同类故障测试；本次没有把该路径算成已复现。

证据与回归要求

探针：arch-probe/wake-submission-error-consumes-wait。还需覆盖：接受后回执丢失、排队、transport 缺席、重启、重复扫描、记录存储 unknown。当前结论不等于“所有唤醒都会丢”。

写入与提交顺序错误注入

04

卸载 work-records，工具仍能创建永不上弦的等待。

优先：高卸载后工具链已复现

观察与机制

卸载该 row 后，work_record descriptor 仍可选。真实工具链仍成功 start、wait，但 superchat-work--armed 没有该记录。

工具由通用内置工具注册；上下文 collector 属于 chat-collectors；调度与终态观察者属于 work-records。撤销的是一部分能力，不是完整功能。

建议修复位置

让功能拥有其工具、collector 与 observer 的 Scope-accounted 注册；或将未满足依赖表现为明确的不可用状态。选择最小闭环，不强制一个功能只能一个文件。

保留持久历史可读，不应因卸载功能删除 Tape。timers 的类似归属也应检查，而不是只修一个工具名。

证据与回归要求

探针：arch-probe/unmounted-work-row-still-creates-unscheduled-wait。同时验证 materialized 旧 descriptor、重新挂载、已有等待恢复、在途 Run 语义；不得破坏 exact Sink 与已接受 Run 的契约。

row-owned 工具清单功能插件collector 的归属

05

工具接受了字段，但 action 分支悄悄丢掉。

优先：中工具函数已复现

观察与机制

start 同时给 goal、progress、resume、time wait，工具返回创建成功；落盘的只有目标，没有进展、续接说明和等待。

这是“一个宽参数表 + 分支各自消费参数”造成的语义缝隙。强模型也会误用，小模型只是更早暴露它。

建议修复位置

明确允许的复合操作，先验证整个命令，再写入；冲突字段清楚拒绝。可以支持 start + progress + wait，但不应“任何 action 收下任何字段”或用 conclusion 暗中推断完成。

输出结构化的 applied / ignored-or-rejected 结果；目标是减少隐式规程，不是为了短说明隐藏错误。

证据与回归要求

探针：arch-probe/start-ignores-extra-progress-and-wait（直接工具函数，不算完整 provider 回合）。验证无效时间时是否部分建档、done 与 wait 冲突、字段归一化、重复命令。

07 / ARCHITECTURAL TRADE-OFFS

简化应该减少隐式状态，不是削弱证据和权限。

组合：闭合功能，不追求纯化

建议只在可选能力、替换点和独立生命周期上使用 Service / Event。纯转换函数继续直接调用。先修“关掉一行仍留下半个功能”，再考虑模块内部拆分。

不做：按文件行数重构、每个 helper 都服务化、重新引入空的 Run Scope。

持久化：已有基础，不需新数据库

源码事实现有 Projection 已支持 version、checkpoint 和同事务 catch-up。Work / Timer 却仍自己全量 fold。先复用一次请求的读取快照，量出瓶颈再考虑增量化。

不做：没有基准就引入第二套存储，或把可变 Projection 当新事实源。

Projection全量读取

上下文：统一必要约束，不统一全文

源码事实规则 collector 只处理 chat / inline-ask / inline-act；subagent 单独拼规则和记录快照；workflow 走 prepared 路径。共享 Runtime 不自动保证相同约束。

建议为每个 producer 明确规则、身份、权限、历史与预算的责任；在实际 provider 请求上验证。不要强塞完整聊天历史到 rewrite 或 compaction。

入口限制子代理补充路径

模型接口：先降决策成本，再降字节

建议统一参数名、返回当前状态、提供合法复合命令、消除必败工具。Qwen 基线是接口压力测试，不是预先删到九个工具的理由。

不做：自动补括号再 eval、静态脚本检查器直接变成免审批权威、read 偷偷切换当前记录、依据“碰巧存在当前记录”自动转换业务意图。

不是所有写 Tape 的路径，都有同样的可靠性保证。

日常 Emacs 体验，是架构的一部分。

Buffer-first 利用了 Emacs 最独特的能力：模型与用户操作同一个活对象，用户可以检查和保存。但这也意味着多个 Session / Run 可能接触同一用户 buffer。Session 内排队不能证明跨 Session 的目标协调已经解决；本次没有做多 Run 争用实验，不能宣称存在或不存在覆盖缺陷。

08 / RECOMMENDED SEQUENCE

不另开宏大里程碑，按五个可验收切片推进。

以下全部是建议，不是用户已批准的生产改动。它们应归并进现有 roadmap，而不是让本报告变成第二个工作队列。

SLICE 01
范围闭合

让领域对象自己守住访问范围

Work Record 与 timer 的模型操作校验 Workspace；用户全局管理另有入口；SQL 与 prepared producer 同步清查。先写失败测试，再修入口。

退出条件
A 不能被 B 的模型读取、修改或取消；同域继续工作、委派及临时会话不退化。跨 Workspace 文件编辑仍保留 W9 语义。
SLICE 02
组合闭合

功能卸载后不留下半启用承诺

工具、collector、调度和 observer 的 ownership 对齐。持久历史保留；重挂载恢复按明确契约进行。

退出条件
卸载后不再创建无法调度的等待；旧工具引用失效；重挂载不重复计时；在途 Run 按已有生命周期结束。
SLICE 03
交接闭合

把一次等待关联到一次被接受的执行

明确持久唤醒意图、Runtime 接受凭据与结果。先测试错误和 unknown，再决定最小数据结构；不增加第二个执行所有者。

退出条件
提交失败可见且可恢复；接受后回执丢失不重复启动；真正重启与迟到结果通过故障测试。不承诺外部副作用恰好一次。
SLICE 04
交互闭合

给人一张“稍后”表，给模型明确命令

统一待办查看与取消入口；可读唤醒结果与对话链接；合法复合 work 命令；没有对象与参数错误分开。焦点策略单独确认。

退出条件
用户能看到挂着什么、在哪里、怎样停止；工具无静默字段丢失；自动行为不意外夺取编辑控制。
SLICE 05
测量优化

用本地模型和默认配置验证简化

先固定版本建立 Qwen 基线；分别比较说明长度、工具面和上下文。运行默认权限与正常审阅屏；测量读取开销再优化 Projection。

退出条件
指标包括正确交付、错对象率、审批负担、请求数与耗时。五次试跑只作筛查，不声称通过率“不下降”。

贯穿工作：每片同步修正它触及的契约和架构索引；保留先验安全约束、Tape 来源关系、唯一 Runtime 与 exact Sink。不要先删 outcome、审批或工具以换取表面精简。
