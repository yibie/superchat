01 / VERDICT
我的判断：保留主干，收紧三处接缝
应保留
一条执行主线，而不是一套聊天框架加一套代理框架
聊天、就地操作、改写、workflow 和自动任务仍复用 driver → Runtime → model transport；工具仍通过唯一执行管线，终态仍由 Runtime 判定。新功能没有增设第二个 Run 生命周期，这是最重要的正确方向。
依据：
请求生命周期契约
；本次 Kernel、smoke 与 M3 实跑。
已有改善
“触发过”不再被当作“启动成功”
Timer 增加 sending / started / unconfirmed；Work Record 可从 Tape 恢复失去的等待、找到对应执行、报告中断。默认不重跑不确定的副作用，是比“保证自动成功”更诚实的恢复策略。
依据：
到点未启动的裁定
；26 项相关故障测试与旧探针复测。
优先补
Workspace 归属应在对象入口检查，不只在上下文选择时过滤
历史检索已经修正为随 Run 走，但工作记录和定时器仍可被别的 Workspace 的普通工具访问。权限管线没有被绕开；问题是通过管线之后，领域操作没有检查对象归属。
这里的 Workspace 是产品的数据与工作归属，不是抵挡任意 Lisp 或 shell 的安全沙箱。
优先补
启动来源与能力完整性，不能靠事后推断
后台通知依赖发送返回后才写的
timer.started
；工作记录功能被关闭后，工具仍能承诺一个不会上弦的等待。消费者看到的状态，可能比已提供的能力或执行进度晚一步。
建议是补契约和入口验证，不是再增加一层总控 Event 或新的任务系统。
一句话：
主目录已经证明现有分层可以承载增量修复；当前风险不是“层数不够”，而是几项领域规则尚未在唯一入口变成可执行的不变量。

04 / NEW COUNTEREXAMPLES
单项测试全绿，跨边界组合仍会漏
N1 · P1 建议
故障注入复现
共享重试计时器，绕过了单个任务的重试额度
触发条件：
A 的启动持续报错；B 所属会话一直 busy；两个任务都已到点。
A 失败时累计计数，超过额度后不再给自己安排 retry timer。
B 的 busy 等待不受次数限制，继续安排同一个全局 retry timer。
该回调扫描
全部
未启动任务；调用 A 的启动函数之前，不检查 A 是否已耗尽次数。
retry-limit = 2
→ 原始尝试 + 驱动 5 个产品实际安排的回调 →
A 被发送 6 次
，而 B 没有发送、继续保持共享计时器。
根因：
额度只控制“是否安排计时器”，没有控制“是否允许此次尝试”。共享调度脉冲不能代替每个 occurrence 的准入条件。
最小修复方向：
在开始尝试前检查该 occurrence 的额度与下次允许时间；busy 与 failure 分开计数。单个 timer 可以继续共享，但应只调度合格项。不要用新数据库或完整任务队列解决这个局部错误。
测试手动执行已安排的计时器回调，没有真的等待 5 × 300 秒；使用真实 Timer 事实折叠和重试函数。单任务现有回归通过，未覆盖这种相互驱动。

 355  A busy conversation is tried again after `superchat-timer-busy-retry-seconds'
 356  without limit; a failed start after `superchat-timer-retry-seconds', at most

 359           (run (condition-case err

 368            (t (let ((failed (1+ (gethash key superchat-timer--retries 0))))
