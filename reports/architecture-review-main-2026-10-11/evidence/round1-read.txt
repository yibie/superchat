01 / THESIS
不该推倒重来，但需要把边界落到操作入口。
真正的问题不是“模块太多”或者“提示词太长”，而是已有的架构原则在不同层的落实程度不一致：执行内核严密，后加的工作状态与调度层相对薄弱。
KEEP / 保留
单一执行权威
Run 的接受、取消、终结归 Runtime；模型工具经过一个执行入口；结果交给原先接受的 Sink。这些是异步系统的核心资产。
CLOSE / 补齐
对象范围与生命周期
Workspace 的请求过滤没有自动变成对象读写约束；功能插件撤销也没有覆盖它的全部工具和 collector。
PROVE / 验证
持久意图到执行的交接
工作等待已落盘，不等于后续 Run 已被接受。先写“已唤醒”、再提交的顺序存在实际失败窗口。
本次比前一轮更进一步：
不只提出风险。我用临时数据库和脚本模型复现了跨 Workspace 读写、唤醒提交失败、插件半启用以及字段丢弃。既有回归仍全部得到预期结果——说明缺的是边界测试，而不是所有主干逻辑都失效。

03 / OWNERSHIP & LIFETIMES
复杂度主要来自六种生命周期，而不是六种“Agent”。
这些概念应当保持区分。把它们合并看似简单，通常只会把清理、恢复和授权的错误藏到另一个地方。
对象
拥有的权威 / 生命周期
不能推出什么
Workspace
工作地点、规则、Session 和 Work Record 的归属。跨对话持续存在。
目录归属不等于文件访问沙箱，也不自动限制按 id 的对象访问。
Session
一段逻辑对话、持久身份、权限配置。可包含多次 Turn 和 Run。
不是一件工作，不是当前 buffer，不是一个 Scope。
Work Record
跨多次执行的目标、进展、等待和结论；通过 Tape 重建。
被标完成不等于交付经验证；可继续不意味着自动续跑。
Turn / Run
接受的请求及其具体执行。Runtime 是终态的唯一权威。
Run completed 不等于 Work completed；取消不证明外部 Effect 已停止。
Preset Scope
一次 View 激活的注册集合；进程内存在，退休后撤销。
同名 Preset 不共享同一个 Scope；Run 借用它，不拥有它。
Session Buffer Set
确切活 buffer 对象上的 ownership 标记决定关闭权。
打开了某个文件或显示在某个 tab，并不取得其关闭权。
值得保留的分离
Preset owner 先要求 Runtime 退休其执行，再撤销注册；Session Buffer Set 决定哪些 buffer 可关闭。执行、注册和资源的权威没有混在一个 cleanup 函数里。
生命周期契约
buffer ownership
仍要补齐的连接
“这条记录属于哪个 Workspace”已经存下，但读写记录时没有据此校验；“这个功能已卸载”已经知道，但它的工具仍可能被提供。问题出在对象之间的交接，而非词汇缺失。
Artifact Board 另有用途：持久、带 revision 的交付物登记与传递，不是上述文件 Workspace，也不是活 buffer 清单。旧
workspace_*
工具名仍可能让模型混淆这两种对象；改名应按已接受的迁移范围推进，不能改写历史 Tape。

正常路径统一了；失败路径的严谨程度仍不对称。

一次普通请求
Producer
确定 Session、来源和 Sink；以 Envelope 提交。来源 Workspace 路由在入口发生，不由 Runtime 猜测。
Driver → Runtime
验证 Envelope，先询问准入：处理、排队、steer 或拒绝。不是每次提交都会创建 Run。
Driver
选择工具，收集有预算的 context fragments，组合 system 与 messages；prepared 路径承担自己的准备责任。
Runtime / Transport
接受执行、捕获 Scope 与 exact Sink；适配器构造 provider 请求，驱动工具循环。
Tool execution
固定权限阶段不可被监听器绕过；必要时批准；记录请求、进入与结算事实，再向模型交回结果。
Runtime / UI
封存 Run / Turn，向原 Sink 投递；下游读模型与审阅屏响应终态，不成为第二个终态权威。
评价：
统一的是接受和执行契约；不意味着每个 producer 的历史、规则、预算和工作上下文完全相同。
源码
执行中取消
取消到达
Runtime 停止后续执行资格；不能靠切换 provider 或 Scope 把旧 Run 带回活动状态。
检查开放义务
仍有进入但未结算的 Effect，或未决定的 Approval？有则终态可能是 audit-incomplete，而非伪装成已安全取消。
封存与 quiesce
记录终态、释放执行关联并停止延续。Sink 消失也不把结果改投当前选中 buffer。
迟到事实
真实迟到的结算可以补记一次，但不能改变 Run 终态、再次投递终态或重新调用模型。
重启

评价：
这部分复杂度有实际作用，应通过回归保护，而不是为缩短 Runtime 删除。

05 / TRUST & DATA
必须区分三种“边界”。
注册边界
Scope：
谁能看到某个工具、监听器或命令；卸载时撤销哪些注册。
它约束正常组合路径，不约束任意 Lisp 的全局修改。Service provider 仍是全局的。
领域范围
Workspace：
哪些规则、会话、工作记录属于这个工作的地方。
请求阶段的过滤已存在；按 id 的工作读写和 timer API 没有全面守住这个范围。
执行权限
Permission level：
这个工具调用是允许、询问还是拒绝。
eval_elisp 是完整 Emacs 控制。批准后在宿主执行，不等于有 OS 隔离或可回滚事务。
一次调用经过权限管线，不等于它操作了正确对象。
当前
work_record
属于内置工具；管线允许调用后，业务函数仍应校验“调用 Session 与目标记录是否同 Workspace”。这个校验目前缺失。相反，编辑 Workspace 外的普通文件是 W9 接受的行为，不能把它误判成同一种缺陷。
Tape 是事实源，不是整个 Emacs 世界的快照。

五个缺口，指向三个共同根因。

07 / ARCHITECTURAL TRADE-OFFS
简化应该减少隐式状态，不是削弱证据和权限。
组合：闭合功能，不追求纯化
建议
只在可选能力、替换点和独立生命周期上使用 Service / Event。纯转换函数继续直接调用。先修“关掉一行仍留下半个功能”，再考虑模块内部拆分。

docs/design/plugin-architecture.md:17–49
17  A Scope is a process-local registration context. Contributions are visible to it and its descendants, not to siblings or ancestors. Nearest-layer definitions shadow inherited names; duplicate identifiers in one layer are rejected. Registrations made through a plugin's effect Scope land in its mount layer, while cleanup remains owned by that exact installation.
  18  
  19  Scope disposal withdraws registrations, disposes children before parent effects and unlinks the Scope. Explicit unregister and disposal consume the same one-shot cleanup. Empty layers and consumed cleanup effects do not accumulate through repeated mount/unmount cycles.
  20  
  21  The registering interface determines the default target:
  22  
  23  - Tool and command registrations use explicit `:scope`, then the applying plugin's effect Scope, then the execution Scope, then global.
  24  - Event listeners take an explicit Scope through `superchat-on`.
  25  - Surface names are package-wide Envelope vocabulary. A plugin-added Surface has Scope-accounted cleanup, but the Surface list is not a Preset-shadowed registry.
  26  
  27  Arbitrary Elisp global mutation, timers or external effects are not automatically reversed. Register cleanup through the supplied Scope; the contribute-only-through-Scope Invariant is advisory, not an Elisp sandbox.
  28  
  29  ## Services and execution lookup
  30  
  31  A Service declares required methods and has one active global provider. `superchat-service-provide` validates the method table. Preset Scopes cannot provide a shadow Service: provider replacement affects dependents globally.
  32  
  33  `superchat-service-call SCOPE NAME METHOD ...` selects the caller's execution context, not a private provider. A nil Scope inherits the current execution Scope and otherwise uses global. Explicit `superchat-scope-global` chooses global. `superchat-service-get` is lookup-only: pass the Scope explicitly when inspecting one; nil there retains its global lookup meaning.
  34  
  35  Runtime notifications, provider attempts, asynchronous tool callbacks, terminal Sink delivery and FIFO dispatch restore the accepted execution Scope. Runtime holds this reference privately while needed and releases it at quiesce; it is not serialized into Envelope, Tape or public status. Services remain global even when their methods execute for a child Scope.
  36  
  37  ## Scoped tools, commands and permission listeners
  38  
  39  Tools and commands are read through the caller's visible Scope layers. A tool's materialized callable retains the exact installation identity it was materialized from. Revocation invalidates an old descriptor rather than letting it run a replacement's implementation. `superchat-register-tool NAME &key function description args async surfaces scope` declares nothing about what the tool does; there is no effect resolver, approval preview or policy registry any more.
  40  
  41  Whether a call may run is decided at execution, not inferred from a cached model-facing tool list. The Session's permission level is applied as a fixed stage after the `tools/pre-execute` waterfall, whose listeners are collected through the caller's Scope ancestry, and the stronger answer stands: `deny` over `ask` over `allow`. A listener can therefore tighten a call and never loosen it; one that answers without delegating ends the waterfall but cannot skip the level stage. An `ask` goes to the `approval/request` waterfall, which ends in the human answerer. A plugin that needs rules for one request registers both on a child Scope it creates for that request and disposes with its Run. See [Permissions the DeepSeek Harness way](../decisions/implemented/2026-09-17-permissions-the-dsh-way.md).
  42  
  43  Commands preserve user-file template fallback when a handler declines or the command provider is absent. Intentional same-layer tool or command replacement requires explicit unregister followed by registration. MCP refresh validates replacement data before changing its own installation; unchanged discovery preserves the existing installation.
  44  
  45  ## Preset composition and lifetime
  46  
  47  Preset data carries a native `:plugins` composition with unique names and proper keyword configuration plists. Markdown frontmatter supports an inline list such as `plugins: [foo, "bar"]`, including `[]`. Map, nested and multiline forms are rejected; they are not silently accepted as full YAML configuration support.
  48  
  49  Each Chat View activation creates an exact `preset/<name>` Scope directly under global. Two Views choosing the same name receive different Scope objects. Preset data contains no Scope. Runtime creates no automatic `run/<id>` Scope, and Session identity is not a Scope level.

  73    "Apply unseen events to materialized projection NAME in SCOPE.

  75  Return the last applied event id."

  92               (lambda ()
