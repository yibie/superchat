# Decision: 写在消息中间的代理技能只管这一条消息

Status: accepted — 用户，2026-10-10。上一份报告末尾问"是所有写在正文里的代理/计划类技能都只管这一轮，还是另用一种写法"，并建议"写在开头是切换整段对话（现状不变），写在正文里只管这一轮"；用户答"好，下一步"。"实现中定下的几点"是实现时定的，随本次向用户报告，用户可以改。

## Problem

`>技能` 调用一个 `agent` 或 `plan` 类型的技能时，分发处在调用之后把它变成整段对话的预设（`superchat--activate-capability`），之后每条消息都带它的人设和工具。`prompt` 类型的技能一直只作用于调用它的那一条消息。

同一天的[另一条决定](2026-10-10-triggers-anywhere-in-the-message.md)让 `>技能` 可以写在消息中间。gptel 的 presets 视频里，写在句子里的预设只对那一次请求生效；用户要求学它对架构有益的部分，不抛开 Superchat 的结构。

代码事实：

- `superchat-preset-apply` 的参数是（预设，这一轮），它只改这一轮：模型、工具、把人设放进系统提示、跑 `:pre`。切换整段对话是分发处另做的一步。
- 带技能的那一轮不套用对话当前的预设（发送路径上的条件是"这一轮没有技能"）。
- Runtime 拒绝"请求的能力名和代理预设声明的能力名不一致"的请求（`superchat-runtime--validate-profile-capability`）；请求的能力名来自对话当前的状态。探针：不切换对话而调用一个声明了 `capability:` 的代理技能，报 "Capability chat conflicts with Agent Profile …"。
- 计划的批准在对话上进行：批准时如果对话当前的预设是计划类，会把它清掉（`superchat-plan.el`）。

## Decision

1. **`agent` 类型的技能写在消息中间时，只作用于这一条消息。** 这一条请求带它的人设、工具和模型；对话的预设不变，不写 `capability.activated` 记录；下一条消息和调用之前一样。
2. **写在消息开头时不变**：切换整段对话。
3. **`plan` 类型的技能写在哪里都切换对话。**
4. `prompt` 类型不变（本来就只作用于一条消息）。

## 实现中定下的几点

- 解析点在认出正文里的技能时，在这一轮的状态上记 `:skill-from-body`；分发处据此跳过切换（`superchat--skill-for-this-message-only-p`）。没有新的请求路径。
- 只管一条消息的那次请求，能力名用技能自己声明的（没声明就沿用对话的），否则 Runtime 会拒绝它。这次执行因此记在技能的能力名下，而对话的能力名没变。
- 对话已经在另一个代理模式里时，这一条消息只带被点名技能的人设和工具，不带对话当前模式的；下一条恢复对话当前模式。这是"带技能的那一轮不套用对话预设"这条现有规则的结果，没有另加逻辑。
- 计划类不做"只管一条"：提出计划、批准、退出计划模式是对话上的几步，一条消息里做不完。
- 回显区在只管一条时写 "🎯 名字: this message only"。

## 不切换时没有的东西

- 技能声明的 `plugins:` 不会挂载。挂载发生在切换对话那一步。
- 对话记录里没有 `capability.activated`；"这一条用了哪个技能"只在这次请求的 `:preset` 上。

## Alternatives considered

**另用一种写法表示"只这一次"。** 没选：用户接受了"位置决定范围"；多一种符号要多记一条规则。

**计划类也只管一条。** 没选：见上，批准流程依赖对话处于计划模式。

**只管一条时仍然切换、结束后切回。** 没选：切换会写记录、退役旧的作用域并取消其中的执行；为一条消息做两次代价和风险都不对等。

## Consequences

验收：`scripts/skill-once-regression.el`（5 个测试，都经完整发送路径，读脚本模型实际收到的请求）。

- 以前在消息开头调用代理技能的用法不变。
- 想让代理技能管整段对话，必须把它写在开头。
- 依赖 `plugins:` 的代理技能写在中间时功能不全，见上一节。
