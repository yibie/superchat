# Decision: 调用技能的那条消息也说明用户在哪里

Status: accepted — 用户，2026-10-10。上一份报告列出"调用技能的那条消息不带'你当前在哪个 buffer'和窗口布局"这个早就存在的缺口，建议先修；用户答"先修缺口"。

## Problem

调用技能的消息（`>技能` 写在开头或中间，三种类型都一样）送给模型时，没有 `[Emacs origin]` 那一段（当前 buffer、文件、major mode、光标位置、用户明确选中的文字），也没有 `[Emacs windows]` 窗口布局。普通消息有。

原因（代码事实）：技能调用之后，分发处把技能和用户输入合成的文字放进这一轮的 `prompt`，它作为 `:chat-prompt-override` 到达收集器。来源收集器和窗口收集器看到这个标记就不出声，说明文字写的理由是"这是用户在检查器里预览并确认过的正文，再往里加会重复，也会把用户删掉的选区加回来"。但用户预览过的请求另有标记 `:chat-prepared-context`，而且带这个标记的请求根本不运行收集器（`superchat-pipeline--collect-context`）。所以这两个收集器里对 `:chat-prompt-override` 的判断，实际只拦住了技能消息。

真实模型上的后果（2026-10-10，沙箱 Emacs）：`用一句话说明 >duty 周五要交什么`，DeepSeek 回答"我没有关于周五要交什么的信息"；消息里写明 buffer 名之后 DeepSeek 3/3、本地 Qwen 1/1 答对。

探针确认系统提示没有缺段：技能消息的系统提示短，是因为技能只声明了少数工具，相应的工具说明不带；工具相同时系统提示只多出技能的人设。

## Decision

来源收集器和窗口收集器只在请求带 `:chat-prepared-context`（用户预览过）时不出声。技能固定了正文的消息和普通消息一样带上来源、选中的文字和窗口布局。

不变的：用户在检查器里预览并发送的请求；技能合成的正文本身；系统提示；历史和附件的收集（本来就对技能消息生效）。

## Alternatives considered

**代理类技能不再固定正文，只让提示类技能固定。** 没选：只修了一半，提示类技能的消息仍然不知道用户在哪里。

**给技能消息另加一个"带来源"的开关。** 没选：标记已经有两个，问题正是把它们当成了一个。

## Consequences

验收：`scripts/skill-context-regression.el`（5 个测试，经完整发送路径）。

- 所有技能消息送给模型的内容变长了：多出来源一段和窗口一段，有选区时还有选中的文字。
- `scripts/skill-once-regression.el` 里一条断言原来假定"用户的话是消息第一行"，改为"出现且只出现一次"。
