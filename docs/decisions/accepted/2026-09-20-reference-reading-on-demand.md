# Decision: 模型按需读取的参考资料（M5 第三片，重写）

Status: accepted（契约）— 2026-09-20。用户当日对四项选择作出裁定（见"已裁定"），并要求"先把这些写进契约，再实现"。取代[原提案](../proposed/2026-09-16-emacs-operating-context-and-reference-contract.md)里 "Slice 3" 一节及其验收条目；原提案的第一、二片（accepted，已交付）不受影响。实现状态由[路线图](../../roadmap.md)管理：**机制已交付（2026-09-20），效用未验证**——见文末交付记录。本文正文写于实现之前，其中关于新工具的权限、记录和输入限制是拟采用的政策；它们现在各有离线测试验证，没有经过真实模型。

这一片要证明的不是"又有一个工具能读出文字"，而是：**模型能否在保持当前任务和权限不变的情况下，适时取得并正确使用所需知识。**

## 要解决的问题

一句话：**模型在任务进行中，没有办法自己取一页操作资料来读，而不改变自己的角色、工具面和执行上下文。**

现在知识只有两种到达模型的方式：

- **常驻**：写进每次请求的系统文字。第四片的 [Emacs 操作说明](../implemented/2026-09-20-emacs-operating-note.md)就是这样——请求里有 `eval_elisp` 或 `edit_buffer` 就附上整段。它判断的是"有没有这种能力"，不是"这次需不需要这份知识"：解释代码、查变量、改普通文本，收到的是同一段键位配置说明。
- **用户显式调用技能**：`>技能名`。这是用户在组织任务，不是模型在查资料。

两者之间缺一档：模型在当前任务里读一份资料，读完还是原来的它。

### 已核对的代码事实（2026-09-20）

- `superchat-skills-load` 返回 Preset；`superchat-preset-apply` 会设置本轮的 Preset、模型（用户没有显式 `@model` 时）和工具，并运行 pre；agent、plan 型把正文放进系统提示。prompt 型正文不进系统提示，但同样可以带模型和工具配置。所以技能有不同类型，**不能一概说成"换身份"**；准确的说法是：`>name` 这条路径上没有哪一种类型保证"读取不带配置副作用"。
- 模型驱动的技能匹配函数 `superchat-skills-match` 在代码里没有调用者；常驻系统文字里没有技能目录。普通聊天中模型不知道有哪些技能，只有用户能触发。
- `superchat-llm-tools-enabled` 的 `on-demand` 是 `always` 的兼容别名，不是按需工具机制。按关键词猜测是否附加工具的旧机制已删除，本提案不恢复它。
- 操作说明的体积上限（1024 字符）目前只是一条测试断言，不是写明的规则。

### 一次测量，以及它不能说明什么

取自一次默认 chat 请求的记录（`calibrate-after-operating-note-01`，apply 第一请求）：工具说明的序列化 JSON 约 5700 字符（9 个工具），系统文字约 1200 字符（其中操作说明 1014）；产品认识的内置工具共 34 个，默认只发 9 个。

这组数字只说明**目前没有观察到工具数量造成的实际问题**。它不能说明更多：字符数不是目标模型 tokenizer 的实测；窗口装得下不等于模型选得准；单次请求的体积不等于多轮任务的总成本。

## 本提案不做什么

- **不做工具懒加载。** 理由只有一条：暂无实际瓶颈，而新增机制会增加复杂度和往返。不以"占窗口比例小"或未经验证的缓存推论作为依据。重新调查的条件是**观察到**工具选择错误、请求成本或延迟成为问题，再结合工具数量和 schema 体积判断；工具数量只是提醒线，不是自动立项线。登记在 `.scratch/followups/03-tool-lazy-loading-is-not-started.md`。
- **不做通用的"懒加载框架"**，也不另起"懒加载技能"项目。技能系统保持原样；参考资料不走 `superchat-skills-load`，不产生第二个相互竞争的目录和读取入口。
- **不把发现做成权限点。** 发现资料不授权任何事；读取资料不改变权限档位、工具面或审批。
- **不自动执行资料里的任何内容。**

## 提案：六个部分

### 1. 短目录

常驻系统文字里的一小段：每份资料一行——稳定 ID、一句用途。它是模型**行动之前**发现资料的入口。由现有的 `system-instructions` collector 贡献，按最终工具面渲染：读取工具不在最终工具面里，目录就不出现，不广告一个不存在的入口。

### 2. 只读的参考读取工具

按稳定 ID 返回随包资料的正文和内容版本。未知 ID、路径样式的输入明确失败；不拼路径、不读任意文件、不退回文件搜索。资料随正在运行的包版本发布，不依赖用户技能目录。

权限（按现行 M6／M7 重写；原文里的 Authority 和免提示名单已不存在）。**拟采用的政策**：它归入现行决定表的"内置工具"一类，三个档位都允许、不向任何人提问，`read-only` 档也可用——它不改任何东西；调用经过正常执行管线并留下 Tape 记录，没有另一条不留痕的读取通道。现行权限表怎样分类是实现的依据，不是新工具已经符合政策的证据。实现后要验证的三件事：只接受受控的资料 ID、不会变成任意文件读取入口（做法是工具本身根本不碰文件系统）；三个档位下都不提问；执行留下记录。

工具名 `read_reference`，唯一参数是字符串 `id`。加入内置默认工具集合（默认 chat／act 请求因此从 8 个内置工具变成 9 个，另有 `ask_user`）；用户已显式设置工具名单的，保留原选择，不自动追加。

**inline-ask 本轮不加入**：它的工具名单是一份固定常量（四个内置读取工具），不会因为本工具存在而自动扩大。这是本轮的范围排除，不是"inline-ask 不需要资料"的结论。

#### 资料放在哪里

独立的 Elisp 数据模块 `superchat-reference.el`：只有数据和两个纯函数（生成目录、按 ID 取正文），不放进工具执行或提示收集器。

- 每个条目：稳定 ID、一句用途摘要、正文，以及它对应的报错特征（第 3 部分）。目录和正文靠同一个 ID 关联。
- 目录只由 ID 和摘要生成，不需要读正文。
- 内容版本由正文计算（正文哈希的前几位），读取时返回。
- 不增加构建步骤；每种声明支持的安装方式只要带上这个 `.el` 就带上了资料。
- 这是当前单份资料的简化选择，不规定以后所有参考资料只能写在 Elisp 里。
- 上限：目录整段不超过 600 字符，每条摘要不超过 120 字符，每份正文不超过 4096 字符；超长的资料拆成多个条目。

### 3. 对应关系明确的报错里的指路句

工具报错经现有反馈路径送达模型，比期待模型主动浏览目录更直接。**但模型是否注意、理解并照做，未经验证；它也不是唯一入口**——许多错误根本不触发报错：

- `lookup-key` 返回数字，调用成功，模型解释错了；
- 改了错误的 keymap，表达式正常执行；
- Buffer 改了、当前会话没改，每一步都成功；
- 没验证重启，却在答复里声称重启有效。

所以入口是互补的两种：短目录管行动之前，指路句管可识别的错误。都管不到的那部分，留在常驻说明里或不在本片范围内。

指路句的边界：

- 保留原始错误原文；指路句附在后面，不替代错误事实。
- 只在对应关系明确时给出（例如 `eval_elisp` 报一个以 `-map` 结尾的变量不存在 → 键位资料）；不把所有错误都导向同一本手册。
- 指路不执行资料里的代码，也不替模型发起读取。
- 读取工具不在当前请求的工具面里，或资料不可用时，不给指路句。
- 同一份资料在一次工具循环里最多指一次，不反复催。

放在哪里（2026-09-20 已查清）：不放在工具函数里——工具执行时不知道本请求的工具面。放在 `superchat-llm.el` 已有的失败反馈里（`superchat--llm-tool-error-feedback`：工具轮里有调用失败时，产品在工具结果之后追加的那条"读上面的错误、改正再试"）。那里拿得到当前请求对象上的工具列表，而且它本来就是产品就失败调用对模型说话的唯一位置。工具结果里的原始错误因此**按构造**不被改动。已知的收窄：判断依据是追加反馈那一刻请求对象上的工具；如果之后有中间件在下一次请求前把 `read_reference` 拿掉，模型调用它会得到现有的"工具不存在"反馈。

首批对应关系只有两条，都来自验收里实际出现过的错误：`eval_elisp` 报"某个以 `-map` 结尾的变量不存在"，以及 `eval_elisp` 报"按键序列以非前缀键开头"→ 键位资料。

### 4. 常驻说明的体积上限

把现在只存在于测试里的 1024 字符上限写成规则：常驻操作说明只放"模型还不知道该去查之前就必须遵守"的内容（保存归用户、只报告检查过的事实）。以后新发现的教训进参考资料，不往常驻说明里加。短目录另有独立上限。超限由发布前检查拒绝，不在运行时悄悄截断。

### 5. 资料的地位：低于产品权限和用户指令

只读的读取工具**不等于**资料内容安全：读出来的文字仍可能建议模型保存文件、执行整个 init Buffer、修改无关配置或绕过审批。把第四片的文字搬进文件不解决内容问题，只改变它出现的时间。

- 资料是操作参考。它与用户本次的指令、权限档位、审批结果冲突时，后者为准；资料正文自己要写明这一点。
- 资料里出现 tools、model 之类的字样不被解释成配置。读取前后，模型配置、工具选择、当前 Preset、插件组合、Scope 和权限档位都不变。
- 资料内容必须符合 [buffer-first mutation](../implemented/2026-09-18-buffer-first-mutation.md)：不指示模型保存。
- 用户调用技能（`>name`）与模型读取资料是两条路，互不触发：读资料不激活技能，技能正文也不因此变成可按 ID 读取的资料。
- 首版不含用户自有资料和外部路径加载。

第一份资料"修改 Emacs 键绑定"的正文要求：

1. 先观察原值和目标 Buffer；
2. 区分三个状态——配置 Buffer、磁盘、当前会话；
3. 只应用本次修改所需的表达式，不默认执行整个 Buffer；
4. 撤销只恢复本任务改变的部分；
5. 持久化由用户决定；
6. 结论以实际观察为准。

### 6. 两层验收，分开记

| 层次 | 要回答的问题 | 怎样判定 |
|---|---|---|
| **机制验收** | 资料能否被发现和读取，内容是否正确，是否保持原有权限和任务上下文 | 离线回归，先红后绿：真实准备／选择／组装路径加假 transport，捕获模型实际收到的请求。目录随最终工具面出现和消失；按 ID 读出正文与版本；未知 ID 和路径输入失败且没有文件读取；读取前后配置快照一致；三个档位都不提问；Tape 有工具记录；指路句只出现在约定的错误上、保留原错误、读取工具不在时不出现；体积上限由检查拒绝越界；第一份资料的正文逐条对照上面六点人工审阅。 |
| **效用验收** | 模型是否在需要时读取，读后是否正确使用，是否减少目标错误，是否引入额外误操作 | 真实模型对照：同一模型、同一任务、同一初始状态，比较"只有常驻说明"与"加上目录和资料"。逐次记录四件事：需要时读了没有；读后用对没有；目标错误（第四片列出的那几类）出现几次；有没有新的误操作（自行保存、执行整个 Buffer、改无关配置）。往返次数和耗时另记，等待批准的时间单列。 |

两种状态的写法现在就定下：

- 只通过机制验收，记为**"机制已交付，效用未验证"**。这可以是一个被明确接受的阶段性结果，但不能据此写"按需知识的缺口已经补上"。
- 效用验收的条件和样本事先固定（见下节），所以可以报告"这组任务里 N 次中通过 M 次"。要禁止的是不当推断，不是统计本身：小样本不外推成产品或模型的成功率；"读了"不等于"有用"；"通过了"不等于"因读取而通过"。
- 如果对照显示模型在需要时不读，或读了没有改善，第三片就停在机制上，或撤回，不为了留住机制去加更多提示。

真实验证可以继续暂缓；暂缓不改变上面的记法。

## 考虑过的其它做法

- **增加一个 `>emacs-guide` 技能**：沿用 Preset 解析和用户显式触发，模型在任务中途取不到。
- **接通 `superchat-skills-match` 做自动技能匹配**：每轮多一次模型分类，匹配到的技能还会应用配置；解决的是"帮用户选技能"，不是"模型查资料"。
- **全部放进常驻说明**：每个任务都承担所有任务的知识成本，而且随教训累积只增不减。
- **通用文件读取充当资料入口**：`read_file` 已经存在，但资料的位置随安装方式变化，靠路径发现不可靠，也会把"读随包资料"和"读用户文件"混在一起。

## 风险

- 目录进了提示，模型仍可能不读；指路句送到了，模型仍可能不理。这正是效用验收要回答的，实现之前不预设答案。
- 多读一次资料多一轮往返。
- 资料文字的正确性要随版本维护；读取不改配置，不等于知识一定正确。
- 资料与常驻说明内容重叠时，两处可能不一致；哪些要点留在常驻说明、哪些移进资料，对照期间两处都保留（见"已裁定"第 3 项），资料正文不得与常驻说明矛盾，由机制验收的人工审阅核对。

## 效用对照的做法（开跑前冻结）

一次小规模、有运行次数上限的真实模型对照。它只能提供初步证据。

| 条件 | 两组保持一致 |
|---|---|
| 产品、模型及参数 | 同一产品提交；同一模型和参数（沿用 M5 验收的 `deepseek-chat`、非流式、`thinking.type=disabled`） |
| 任务起点 | 每次运行独立恢复相同的文件、Buffer 和会话状态 |
| 常驻说明 | 两组完全相同（2026-09-20 更正之后的那一版） |
| 人工审批与保存 | 同一套规则；每次实际的选择和等待时间照实记录 |
| **唯一预定差异** | 第三片关闭／开启。关闭的做法是用产品自己的规则：工具名单里不含 `read_reference`——目录和指路句随之消失，不另设实验开关 |

三类任务，缺一不可：

- **相关任务**：确实可能用到键位资料——M5 验收的那项任务（给当前 major mode 加一个快捷键并在同一 Session 撤销）。
- **工具不报错但容易理解错的任务**：例如"这个按键在当前 mode 里是否空闲"，所选按键使 `lookup-key` 返回数字。只测报错指路不够，这一类测的是目录这个入口。
- **不相关任务**：例如解释一段代码、修改一段普通文本。检查模型是否无故读资料，或因资料扩大了操作范围。

规模：每类任务、每组各 2 次，共 12 次有效运行，这是上限。因验收脚本自身故障而无效的运行照实记录，可补跑，补跑总数不超过 4 次。数字可在开跑前调整，开跑后冻结。

每次运行分别记录五项：是否读取；读的是不是相关内容；读后是否正确使用；最终任务结果（由独立检查器判定）；额外的调用、延迟（等待批准单列）与误操作（自行保存、执行整个 Buffer、改无关配置）。

结果怎样说，现在定下：

- 要说"有初步证据表明有帮助"，须同时满足：开启组在相关和易误解任务里读了相关资料；目标错误比关闭组少；没有新增误操作；不相关任务里没有无故读取。
- 不满足就写"初步观察，无结论"，并照实列出看到了什么。
- 不为得到正面结论去调整目录、正文或指路句再重跑。对照开始之后改动这些文字，本次对照作废；要再比，先重新声明一次对照。

## 已裁定（用户，2026-09-20）

1. **正文位置**：独立的 Elisp 数据模块。理由是减少随包资源遗漏的风险；只是当前单份资料的简化选择。
2. **inline-ask**：本轮不加入。范围排除，不是结论。
3. **常驻说明里的键位要点**：对照期间保留，两组相同。理由是保持实验条件，不是确认常驻内容已经正确。前置条件——先处理已指出的内容问题——已完成：[操作说明的更正](../implemented/2026-09-20-emacs-operating-note.md)（不再无条件推荐 `eval-buffer`，不再预设"未保存"）。
4. **效用验收**：做，按上节的有上限对照；不是"一开一关各跑一次"。

## 实现顺序

1. 红测（新文件 `scripts/reference-regression.el`，各自先红在所指的缺口上）→ 数据模块与第一份资料 → 读取工具 → 目录块 → 指路句 → 变异体。canonical smoke 基线的变化逐项列出。
2. 机制验收通过后，状态记为"机制已交付，效用未验证"。
3. 效用对照另行安排（需要用户在场审批），开跑前冻结上节的数字和任务文本。
