# Decision: Workspace 是一份存下来的记录，目录只是它的一个属性

Status: accepted — 用户 2026-11-10 说"我宁愿先定义好 workspace，我认为应该和 Holon 一样有明确的分层和定义，相当于一个虚拟层"，并定了三点：没有根目录的 workspace 有规矩，规矩文件默认放在 superchat 自己的目录下；成员规则只做自动的；第一版只有 Home 和项目两种。用户同日又定了：不在项目里的文件用文件路径当标识，其余 buffer 用 buffer 名。第四轮原型（下文"试验"）之后，用户同日批准从原型做成正式实现，对所有人默认打开，不设开关。已实现，证据只有脚本化的模型（见"验证"）。标着"提议"的条目用户没有逐条答复；它们按提议实现了，仍待用户确认，见"实现时定的"。

本条取代 [2026-11-09 的提案"工作记录属于开它的那段对话"](../proposed/2026-11-09-a-work-record-belongs-to-its-conversation.md)，并修改 [workspace 契约](2026-10-01-workspace-work-record-session-rules.md)的对象表、W1、W4、W5、W6、W10、W11、S2、R2。被改的各条旁边都加了一行 2026-11-10 的注，指回这里；原文没有改。

## Problem

**你这边发生了什么：** 2026-11-09 你从 telega 的聊天 buffer 叫出 superchat，让它导出聊天记录。这件事跨了 12 次执行，但它落在临时对话里，工作记录开不了，任务只留在聊天历史里，后来被挤掉。

**为什么：** 契约把 workspace 定义成"Emacs 认作 project 的一个目录"。于是"这件事属于哪个上下文""东西能不能留下""命令在哪跑""哪些文件算里面"四个问题，都由"有没有目录"一个答案决定。不对应文件的工作（telega、elfeed、日程）没有目录，就什么都留不下。

代码里这表现为一个字段干五件事。2026-11-10 逐处翻看 `superchat*.el`，有 85 处读 workspace 的根目录，或假设"workspace 就是 project""没有 workspace 就是临时"：

| 用根目录做什么 | 处数 |
|---|---|
| 判断 buffer 属于哪个 workspace | 22 |
| superchat 存自己的东西（编号、规矩、记录） | 15 |
| "没有 workspace 就是临时"的行为 | 13 |
| 命令默认在哪跑 | 13 |
| 只是显示 | 8 |
| 判断文件在 workspace 之内还是之外 | 7 |
| 其它 | 7 |

**别人怎么分：** Holon 分四层，每层只回答一个问题：Agent Home（agent 自己的东西放哪，永远存在）、Workspace（现在在哪个项目的上下文里）、执行根（命令实际在哪个目录跑）、工作目录（这一条命令在哪）。换 workspace 是显式操作，`cd` 不改变它。OpenClaw、Hermes、Grok Bot、Muse 这几个个人助手都把状态挂在助手自己身上，对话按消息来源自动归类。读到的材料见 [参考实现里的事实](../../research/workspace-and-work-record-references.md)和 2026-11-09、11-10 两天读的文档。

## Decision（提议；用户批准了实现，上面 Status 里列的几点是用户定的，其余逐条没有答复，按提议实现，待确认）

### 五层

| 层 | 回答什么 | 在 Emacs 里是什么 | 活多久 |
|---|---|---|---|
| Home | 不属于任何项目的东西放哪 | 一个固定的、属于用户本人的 workspace，不用设置就存在 | 永远 |
| Workspace | 这件事属于哪个上下文；规矩和记录在谁之间共享 | 一份存下来的记录：编号、名字、种类、成员规则，外加可有可无的根目录 | 到用户删除它 |
| 来源 | 此刻从哪叫出 superchat | 当前 buffer，和它的稳定标识 | 标识存在期间 |
| 对话 | 接着哪一段说 | 一段 Tape 会话，属于恰好一个 workspace | 永久存档 |
| 工作目录 | 这一条命令在哪跑 | buffer 的 `default-directory` | 只有这一条命令 |

### Workspace

D1. workspace 是 superchat 存下来的一份记录，不是一个目录。它有：编号、名字、种类（项目、Home）、成员规则、可选的根目录。名字存下来，不再从路径算。

D2. 第一版只有两种：项目和 Home。不能新建别的没有根目录的 workspace。

D3. 成员规则只有自动的两种，用户不手动划 buffer：
- "这个根目录下的文件"：项目。仍以 Emacs 的 project 机制为准（W1 对项目照旧成立）。
- "这些 major mode 的 buffer"：`superchat-personal-workspace-modes` 列的那些界面。
都不匹配的 buffer 归 Home。

D4. 根目录原来干的五件事分开回答：

| 问题 | 项目 | Home |
|---|---|---|
| superchat 把它的编号和规矩存在哪 | 根目录（`.superchat/`、`AGENTS.md`），照旧 | superchat 数据目录下的固定位置 |
| 哪些文件算"之内" | 根目录下的 | 没有边界：任何文件都不标"之外" |
| 命令默认在哪跑 | 根目录，照旧 | 叫出对话的那个 buffer 的 `default-directory` |
| 种类 | 项目 | Home |
| 名字 | 存下来的名字 | 固定的一个名字 |

Home 不拿一个真实目录当根目录。2026-11-10 的翻看表明那样做有 28 处出错，而且错在含义上：命令会在数据目录里跑；从 Home 改的每个文件都被标成"之外"；`open_file` 拒绝数据目录下的一切，模型打不开 Home 自己的规矩文件；在用户这台机器上数据目录位于另一个 git 仓库里面，Home 会被认成那个项目的一部分。

D5. 工作目录不改变归属。对话中 `cd`、打开别处的文件，都不换 workspace。

### Home

D6. Home 永远存在，属于用户本人。它放三样：工作记录、定时器、它自己的规矩。

D7. Home 的规矩文件在 superchat 数据目录下。它只对 Home 里的对话生效，不叠加到任何项目的对话上。项目的规矩也不进 Home。这样 R1 仍然成立：不存在所有 workspace 都带上的规矩或记忆。

D8. 模型按 R4 写 Home 的规矩：只在用户明确说"记住"时写，改的是那个文件的 buffer，用户保存才生效。为此，数据目录的保护要给这一个文件开例外。

D9. Home 里的回忆只搜当前这段对话，不搜 Home 的其它对话。工作记录不在此限：Home 的对话都能看到 Home 的工作记录并接手。

D10. 临时对话变成用户主动要的例外，不再是"碰巧没有目录"的结果。它照 W10：什么都不留，不带进别的对话。

### 来源和对话

D11. Home 里的对话按来源分：同一个来源以后再叫出，接上同一段对话；不同来源是不同的对话，互相看不到对方说过的话。项目里照旧是一个 workspace 一段主对话（S2 对项目不变）。

D12. 来源的标识是一个从粗到细拼成的字符串，原样存、整串比较，不做有损编码。例：`telega:chat:<编号>[:topic:<编号>]`、`elfeed:entry:<编号>`、`eww:<网址>`、`buffer:<mode>:<名字>`。

D13. 标识在发请求时现算，查找顺序：
1. 每种 mode 一个函数，读这个 mode 自己的变量（telega 的聊天编号、elfeed 的条目编号等）。
2. 没有函数、但 buffer 对应一个文件的：用文件的完整路径，`file:<路径>`（用户 2026-11-10 定）。
3. 其余的：用 buffer 名，`buffer:<mode>:<名字>`（用户 2026-11-10 定）。`*scratch*` 属于这一条。

所以每个来源都有标识，不存在一个共用的"未知来源"对话，也不再有"每次新开"的情况。

第 3 条的已知代价：两个内容不同、名字相同的 buffer 会接上同一段对话。所有条目共用一个 buffer 名的 mode（如 elfeed 的条目）必须有第 1 条的函数，否则不同条目会串。Emacs 给重名 buffer 加的 `<2>` 这类后缀取决于创建顺序，重启后不稳定。

Emacs 没有通用机制可用：多数相关 mode 没有定义书签记录，定义了的又带着每次都变的字段。

D14. 对话和来源的绑定记在 Tape 上；一个来源名下最新的那段是它的对话；新开对话仍在同一个来源名下。

## 它推翻了什么，凭什么

这条不是小修。它和三处已经定下的东西相反，都要写明。

**"一个长期存在的临时区"（2026-10-01 否掉）和"默认的个人项目"（2026-11-06 否掉）。** Home 就是这个。

- 10 月 1 日的理由：不在 project 里的使用都落进同一个地方，会变成事实上的全局记忆。
- 11 月 6 日的理由：项目还管着读哪些文件、`AGENTS.md`、改动审阅，为了归属造一个项目会把这些一起带进来。
- 现在凭什么：D11 让 Home 里的对话按来源分开，D9 让回忆不跨对话，所以落进同一个地方的只有工作记录、定时器和 Home 自己的规矩，不是对话内容。D4 把归属和"读哪些文件、哪些算之内"拆开了，Home 不带后两样。
- 仍然成立的代价：Home 的规矩和工作记录确实被所有不在项目里的使用共享。在 telega 里说的"记住"，从 elfeed 叫出的对话也会带上。这正是当时担心的那种混淆的缩小版，只是它到不了项目里。

**R2："superchat 不另设自己的规矩文件"。** Home 的规矩文件就是 superchat 自己设的。用户 2026-11-10 定了这一点。

**W10 的默认地位。** 临时对话从默认变成例外。

## 试验（实现前）

定义落进代码之前，先在副本里做原型，看四件事：

1. **能留：** 从聊天类 buffer 叫出对话、开工作记录；从另一个来源叫出的对话能看到并接手；记录到点被唤醒。
2. **不串：** 在一个来源的对话里说一句带标记的话，从同一来源再开（窗口开着、关掉之后）要接上；从另一个来源、从项目里开，请求里都不能有它。回忆、工作记录清单、定时器各查一遍。
3. **规矩：** Home 的规矩进 Home 的请求，不进项目的请求；项目的规矩不进 Home 的请求；模型能打开并修改 Home 的规矩文件，打不开数据目录下的其它东西。
4. **代价：** 整套回归里有多少测试失败，按"断言的是旧行为"和"别的原因"分开；冒烟基准有哪些要变。

此前三轮原型（2026-11-09，都没有合并）已经测过其中一部分：

| 做法 | 记录有地方留 | 串话 | 就地命令的上下文 |
|---|---|---|---|
| Home 有一段主对话 | 有 | 比现在多：关掉窗口后仍接上同一段 | 保留 |
| Home 每次新开一段 | 有 | 没有 | 丢失：同一个 buffer 连开两次是两段 |
| 按来源分（本提案，2026-11-10 第四轮） | 有 | 没有：历史、自动回忆、`memory_search`、`tool_history` 四条途径都查过 | 保留：关掉窗口后、模拟重启后也接上 |

第四轮（2026-11-10，没有合并）的其它结果：

- 原型 7 个文件，加 246 行、删 34 行。开关关掉时，139 个脚本 9423 项测试和改动前逐项一致。
- 开关全开时 612 个测试新失败：567 个是测试辅助函数按旧名字找聊天 buffer（修正辅助函数后 562 个通过，另 5 个是读代码判断的）；43 个断言的是旧的临时对话行为；2 个是别的原因（一个比对会变的冒烟基准 A，一个是会话缓存只为旧名字的 buffer 写）。冒烟基准 10 个用例要变。
- 那一轮的原型里，没有标识的 buffer（scratch、不在项目里的文件）每次打开都是新对话，43 个里有 21 个断言的正是这一点。D13 的第 2、3 条是为此改的，改后的规则还没有试验过。
- 原型没有修的：管家把一行内容带进对话的路径（`superchat-butler--home-view`）没有传来源 buffer；定时器的几句措辞仍说"不属于任何 workspace"；定时器的任务对话没有绑定，拿不到 Home 的规矩。
- 模拟重启是清掉内存状态并重开数据库，不是真的重启 Emacs。

## 做成了什么（2026-11-10 实现）

**你这边发生了什么：** 从任何不在项目里的 buffer 叫出 superchat，进的是 Home 里属于这个 buffer 的那段对话。比如在 telega 的一个群里叫出它、让它开一条导出聊天记录的工作记录，这条记录会留下；关掉窗口、过后再从同一个群叫出，接上的是同一段对话；从一条 RSS 条目叫出，是另一段对话，看不到群里说过的话，但工作记录清单里能看到那条导出任务，也能接手。

按文件：

- `superchat-workspace.el`：
  - Home（`superchat-workspace-home`）：编号在数据目录的 `home/id`，第一次需要时生成；名字 "Home"，种类 `home`，没有根目录。
  - 不被任何项目认领的 buffer 归 Home（`superchat-workspace-of-source`）。设了 `superchat-personal-workspace-directory` 的，界面类 buffer 照旧归那个目录。
  - 来源标识 `superchat-source-key`，按 D13 三条算。第一条的表是用户选项 `superchat-source-key-functions`。自带的函数：telega 聊天（聊天编号，有话题时加话题编号；不带账号）、elfeed 条目（条目编号）、eww（网址）、dired（完整目录，`dir:<目录>`）、Info（手册名和节点）、Gnus 分组、notmuch 搜索和线索、rcirc 频道。每个函数只用 `bound-and-true-p` 读变量，对应的包没加载时返回空。
  - Home 的规矩：`superchat-workspace-rules-root` 回答"这个 workspace 的规矩存在哪"，Home 只认 `home/AGENTS.md`。"记住"的说明对 Home 先说一句这是 Home，再指向这个文件。
  - `superchat-workspace-home-rules-file-p` 是 `open_file` 的那一个例外。
- `superchat.el`：
  - `workspace.bound` 事实带上编号、根目录（Home 为空）、种类、名字；Home 的对话还带来源标识。重开对话只读 Tape 上的这些。
  - 从 Home 的来源叫出时，找这个来源名下最近活动的那段对话（`superchat--home-view`），没有就新开一段并绑定。对话的命令在来源 buffer 的 `default-directory` 里跑。
  - 在 Home 的对话窗口里 `M-x superchat` 停在这段。`/workspace` 不带参数时显示 "Home (no directory…)"。`/reset` 不解绑 Home，回显改成 "Reset Capability and Topology. This conversation stays in Home; its history is kept."。
  - 分支出来的对话属于 Home，不归任何来源。
  - 会话缓存（关窗口时写给下次启动的那份）原来只给名叫 `superchat-buffer-name` 的 buffer 写，现在也给用户打开的 Home 对话写，见下文。
- `superchat-tape-view.el`：`superchat-view-source-session-ids` 按来源找对话；会话配置多出 `:workspace-kind`、`:workspace-name`、`:source-key`。回忆的范围（`superchat-view-recall-session-ids`）代码没改：Home 没有根目录，本来就只搜自己（D9）。
- `superchat-prompt-hooks.el`、`superchat-subagent.el`：规矩从 `superchat-workspace-rules-root` 取，Home 的对话（聊天、就地问、就地做、改写、子代理）带 Home 的规矩，项目的带项目的。
- `superchat-tools.el`：`open_file` 拒绝数据目录下的一切，只放过 Home 的规矩文件；判断按文件真实指向的位置，规矩文件若是指向数据目录里别的文件的链接，照样拒绝。
- `superchat-work.el`：
  - Home 算一个 workspace：能开工作记录，Home 的对话都看得到 Home 的记录，能接手。
  - 到点唤醒 Home 的记录时，新开的后台对话绑定 Home，不归任何来源，在用户主目录里跑。结果告诉开这条记录的那段对话（Home 没有主对话）。
  - 记录清单的 Workspace 一栏对 Home 的记录写 "Home"。
  - 独立缺陷的修复：`work_record resume` 一条不是当前的记录时，先把它设为这段对话的当前记录，回复写明这一点。原来回复说"这段对话结束后接着做"，但接着做只认当前记录，所以什么也不会发生。`read` 没有改：它只用来看，清单上写着"用 read 读一条"，看一眼不该换掉当前的工作。
  - 拒绝的措辞：记录不属于任何 workspace（Home 之前的临时对话开的）时，说它属于开它的那段对话，不再说"属于另一个 workspace"。
- `superchat-timer.el`：
  - 在 Home 里设的定时器归用户本人（`you`），所有对话都看得到，提醒在设它的那段对话里响。
  - 任务的对话绑定 Home、带 Home 的规矩。
  - 回复不再说 "This conversation belongs to no workspace"，改说这是用户本人的、在 Home 里设的。
  - 取消被拒时，只有对方真属于另一个项目才说"属于另一个 workspace"。
- `superchat-watch.el`：Home 里设编译规则被拒，理由说 Home 没有目录。
- `superchat-butler.el`：管家把一行内容带进对话、而眼前没有对话时，Home 的工作带进它来源的那段对话；来源不明（后台对话）时带进用户当前所在 buffer 的那段，再不然带进工作所在的那段。
- 其它只改了说明文字：`superchat-inline.el`、`superchat-changes.el`、`superchat-dispatcher.el`。

## 实现时定的（用户没有逐条确认）

- **"最新的那段"按最近活动算**，和项目的主对话同一个算法，不按绑定先后。用户从历史列表打开同一来源的一段旧对话并接着说话，以后从这个来源叫出的就是它。
- **按 buffer 名的标识原样用名字。** 不去掉 Emacs 加的 `<2>` 这类后缀；这类后缀取决于 buffer 创建的先后，重启后可能落到另一个 buffer 上，于是接上另一段对话。文档里写明了。
- **不在项目里的 dired buffer** 用 `dir:<完整目录>`（第一条里的函数），不按 buffer 名。
- **对项目也存名字和种类。** D1 说名字存下来、不再从路径算；旧的事实没有名字，照旧从根目录算。
- **Home 的对话分支出去以后不归任何来源。** 否则从来源叫出时会跳到分支上。
- **后台的 Home 对话（唤醒的记录、定时任务）在用户主目录 `~/` 里跑。** 它没有来源 buffer；原来临时对话的这种情况落在哪个目录，取决于定时器触发时碰巧是哪个 buffer。
- **会话缓存。** 这份缓存是旧的交接：关掉"主对话"时把全文写给下次启动的记忆摘要。原来写它的是名叫 `superchat-buffer-name` 的那个 buffer，从不在项目里的 buffer 叫出时那就是临时对话。现在写它的是名叫这个的 buffer，或用户打开的 Home 对话；项目的对话和后台对话照旧不写。好几段 Home 对话都关掉时，后关的覆盖先关的，和原来只有一份一样。
- **`/workspace 目录` 在 Home 对话里，即使这段对话还是空的，也不改绑**，而是打开那个目录的对话（按表里的提议）。
- **`/workspace clear` 和项目对话里的 `/reset` 照旧解绑。** 解绑后的对话是临时对话：这是现在唯一还会产生临时对话的路，都要用户亲手做。没有另做一个"要一段临时对话"的命令。
- **Home 的规矩文件只认 `AGENTS.md`**，不认 `CLAUDE.md`，因为 `open_file` 的例外只开给这一个文件。
- **模型在项目对话里也能打开 Home 的规矩文件。** 例外按文件开，不按对话开；它是用户自己的文字，改了也要用户保存才生效。
- **用户自己的 `/recall` 照旧搜全部对话**（`superchat-memory-recall-scope`，默认 `all`），和项目里一样。这是用户自己的检索，不是模型的；`eval_elisp` 能直接读数据库，也照旧。

## 旧的对话

不改写任何旧的 Tape 记录。打开时：

- **原来绑在项目上的对话**（事实里没有种类和名字）：照旧是那个项目的，名字从根目录算；仍按最近活动当项目的主对话。根目录不在了，绑定照旧丢掉。
- **原来的临时对话**（没有 `workspace.bound`）：仍在历史列表里，打开后仍是临时对话，标题写 "temporary"，请求里仍是临时对话那句说明，开不了工作记录。从任何来源叫出 superchat 都不会进它，因为它不在任何来源名下；在它自己的窗口里 `M-x superchat` 停在它。
- **临时对话里开的工作记录**（没有 workspace 编号）：只有开它的那段对话能碰；用户自己的清单和命令照旧能看到、完成。
- **临时对话里设的定时器**：原来就归用户本人，不变。
- 从 Home 的来源第一次叫出时，总是新开一段 Home 对话；旧的临时对话不会被认作某个来源的对话。

## 验证

证据只来自脚本化的模型：请求发给测试里的假网络，没有接真实模型。

**新测试先在改之前的代码上跑。** [`scripts/workspace-home-regression.el`](../../../scripts/workspace-home-regression.el) 有 35 个测试，在改之前的代码上 35 个全部失败，改之后全部通过。它覆盖：

- 归属和存储：不在项目里的 buffer 归 Home；Home 的编号、名字、种类、来源标识写在 `workspace.bound` 事实上，清掉内存状态、重开数据库之后读回来还是 Home。
- 数据目录在一个 git 仓库里时（用户机器上 `~/.emacs.d` 就是这样），Home 不被认成那个仓库；测试里真的 `git init` 了一个目录。
- 规矩两个方向都隔开：聊天、就地问、子代理三种请求都查了。
- `open_file` 能打开 Home 的规矩文件，打不开数据目录下的其它文件，包括 `home/id` 和一个指向别处的同名链接。
- 命令的目录：Home 的命令在来源 buffer 的目录里跑，它改的文件不标"之外"；项目照旧在根目录跑、照旧标出。
- 按来源分对话：D13 三条各测了。聊天和 RSS 条目用两个替身 mode；真实的标识函数单独测，buffer 局部变量手工设好。同一来源在 buffer 关掉以后、模拟重启以后都接上原来的话。
- 不串话：历史、自动回忆、`memory_search`、`tool_history` 四条路都查了。先在说过那句话的对话里搜一次，确认搜得到，再去别的来源和项目里搜。
- 工作记录：从另一个来源看到、`read`（不变成当前记录）、`update`、`resume`（变成当前记录，后面那一轮在这段对话里跑完）；项目里的 `resume` 也一样；等时间的记录到点在 Home 里被唤醒。
- 定时器的归属和谁看得到；Home 不能设编译规则。
- 命令：`/workspace`、`/reset`、新开对话、指定过个人 workspace 的情况。

## Consequences

- **不在项目里的使用都留下东西了。** 这正是 2026-10-01 否掉的"长期存在的临时区"，代价照旧：在 telega 里说的"记住"，从 elfeed 叫出的对话也会带上；Home 的工作记录清单对每段 Home 对话都可见。到不了项目里。
- **来源标识是按 mode 写的。** 不在 `superchat-source-key-functions` 里、所有 buffer 又同名的 mode，所有条目会接上同一段对话。表是用户选项，可以补。
- **按 buffer 名的标识不稳定**：带 `<2>` 后缀的名字，重启后可能对应另一个 buffer。
- **Home 的对话不会一直变长到装不下**：每个来源各一段，旧的照现有的压缩办法处理。但"一个来源一段"也意味着同一个聊天几个月的话都在一段里；想重新开始用新开对话，它会成为这个来源的对话。
- **临时对话只剩用户亲手解绑这一条路。** 历史里的旧临时对话照旧可用。
- **会话缓存在 Home 下更常被写**：原来只有一段临时对话写它，现在每段打开过的 Home 对话关掉时都写，后关的覆盖先关的。

## 没有验证的

- 没有接真实模型。真实模型看到"别的工作记录"那一行会不会去接手、会不会用 `resume`，没测。
- 标识函数没有在真实的 telega、elfeed、eww、notmuch、Gnus、rcirc buffer 上取过值，只读过代码、用手工设的变量测过；mu4e 和 erc 没有做函数。
- 没有真正重启 Emacs：重启是清掉内存状态并重开数据库模拟的。
- 没有在用户自己的 Emacs、配置和数据目录上试过。用户的数据目录在不在 `~/.emacs.d` 那个 git 仓库里、改没改过位置，没查；测试里用一个真的 git 仓库包住数据目录，证明 Home 不会被认成那个仓库。
- 85 处的清单在实现时逐处对照过，没有另外的人复核。
