# Decision: 轮次要有工具才开始，没有进展就停下；状态行写在自己的对话里

Status: accepted and implemented 2026-10-12。用户看过后接受了三处（leader 转达）：刹车用 2 轮；2026-10-10 那份决定的一半被改掉；预设的名单里没有 `work_record` 时 `/work` 拒绝而不是替用户加上。起因是用户当天在自己的 Emacs 里实测 `/work`（切片 7，`b1900632`）。做法由 leader 写在转达里（"切片 7b"）；刹车的轮数用户没有裁定，leader 建议 2，做成了可配置。下面标了"和转达不同"的两处是实现者读代码后定的。

证据的范围：脚本模型，批处理 Emacs。没有真实模型，没有真人再测一遍。

## 实测里发生了什么（事实）

用户的配置里 `superchat-llm-tool-names` 是一份明确的名单，没有 `work_record`。`/work <目标>` 建了记录，第 1 轮把事情做完了，但模型没有 `work_record`，不能结项也不能说"等你"。第 2 到 5 轮什么都没改，每一轮模型都在说它没有这个工具；第 4 轮它写了"停下来等你"，第 5 轮照样开始。用户在第 5 轮的提问面板上按停才结束，上限是 256。

同一次实测里，对话旁边多出一个名叫 `*superchat*` 的 buffer，里面是几行 `Prefill / waiting first token… 10s`，模型在第 2 轮把它读了进去。

## 1. `work_record` 跟着 `work-records` 这一行走

- 这一行挂着，默认工具面就带 `work_record`，`superchat-llm-tool-names` 滤不掉它。别的内置工具照旧按名单收窄。
- 这一行没挂，任何工具面都不带它；模型硬调用，得到的是"not available"，不建记录。
- 请求或预设自己的明确工具名单（`:tools`）不被放宽：名单里没有它，就没有它。
- `/work <目标>`、`/work resume`、工具自己的 `resume`，在模型拿不到 `work_record` 时不开始任何东西，并说明原因（行没挂、预设的名单里没有、预设不给工具、工具整体关着）。不建记录，不排轮次。

**和转达不同：没有改用 `superchat-register-tool`。** 转达说让这一行用插件接口注册工具。读代码有两处挡着：该接口拒绝内置名字（`work_record` 是保留的内置名）；插件注册的工具在档位规则里是"外部工具"，默认档位下每次调用都要问用户。代码里已有"某一行拥有的内置工具"这套机制（`superchat-tools--row-owned-builtin-names`，子代理、workspace、memory 的工具就是这样挂的），`work_record` 加进了这张表，行在 `:apply` 里登记它；另加一张很短的表 `superchat-tools-row-offered-builtin-names`，列出名单滤不掉的行工具，目前只有它。行为和转达要的一样，工具仍是内置的，不多一次审批。

**这改掉了 2026-10-10 那份决定的一半**（[工具要么记下要么拒绝](2026-10-10-the-work-record-tool-keeps-or-refuses.md)，F4）。那时定的是：这一行关着，工具还在，读、更新、等用户、完成都照常，只有"等某个时间"被拒绝。现在这一行关着，模型根本没有这个工具。函数本身被直接调用时仍按 F4 的方式回答（那几条用例没动）；走真实工具循环的那条用例改成了现在的行为。

## 2. 刹车：连续几轮没有进展就停

- `superchat-work-round-idle-limit`，默认 2，nil 关掉。
- 一轮有进展，指的是：有结构化工具改了某个 buffer（Tape 上该次执行的 `tool.completed` 带 `:buffer`），或模型在记录上写了东西（更新、等待、完成、委派），或留下了未保存的改动（`work.facts`）。
- 连续 N 轮都没有，就不再排下一轮：记录记成 `work.waiting :for user`，说明里写 "no progress in N rounds"；对话里写一行；回显区说一句。表上按现有的"等你"一行显示。
- 用户清掉等待、`/work resume` 之后重新数，再给 N 轮。
- 一轮排了队却没跑起来（对话已关而被丢弃）不算空转。

**这是有意和 DeepSeek Harness 不同的地方。** DSH 的驾驭员只在上限、complete、blocked、中止时停（`goal-round-driver/src/index.ts:166-240`，leader 读的，实现者没有重读）。这里加刹车的理由是当天的事实：模型做完之后会在轮次里打转，而用户在场的话每轮都在等、不在场的话每轮都在花钱。

不足：`eval_elisp` 和 shell 改的东西不被追踪。只靠它们干活、又不在记录上写任何东西的两轮，会被读成没有进展而停下。轮次提示里本来就要求模型用 `work_record update` 记进度，那算进展。

## 3. 状态行写在自己的对话里

**和转达不同：不是轮次独有的毛病。** 转达的推论是排队时绑定的 buffer 名字在派发时丢了。探针显示用户自己发起的执行也一样：只要慢到状态行被定时刷新（约 1 秒以上），而对话 buffer 的名字不是默认名（编辑器布局下是 `*superchat:ID*`），那一行就被写进一个按默认名新建的 buffer。原因在 `superchat--status-refresh-tick`：它从定时器里运行，切到了对话 buffer，但写状态行的函数是按变量 `superchat-buffer-name` 去找 buffer 的，那时这个变量是全局默认值。修法是在这一处把它绑定成对话 buffer 的名字。

这个毛病从什么时候有的没有查。

## 4. 测试实例的数据没有隔离成

当天的实测本想用独立的数据目录，结果写进了用户日常的数据库。原因（读用户的配置确认）：测试实例在命令行里设了 `superchat-data-directory`，而用户配置里设置它的模块在"启动后空闲时加载"的名单里，后加载的把先设的盖掉了。实机清单第 0 步加了"先验证数据目录生效"的三条验证。用户的数据库没有动。

## 没有证实、没有做

- 没有真实模型，没有真人。用户实测里的那个场景（名单里没有 `work_record`，`/work` 之后自己结项）只在脚本模型上重放过。
- finish check 和轮次提示两句相反，仍然没有处理。
- 预设的名单里没有 `work_record` 时 `/work` 是拒绝，没有替用户临时加上。
- 行关着时，记录的那一块上下文和 `/work` 命令本身仍然存在；只有工具没有了。
- 用户数据库里那次实测留下的对话和记录还在，没有清。
