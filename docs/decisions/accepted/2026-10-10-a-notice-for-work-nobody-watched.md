# Decision: 没人看着的工作结束后，在模式行留一个不会自己消失的标记

Status: accepted — 用户，2026-10-10。上一份报告建议"先只做 Emacs 内的，在模式行上留一个不会自己消失的标记，点开能看到是哪条工作记录做了什么；系统桌面通知作为可选项以后再加"，并问通知用什么形式；用户答"先执行下一步"。"实现中定下的几点"是实现时定的，随本次向用户报告，用户可以改。

## Problem

到点的定时任务和被唤醒的工作记录由 Superchat 自己开始执行。2026-10-07 的裁定让这类执行不显示审阅屏、不拿光标。它们结束时用户能看到的只有回显区的一行，下一次按键就没了：

- 留下未保存改动时，有一行"N buffers edited by this Run are unsaved"（`superchat-changes--announce`）。
- 用户不在那段对话的窗口里时，有一行"run … completed (session …)"（`superchat--notify-run-terminal`）。
- 执行失败、且没有改任何东西时，只有后一行。

2026-10-07 的报告把"自动执行留下的未保存改动只有回显区一句话，容易错过"列为没解决的事。

## Decision

Superchat 自己开始的执行结束时，留下一条通知，模式行上出现一个标记，写着待看的条数。标记一直在，直到用户看过或清掉。

- **哪些执行**：和"不显示审阅屏"用同一个判断（`superchat-changes--unattended-run-p`，从对话的持久记录里读）：到点的定时任务开始的执行，被唤醒的工作记录的那次执行。用户自己发起的执行不留通知。
- **哪些结局**：每一种，包括失败、取消、超时。失败且什么都没改的那种最容易错过。
- **标记**：`global-mode-string` 里的一项，形如 `[Superchat: 2]`。几条通知是一个标记加一个数。鼠标点它，或 `M-x superchat-changes-notices`，打开列表。
- **列表**：一行一条，写着结束时间、是谁开始的（哪条工作记录、哪个定时任务）、怎么结束的、留下几个未保存的 buffer、在哪段对话。`RET` 去那段对话并去掉这条通知；`d` 去掉这条；`D` 全部去掉。
- **不会自己消失**指：只有上面三个键会去掉通知。用户之后自己发起的执行、打开列表本身，都不会。

不变的：自动执行不显示审阅屏、不拿光标；回显区原有的两行；保存仍然只由用户做。

## 实现中定下的几点

- 挂在现有的"执行结束"事件（`turn-completed`）上，放在现有的 `changes` 插件里，没有新增插件行。M3 回归集钉着一份插件名单，那个文件不归实现者改。
- **没有用"套一层 Sink"。** [同日的提案](../proposed/2026-10-10-source-turn-destination.md)把这一项写成套在现有 Sink 外面的一层。查代码后改了主意：`turn-completed` 对每一种结局都发，而 Sink 只在有最终回答或出错时被调用；"是不是没人发起的"已经有一个从持久记录判断、有测试的函数，不需要在造 Sink 的那一刻知道。提案里"去向用包一层来组合"那条原则说的是用户为某一次请求选的去向；这里是产品按一个记录里的事实给的默认行为，两者不是一回事。提案已同步改写。
- 通知只存在这个 Emacs 的内存里，重启后没有。它指向的未保存 buffer 也活不过重启；重启前没跑完的唤醒由 `superchat-work--report-cut-off` 在主对话里交代，工作记录自己列着它的各次执行。
- "留下几个未保存的 buffer"是执行结束那一刻数的，之后用户保存了也不会变。
- 没有另加回显区文字，也没有响铃。

## Alternatives considered

**系统桌面通知。** 这次没做，留作以后的可选项：它离开了 Emacs，需要按平台分别实现。

**自动执行也显示审阅屏，只是不选中它。** 2026-10-07 已经否掉：仍然会占掉用户正在用的窗口。

**把通知写进对话记录，重启后还在。** 没选：需要再加一种"用户已看过"的记录来清它，而重启后该交代的事已经有别的路径。

## Consequences

验收：`scripts/unattended-notice-regression.el`（8 个测试；到点任务和唤醒记录走真实路径）。

- 模式行多出一项。没有待看通知时它是空的。
- 自动执行很多的用户会看到数字一直涨，要自己清。
