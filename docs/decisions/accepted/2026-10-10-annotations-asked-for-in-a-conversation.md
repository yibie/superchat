# Decision: 在对话里用 `>annotate` 让这一条的回答挂到 buffer 上

Status: accepted — 用户，2026-10-10。用户要求"优化一下 annotation 的效果，以及它的目的"，并给了 gptel-annotate 的链接。上一份报告列了三件要定的事和建议：挂到叫出这段对话时所在的 buffer、也允许在标记后写文件名；带对话历史；这一步不给工具。用户答："1. 同意建议。2. 可以戴。3. 不给工具。""实现中定下的几点"是实现时定的，随本次向用户报告，用户可以改。

## Problem

[批注](2026-10-10-remarks-hung-on-the-text.md)只有一个单独的命令 `superchat-annotate`：它不带对话历史，模型只看得到那段文字和一句指令。gptel-annotate 的说明里写明，它最有用的用法是在一段已经有上下文的对话里叫出批注，单独当命令用是"盲的、一次性的"。例如先和模型讨论一份纪要哪里有问题，再说"把这些标到纪要上"。

## Decision

对话里的一条消息写了 `>annotate`，这一条就照常作为这段对话的一条消息发出（带历史、Workspace 规矩、你所在的位置），它的回答除了照常显示和记录在对话里，还按批注的规则挂到目标 buffer 上。

- **目标**：`>annotate` 后面没有名字时，是叫出这段对话时所在的 buffer，取自这次请求冻结下来的来源，发出之后切窗口不会改变它。`>annotate 名字` 或 `>annotate "带空格的名字"` 指定一个 buffer 或文件；文件还没打开就打开它。
- **历史**：带。这一条和别的对话消息走同一条路。
- **工具**：不给，对话正处在某个代理技能的模式里时也不给。
- **只管这一条**：下一条消息照常，对话的模式不变。挂上的批注留着。
- **定位、显示、不改文件**：和命令完全一样，用的是同一段代码。对同一个 buffer 再要一次，旧的批注被换掉。

## 实现中定下的几点

- **`>annotate` 不是技能，是这一条回答的去向。** 解析点认出它，记在这一轮输入上（`:destination annotate`），在 `>技能` 之前解析。所以 `annotate` 这个名字被占用：同名的技能在对话里叫不出来。
- **Superchat 自己发出的消息从不认它**，写在开头也不认。定时任务和被唤醒的工作记录发的文字是模型写的，不应该能往你的 buffer 上挂东西。这比 `/命令`"自动消息只认开头"更严。
- **开头的命令优先**：消息以 `/命令` 开头时，后面的 `>annotate` 是普通文字。
- **后面那个词算不算目标**：加了双引号的一律算，找不到就报错，不发请求。没加引号的只有在它正好是一个现有 buffer 的名字或一个存在的文件时才算，否则它是你要说的话的一部分。
- **只写 `>annotate` 没有别的话**：用命令的默认指令（`superchat-annotate-default-instruction`）。
- **去向是包一层**（[结构提案](../proposed/2026-10-10-source-turn-destination.md)的原则 3）：对话自己的 Sink 照常被调用，外面一层在回答到达时再挂批注。所以回答的原文（一行行 `行号 | 引用 | 意见`）仍然显示在对话里。
- **格式要求放在系统提示的最后**，在人设和 Workspace 规矩之后，并说明前面关于"怎么回答"的要求不适用于这一条。带行号的原文作为附带内容放在这条用户消息里。两样都由一个新的收集器给出，没有第二条请求路径。
- **批注整个 buffer**，不看当时有没有选区；超过 `superchat-annotate-warn-lines` 行时不另外提示。
- **记录里留着 `>annotate`。** 发给模型的这一条不带标记，但对话记录里存的是带标记的文字（标记放在末尾，指定过的目标跟在后面）。所以之后各轮的历史里看得出这一条要的是批注，"重新生成"会重新批注，"编辑上一条"会把标记放回输入栏。
- **之后的消息会被告知"那件事做完了"。** 这段对话发过批注消息之后，它后面的每条普通消息的系统提示末尾多一句：之前那条的回答已经由 Superchat 挂到某个 buffer 上，原文没改，不要再把意见写进 buffer。没发过批注消息的对话没有这句话。这是真实模型跑出问题后加的，见下面。
- **结果说在回显区**：挂上几条、没挂上几条、看不懂几行，以及是哪个 buffer。目标 buffer 在回答到达前被关掉时，说"要批注的 buffer 不在了"，不报错，回答仍在对话里。

## Alternatives considered

**flymake。** 用户明确说不用。

**做成一个技能。** 没选：技能改的是"模型按什么身份回答"，这里改的是"回答去哪里"；做成技能会走切换对话模式那条路。

**把回答从对话里隐藏，只留一行"已挂上 N 条"。** 没做：记录里无论如何存着模型的原文，没挂上的行留在对话里正好能看到。要不要隐藏是另一个界面上的决定。

## Acceptance criteria

`scripts/annotate-chat-regression.el`，15 个测试，都真的在一段对话里发消息，读脚本模型收到的请求和 buffer 上挂了什么：

- 回答挂在叫出对话的 buffer 上；请求里有带行号的原文、上一轮的问答、你所在的位置，没有 `>annotate` 这个标记，没有工具；格式要求在系统提示的最后；原文和"已修改"状态不变；回答仍显示在对话里。
- 下一条消息是普通消息：没有格式要求，没有带行号的原文，工具回来了。
- 只写 `>annotate` 时用默认指令。
- 后面写 buffer 名或加引号的文件名时，挂到那个 buffer 上；不是名字的词留在消息里；加了引号却找不到时不发请求。
- Superchat 自己发的消息不认这个标记；标记必须独立成词；开头的命令优先。
- 代理技能生效时：格式要求排在人设之后，没有工具，对话的模式没变。
- 目标 buffer 被关掉时说出来、不报错；什么都没挂上时说出来；再要一次换掉旧的。
- 下一条普通消息被告知之前的回答已经挂到哪个 buffer 上，历史里那一条带着标记和目标名；没批注过的对话没有这句话。
- "重新生成"会重新批注；"编辑上一条"把带标记的文字放回输入栏。

对新代码做了 25 处变异（解析 6、分发 9、去向 4、收集器 6），全部被发现。

## 真实模型经过对话的结果

沙箱 Emacs、替身用户，场景 ANH（在 `.scratch` 下的测试台里，不受版本管理）：从一份 15 行的周会纪要叫出对话，连发三条——先问"决定一节有哪几条和问题一节对不上"，再发"把你刚才说的这些问题标到纪要上 `>annotate`"，最后发"只回答两个字：你好"。

**第一批，加"那件事做完了"这句话之前：**

| | 批注那一条 | 下一条普通消息 |
|---|---|---|
| DeepSeek，3 遍 | 挂上 2、6、5 条，行号全部正好对，没有挂不上或看不懂的 | 2 遍回答"你好"；**1 遍没有回答，而是用编辑工具把意见写进了纪要**（buffer 被改，未保存） |
| 本地 Qwen，关掉思考，1 遍 | 挂上 4 条，行号全对，67 秒 | 回答"你好" |
| 本地 Qwen，开着思考，1 遍 | 挂上 3 条，行号全对，279 秒 | 回答"你好" |

出问题的那一遍里，历史上一条存的是去掉标记后的"把这些问题标到纪要上"，后面跟着两行 `行号 | 引用 | 意见`，没有任何地方说这两行已经挂到纪要上了。下一轮的模型手里有编辑工具，就自己去"标"了。这是从那一遍的请求和回答读出来的推论，没有单独验证。

**第二批，记录里留着标记、之后的消息被告知"已做完"之后：**

| | 批注那一条 | 下一条普通消息 |
|---|---|---|
| DeepSeek，5 遍 | 挂上 9、8、11、7、7 条，行号全部正好对，没有挂不上或看不懂的 | 5 遍都回答"你好"，原文没有被改 |
| 本地 Qwen，关掉思考，1 遍 | 挂上 3 条，行号全对，49 秒 | 回答"你好" |

每一遍里，批注那一条的请求都带着上一轮的问题、带行号的原文和格式要求，没有 `>annotate` 这个标记；意见的内容接着上一轮的讨论。

这些数字能说明和不能说明的：

- 修之前 3 遍里出 1 次，修之后 5 遍里 0 次。样本很小，只能说没有再看到，不能说不会再发生。
- 本地 Qwen 开着思考的那一遍没有撞到 8192 的上下文上限（纪要短），所以"上下文用完时明说没有批注"这条路在对话里没有被真实模型走到；它只有命令那边的真实运行和这里的脚本测试作证。
- 只测了一份 15 行的纪要。代码材料、长文件、对话已经很长的情况都没有测。

## 没有解决的

- **"那件事做完了"这句话只记在当前这个 Emacs 里。** 重启之后，历史里还有带 `>annotate` 的那一条和它的几行回答，但后面的消息不再被告知它们已经挂过；挂上的批注本身也不会在重启后留下。
- 回答的原文留在对话里，也进入之后的历史。
- 补全里 `>` 的候选还没有 `annotate`。
- 一次只批注一个 buffer，批注整个 buffer。
- gptel-annotate 的"模型给出替换文字、一键接受"和"保留多轮批注来回切换"没有做。前者会改文件，应该走改写的审阅路径。
- 没有真人在键盘前用过。
