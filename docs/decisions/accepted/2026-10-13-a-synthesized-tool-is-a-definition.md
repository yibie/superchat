# Decision: 模型自己写的工具，存下来的是定义

Status: accepted 2026-10-13, implemented（切片 8c）。五条裁决是用户同意的（leader 转达，`reports/guidance-2026-10-11/SLICE-8.md`）；方案里的四个问题用户逐条答了，记在各节。来源是 2026-10-13 的架构走查（`reports/architecture-map-2026-10-13/CONTRADICTIONS.md`）的 C1、C2、C3、C4、C5、C7。

证据的范围：脚本模型，批处理 Emacs。没有真实模型，没有真人，没有读过也没有动过用户真实数据目录里的那两个文件的内容（只数过条数：14 个工具，20 行账本，全是 `approved`）。

## 出了什么事

2026-10-11，一个用 `define_tool` 写的工具在后来的一次执行里被批准并调用，返回的是 `[Tool call blocked: Run is no longer active]`，Tape 上却记成成功。原因（读代码确认）：登记表里存的是**已经被当时那次执行包装过**的工具。包装里带着那次执行的编号和"它还活着吗"的判断；执行结束后再调，里层拒绝，外层把拒绝的文字当成返回值，记成成功。

好比把一张只在当天有效的门禁卡存进抽屉。第二天拿出来刷不开，系统却记了一笔"刷卡成功"。

同一次走查还查出：登记表说是"按 Session"，实际是整个 Emacs 一张；账本对每个定义都写"用户已审过"，不管当时有没有问过人；给模型和用户的文字说"每次调用都会问"，而放开的档位下并不问；子 agent 的定义说是"随请求结束"，实际改掉的是全局的函数。

## 1. 存的是定义，每次执行现场包装

- 登记表（`superchat-synthesis--table`）里的每一项是 `(:name :description :args :body :key)`，没有任何可以调用的东西。
- 每次请求收集工具时，`superchat-synthesis-tools` 从定义现做出未包装的工具，请求再用**自己的**包装器包一层——和内置工具走的是同一条路（`superchat-llm.el` 里那句 `(mapcar wrap-fn tools)`）。所以执行 A 里写的工具，在执行 B 里带的是 B 的编号和 B 的活性判断。
- 正在进行的那次请求里，照旧把包装好的工具注入进去，"下一步就能用"不变。
- 函数体不再绑到全局符号 `superchat-syn--NAME` 上，每次从定义现做一个函数。两个 Workspace 可以各有一个同名工具，后写的改不了先写的。

## 2. 属于谁

- 钥匙是 Workspace 的编号。两个读取点（挑名字的 `superchat--select-tools-adjust-names`、做工具的 `superchat--collect-llm-tools`）都按"这次请求的对话属于哪个 Workspace"取，取不到 Workspace 时读对话自己的记录。
- **临时对话（用户裁定）**：工具只属于那一段对话，只在内存里，从不写进磁盘，账本文件里也没有它。Tape 上仍有一条事实。
- "哪些名字是模型写的"（`superchat--syn-names`）仍是整个 Emacs 一份：权限判断读它，而这个性质在哪个 Workspace 都成立。
- **子 agent**：它的定义只进它自己那次请求，哪里都不存。它想用的名字若已被某段对话持有，直接拒绝，什么都不改。它自己的新名字记在那次请求名下，请求结束时忘掉（`superchat-synthesis-forget-request`，在请求循环收尾处调用）。
- `superchat-synthesis-reset` 清的是这个 Emacs 里所有 Workspace 的，说明文字照实写了。磁盘不动。

## 3. 账本写实际发生的事

- 管道在"问了、答了允许"那条分支上，给执行上下文加 `:admitted-by asked`。`define_tool` 读它。合成模块不自己重算权限规则。
- 账本一行：`(HASH . (:name :state :how :at))`。
  - `approved`：有人看过。`:how asked`（定义时被问到并允许）或 `:how review`（在复核里批准）。
  - `admitted`：档位放行，没有人看。`:how level`。`danger-full-access` 和 `auto` 都是这一种。
  - `rejected`、`deleted`：在复核里拒绝、删除。
- Tape 上仍是 `synthesis.approval.decided`。`admitted` 时 `actor-id` 不再是 `user`。
- **重启后（用户裁定）**：只加载 `approved` 且写明了 `:how`、条目写明了 Workspace 的。其余的不加载，也不在启动时问，列在 `superchat-pending` 里，每个工具一行，`RET` 进入对这一个工具的复核。
- 限度："问了人"在代码里的意思是"走了审批口并得到允许"。如果将来有插件在审批口上自动代答，这里仍会写 `asked`。仓库里现在没有这样的插件。

## 4. 措辞

- 给模型的工具说明、定义成功后回给模型的话、复核界面：不再说"每次调用都会问"，改成"每次调用按这段对话的权限档位放行"。
- 删掉"没有工具写得到账本"的说法。实话是：账本单独放一个文件，只为了普通的数据库写入碰不到它；有完全控制权的工具（`eval_elisp`、shell、自写工具）写得到它，和写得到任何文件一样。
- "Session-scoped""self-confirms"这些不实的文档串改掉了。
- README 权限表里"`edit-buffers` 下每次都问"那一行是对的，没有动。README 加了一段讲自写工具的归属、账本和复核。

## 5. 里层被挡下，外层算失败（用户裁定：窄的做法）

- 一次调用在"执行已不再活着 / 工具已不可用"那道门被挡下时，如果它正处在另一次**同步**工具调用的函数体里，就在外层留下原因；外层收尾时按失败处理：`tool.failed`，模型读到 `[Tool call failed: a call it made to X was refused: …]`。
- 不靠比对返回值的文字。
- 不管权限拒绝：自己会发起调用的工具（如 `elisp_script`）内层被权限拒绝时，仍然把拒绝的文字交给脚本自己处理。
- 不管异步工具，也不管函数体把调用推到定时器里的情况。
- 第 1 条做完后，登记表已经造不出"包了两层"；这一条是给别的来路留的。

## 6. 磁盘上原有的文件（用户裁定：A，并要求能顺手清理）

旧版本存的条目没有写 Workspace，旧账本的 `approved` 在任何档位下都会写，分不清有没有人看过。

- 第一次加载时**一个都不加载**，也**不改写、不删除**任何文件。每个旧工具在 `superchat-pending` 里一行。
- 复核界面（`superchat-tools-review-synthesized`）逐个决定：
  - 批准：进入发起复核的那段对话所在的 Workspace；不在任何 Workspace 的对话里时，问一个目录。存储里那一条写上 Workspace，账本记 `approved` / `review`，立即加载。
  - 拒绝：账本记 `rejected`。存储里那一条留着，供人读。
  - 删除：只把这一条从 `synthesized-tools.el` 里拿掉，账本里它那一行标成 `deleted`。别的文件、别的条目都不动。同一份定义以后再出现在存储里（例如从别的机器同步来），也不会回到表里。
  - 跳过：什么都不写。
- 哈希的算法没变（不含 Workspace），旧哈希仍然对得上。
- 对用户的代价：升级后那 14 个工具都不能用，直到逐个看过。
