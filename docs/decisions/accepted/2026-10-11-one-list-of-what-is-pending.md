# Decision: 一张表，列出 Superchat 正在做什么、在等什么

Status: accepted — 用户，2026-10-11。架构研究（`reports/architecture-options-2026-10-11/`，方向 A 的第一步）和第三轮评审（结构建议 5）都建议做它。我问用户："'一张表'要不要进产品范围？我建议要，先只做读现有数据的那一步，不改任何请求。"用户答："agree with you, just do it." "实现中定下的几点"是实现时定的，随本次向用户报告，用户可以改。

## Problem

"谁在做什么、在等什么"分散在四个地方：工作记录列表、模式行通知的列表、未保存改动的列表、以及各段对话里的说明。研究报告数过：找回一件到点醒来的工作，要 3 条命令、看 4 个界面。还有两种状态在任何列表里都看不到：

- 到点了却没启动的定时任务；
- 说不清有没有启动过的定时任务（对话里有一句说明，别处没有）。

用户也没有任何命令能列出定时器，只有模型有 `timer_list`。

## Decision

新命令 `M-x superchat-pending`，一张表，一行一件事，按"最需要你的在前"排：

| 这一行叫什么 | 它是什么 | 从哪里读 |
|---|---|---|
| Running | 正在跑的执行，写明是你发起的，还是 Superchat 自己开始的（哪个定时任务、哪条工作记录） | Runtime 的活动执行；发起者从那段对话的 Tape 读 |
| Waiting for you | 等你回答的工作记录，带它问的话 | 工作记录的事实 |
| Due, not started | 到点了没被接手的工作记录；到点了没启动的定时任务 | 工作记录和定时器的事实 |
| May have started | 说不清有没有启动的定时任务 | 定时器的事实 |
| Ended, not looked at | Superchat 自己开始、已经结束、你还没看的执行 | 模式行通知的那份名单 |
| Unsaved | 工具改过、还没保存的 buffer | buffer 上的标记 |
| Can be continued | 可以继续的工作记录；上一次执行被打断的会写明 | 工作记录的事实 |
| Waiting for a time | 等某个时间的工作记录 | 工作记录的事实 |
| Waiting | 等别的东西的工作记录 | 工作记录的事实 |
| Scheduled | 还没到点的定时器 | 定时器的事实 |

按键：`RET` 去那段对话（未保存的行去那个 buffer），`v` 看工作记录全文，`k` 停掉一个正在跑的执行（会先问），`d` 清掉一条"已结束没看"，`g` 重读。

**它只读，不写。** 表里没有一条是新的事实：每一行都从别的模块已经保存的东西里读出来。它不是任务队列，不调度任何东西，不新增 Tape 事实，也不改任何请求。

## 实现中定下的几点

- **"可能已启动"照定时器模块自己的规则判。** "正在发送"这笔记录是发送之前写的，发送失败后它还在。所以只有"发送途中，并且那段对话之后确实开始过一次执行"才算说不清；只是发送失败的算"到点没启动"。第一版我只看了"正在发送"，测试当场发现它把每一次失败的启动都说成"可能已启动"。
- **已经判定为说不清的任务只列最近 7 天的**（`superchat-pending-unconfirmed-days`）。它们没有"看过了"这种事实可记，不设期限就永远留在表里。
- **从表里去一条"已结束没看"的对话，就算看过了**，那条通知随之清掉，和通知列表里按 `RET` 一样。**更正（复审的 FR-07）：** 最初的实现先清通知再找对话，对话打不开时通知已经没了，和通知列表的顺序相反。现在先到对话，到了才清。
- **`k` 只对正在跑的执行有效**，别的行会报错。保存、完成记录、取消定时器没有做成表里的按键：这些操作各有自己的命令和确认方式。
- **没有新增插件行。** 命令靠 autoload 标记接进包里；**更正（2026-10-11，复审的 FR-03）：** 这只对包管理器安装成立，而且"和批注一样"说错了，批注是由 `inline-rewrite` 行加载的。用 `-L` 加 `(require 'superchat)` 的开发装法下命令原来不存在。现在 `superchat.el` 为它写了 `autoload`（顺带补上同样漏掉的 `superchat-sessions` 和 `superchat-session-history`），`scripts/command-load-regression.el` 钉住；M3 回归集钉着插件名单，那个文件我不能改。
- **新增一个只读函数** `superchat-timer-unconfirmed-tasks`，列出有 `timer.unconfirmed` 事实的到点任务。
- 审批问题没有进表：今天它们没有登记在任何地方，只是小缓冲区里一个正在问的问题（研究报告的方向 D）。
  **更正（2026-10-11，复审的 FR-04）：** "没有登记在任何地方"不属实。运行时知道一次执行正在等人回答（审批或 `ask_user` 的问题），记录里也有 `approval.requested`。现在这样的执行在表里单列一类 **Asks you now**，排在最前，写明"等你回答"；答完它回到 Running。

## Alternatives considered

**把这些状态存成一张持久的表。** 没选：那就成了第二份事实，会和 Tape 对不上。评审和研究都明确说不要新建任务队列。

**先改请求，把"谁发起的"记在执行上（方向 A 的第二步），再做表。** 没选作第一步：先看只读现有数据能不能让用户回答"谁改了什么、在等什么、怎么停、怎么继续"。答不出来，才知道缺的是事实还是界面。

**把这些行加进现有的工作记录列表。** 没选：定时器、未保存的 buffer、正在跑的执行都不是工作记录。

## Acceptance criteria

`scripts/pending-regression.el`，12 个测试。每一类行都照产品自己的方式造出来（真的发消息给脚本模型、真的让定时器到点、真的让工具改 buffer），再在汇总里找：

- 等用户的记录：带目标和它问的话，指向它所在的对话。
- 等时间的记录：到点之前是"等时间"，到点而没人接手之后是"到点没启动"。
- 完成的记录不在表里。
- 还没到点的定时器在表里；到点而发送失败的任务是"到点没启动"，不是"可能已启动"。
- 发送途中那段对话里又开始了一次执行：是"可能已启动"。
- 产品写下"说不清"事实的任务：是"可能已启动"；超过 7 天不再列。
- 正在跑的执行：写明"是你发起的"；结束后不在表里。
- Superchat 自己开始并已结束的执行：在表里；从表里去它的对话后，通知清掉，行也没了。
- 工具改过的未保存 buffer 在表里；不再是未保存（不管怎么变的）就不在；保存后不在。
- 顺序：先造"可继续"的、后造"等用户"的，表里仍是"等用户"在前。
- 读这张表不往 Tape 写任何东西。
- 表格界面：行里有类别、目标和问的话；`RET` 去到那段对话；对不是执行的行按 `k` 报错。

## Evidence

- 变异测试：改坏 14 处。第一轮发现 11 处；补了两处断言（"标记还在但已不是未保存"、"按相反顺序造数据"）后发现 13 处。剩下 1 处没有被发现："已结束但还保留着停止控制的执行不算在跑"这道判断，测试里造不出那种执行。
- 这些测试在旧代码上加载不了（旧代码没有这个文件），所以"旧代码上会红"在这里不是证据；管用的是变异测试。
- 没有用真实模型跑，也不需要：这张表不发任何请求。
- **没有真人用过。** 列宽、行的措辞、在真实的 Emacs 窗口里好不好读，都没有人看过。这一步本来就是为了让用户看着这张表回答上手清单最后的四个问题。

## 没有解决的

- 每次刷新要读一遍工作记录和定时器的事实，并对每个正在跑的执行回放一次它的对话。对话很长时的耗时没有量。
- 表不会自己刷新，要按 `g`。
- 审批问题现在在表里（见上面的更正），但只说"哪次执行在等你回答"，不显示问题本身的文字；回答仍然要到提问的地方去。
- "谁发起的"仍然靠回放对话来判断，没有记在执行自己身上（方向 A 的第二步）。
- 临时对话里的东西和别的一样列出，没有另外标明。
- **更正（复审的 FR-06）：** 子代理的执行原来写成"你发起的"。现在凡是由另一次执行发起的，写成"started by execution <那次执行的编号>"。
- **更正（复审的 FR-05）：** 一条记录正在被某次执行做着的时候（被唤醒后的那段对话里有执行在跑，或者有执行在跑的对话的当前记录是它），原来同时又被列成"Can be continued"。现在这段时间里它只出现在那次执行的行里，执行结束后再按它的状态列出。
