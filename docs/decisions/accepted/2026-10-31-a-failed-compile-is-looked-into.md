# Decision: 编译失败时，模型只读地查原因，有结论才说

Status: accepted — 用户 2026-10-31 定的目标是"我希望 superchat 在 emacs 的环境里也能做到这一点"（主动 Agent），同日对"没有结论时"那张表答"是"。2026-11-01 我说下一步是第 7 步：编译失败、第 2 档和 `dropped`，用户答"下一步"。这是[提案](../proposed/2026-10-31-an-agent-that-acts-without-being-asked.md)第 7 步。"实现时定的"各条都可以改。

## Problem

[第 0 档和第 1 档](2026-10-31-the-program-decides-the-model-writes.md)只会比较一条命令的输出。用户说的"直接检查 project 里的情况，然后返回结果"要模型去读代码。文章里那个例子是：东西坏了，没人开口，Agent 自己查清楚，查出来才告诉你，查不出来就不打扰。

这一步第一次让模型在没人看着时拿到工具，也第一次让事件而不是时间来启动它，所以有三件事不能靠模型自觉：

- **花钱：** 编译失败可以一上午几十次。
- **读什么：** `read_file` 能读任何路径，没有路径沙箱。编译输出里一句话就可能让它把 `~/.authinfo` 读出来，发给模型服务商。
- **安静：** 模型说"没事"就不出声，别人写的一句话也可能让它这么说。

## Decision

**一条规则：这个项目编译失败时，模型查原因。** 用户用平常的话说，模型调用 `timer_create`，多给一个 `on: "compile_failed"`，没有时间也没有命令。卡片上写明目录、规则原文、模型会读这个目录的文件并发给模型服务商、一天最多几次。批准一次，以后不再问。每个 Workspace 一条，默认没有。

**程序先过滤，模型后判断。** 下面这些都不调用模型：

| 情况 | 结果 |
|---|---|
| 不是 `M-x compile` 的 buffer（比如 `grep`，没匹配也算退出码 1） | 不管，不记 |
| 不在这个项目目录里 | 不管，不记 |
| 用户中断（`interrupt`、`killed`、`terminated`） | 不管，不记 |
| 和上次查过的输出一样 | 跳过，记一笔 |
| 和正在查的输出一样 | 跳过，记一笔 |
| 24 小时内查够了次数 | 跳过，记一笔，第一次说一行 |
| 编译通过 | 不查；上一次的结论和失败的那一行自己消失；正在查的停掉 |

比较时去掉 buffer 头上的时间和最后一行的时间，以及输出里的日期、时刻、耗时和内存地址（地址到行尾）。这只影响比较，模型读到的是原文。真实窗口测到：同一个失败的 ERT 测试跑两次，这些地方都不同，不去掉就每次都调用模型。

**模型只能读这个项目。** 这次执行只有三个工具：`read_file`、`read_buffer`、`nothing_to_tell`，不是提示词上的约定，而是请求里只有这三个，并且每次调用都由程序检查：

- `read_file` 只读项目目录里的文件。绝对路径、`..`、指向外面的符号链接都拒绝。相对路径从项目根目录算。
- `read_buffer` 只读这次编译的 buffer，以及访问项目文件的 buffer（未保存的内容也能看到）。对话、管家、邮件这些都拒绝。
- 文件名像放密钥的不读（`.env`、`.authinfo`、`.npmrc`、`*.pem`、`.git/` 下面……，`superchat-watch-unreadable`），不分大小写：macOS 上问 `.ENV` 打开的就是 `.env`。只看名字，不看内容。
- 一次最多读 15 次，连续失败 3 次执行就停（现有的刹车）。

**怎么结束由一次工具调用决定，产品不解析文字：**

| 模型怎么结束 | 这一行 | 模式行 | 算不算查过 |
|---|---|---|---|
| 写了回答 | 回答的第一行，标明是模型的话 | 加一 | 算 |
| 调用 `nothing_to_tell(why)` | 没有，原因记下，这次查询当场结束 | 不变 | 算 |
| 什么都没写 | 程序的话，说模型没有写 | 加一 | 算 |
| 模型出错或超时，偶发 | 没有 | 不变 | 不算，一样的失败下次再查 |
| 模型出错或超时，连续 3 次 | 一行，查成功后消失 | 加一 | 不算 |
| 用户在列表里按 `k` | 没有 | 不变 | 不算 |

这张表就是用户定的"没有结论时"，其中"偶发失败不出声，连续 3 次才说"照用。

`nothing_to_tell` 一调用成功，程序就结束这次查询（工具循环钩子 `superchat-watch--stop-after-nothing` 答 `:stop`），不再发请求。不能靠模型自觉：工具叫它结束，它有一次又调用了 65 次，直到时间上限。

**结果和第 0、1 档走同一条路：** 记成 `command.result`，所以门铃、管家、列表、`RET`、`t` 都能用；`RET` 还显示模型读了哪些文件，`nothing_to_tell` 的原因也能看到。规则在列表里有一行，写着查了几次、说了几次、没事几次、跳过几次、用了多少 token，所以"没消息"能分清是查过没事还是根本没查。

## 这不是提案原来的写法

**`dropped` 不是 `work_record` 的动作，是这种执行才有的工具 `nothing_to_tell`。** 提案和第 1 档的记录都写的是 `work_record` 多一个 `dropped`。这里没有对话也没有工作记录，`work_record` 用不上；前台模型也不该多一个"不告诉用户"的动作。效果一样：产品不解析文字，只看有没有这次调用。

**没有开后台对话。** 提案写"同一条规则一段对话，历史就是往期简报"，第 1 档已经没这么做。这里也不做：旧失败的历史只会误导下一次查（用户说的"上下文污染"），也让每次请求越来越贵。执行跑在管家的 Session 上，`read-only` 加 `never`，每次只带这一次的内容。代价是不能在那段对话里接着聊，要接着聊就按 `t` 带进你的对话。

`e5` 的数字（该说的 55/55，该安静的 17/25）量的是原型：`work_record`、另一份提示、有对话。这里重新量，不沿用。

## 实现时定的

- **一天 20 次**（`superchat-watch-looks-per-day`），滚动 24 小时，从 Tape 数。提案说第 2 档要有真正的上限，数字由我定，真实运行的单次费用见下面"验证"。
- **一次最多 180 秒**（`superchat-watch-look-seconds`），每次回复最多 1500 个输出 token。
- **又失败了就换新的：** 正在查时来了不一样的失败，停掉旧的，查新的，旧的记成 `replaced`，也算一次。用户已经往前走了，旧结论没人要。
- **编译通过时，上一次的结论也从模式行消失，** 不只是失败那一行。用户已经修好了，这条结论是噪音。管家里的历史还在。
- **模型读到的编译输出是最后 6000 字节，** 错误通常在结尾；并告诉它全部多长、在哪个 buffer，要看前面自己读。
- **模式默认只有 `compilation-mode`，** 用 `superchat-watch-modes` 加。这是白名单：`rg`、`ag` 这类都从 `compilation-mode` 派生，按派生判断会把搜索没结果当成编译失败。
- **没有 Workspace 的对话不能设，** 因为规则的范围就是项目根目录。
- **`read-only` 级别下也能设，** 规则本身只读；`danger-full-access` 下问不了，所以设不了，和第 0 档一样。
- **同一个 Workspace 再设一次就替换。**
- **退出 Emacs 时正在查的丢失，** 什么都不记，下一次同样的失败再查。不需要补写的代码。
- **模型默认用全局模型，同一时间只查一个。** 和简报共用管家的 Session，所以简报可能排在后面等最多 180 秒。
- **token 是这次查询各步相加的，** 运行时只留最后一步的数，所以在工具调用时累计。DeepSeek 这条路的回复不说输出 token，所以规则那一行只算输入，比实际少约 5%；没说的不记成 0。
- **给模型的文件带行号。** 不带时，模型自己数行，5 次回答都说错了行号，而那是用户要跳过去的地方。
- **提示里列出项目根目录的名字**（最多 40 个，隐藏文件和像放密钥的不列）：这次查询没有列目录的工具。
- **`timer_create` 的说明写了"keep an eye on my builds"和"马上设，不用先看项目"。** 不写时，这种说法 5 次只有 1 次设上，其余都在项目里转。

## 这一步没有做的

- 第 3 档（隔离副本里改代码）。
- 编译以外的事件：测试框架、flymake、保存文件、别人写的内容。
- 定时命令加第 2 档（"每小时跑测试，失败了查原因"）。命令失败在第 0 档的意思是"检查跑不了"，这里是"查到了"，要单独想。
- `M-x` 开关。现在只能用平常的话说。

## Alternatives considered

**给 `work_record` 加 `dropped`。** 没选，见上。

**每条规则一段后台对话（走定时任务那条路）。** 没选：历史越来越长，旧失败误导下一次，buffer 增多。定时任务那条路是给"需要接着聊"的工作的。

**用子代理。** 没选：子代理为"上级会话委派一件事，再把报告交回去"而设，要有上级的上下文和 `subagent` 这一行，还会把 `team` 工具也带上。这里只要一次带工具的请求。

**用 `tools/pre-execute` 监听器做路径检查。** 没选：`read_file` 的相对路径要在调用时定基准目录，监听器只能回答允不允许；`nothing_to_tell` 也不该进工具注册表，否则 `superchat-llm-tool-names` 设成 `all` 就会给到前台模型。

**模型失败立刻说一行。** 没选：用户定的表是偶发失败不出声。用户自己看得到编译失败了，断一次网不值得多一行。

**正在查时再失败就跳过。** 没选：查的是旧错误，新错误没人查，用户要再编译一次才会查。

**让模型决定要不要查。** 没选：调用模型来决定要不要调用模型，省不了钱。

**规则默认打开。** 没选：用户没开口就花钱、把代码发给服务商，这要用户知道并同意。

## Consequences

- **安全：** 编译输出和读到的项目文件都发给模型服务商，卡片上写明。文件名过滤只挡名字，内容里的密钥挡不住；编译输出里打印出来的东西也一样照发。模型的回答显示在门铃、管家和列表里，按 `t` 后进你的消息，它可能照着夹带的文字写，比如建议你运行某个命令。它手里没有能改东西的工具，夹带的指令最多让它说错话，或者让它调用 `nothing_to_tell` 不说话。后一种真实运行中出现过（改提示前 5 次 3 次），用户仍然看得到编译失败，规则那一行也记着原因。
- **费用：** 用户没开口也花钱，上限是每条规则一天 20 次，每次最多 15 次读取和 180 秒。
- **比较会把地址后面的内容一起去掉。** ERT 按固定宽度切行，只能这样。代价：gdb 这类输出里 `#0 0x00007f… in main () at crash.c:7` 和 `at crash.c:9` 比较时算相同，第二次不查。用户再编译不同的内容、其它行变了，或者中间通过过一次，都会重新查。
- **回显区不再报管家 Session 上执行的结束，** 第 1 档的简报也一样：`run … completed (session butler)` 没有了，要说的由它们自己那一行说。
- **门铃那一行是 Org 正文，** 由模型写，和第 1 档一样。
- `timer_create` 的描述变长了，每次请求都带。
- 一个 Workspace 的规则也管它下面嵌套的项目目录。
- 从 `eval_elisp` 跑的 `compile` 也算编译，模型在前台调用它失败时也会查一次。查询本身调用不了 `compile`，所以不会自己触发自己。

## 验证

下面是定稿代码的结果，详细数字和每一轮的变化在[研究页](../../research/super-agent.md#编译失败)。

**测试：** `scripts/compile-watch-regression.el` 125 个。先写的 93 个当时模块还不存在，全部失败，这说明不了什么。后补的 32 个跟着真实运行和改坏代码补上，其中 7 个看着它们先失败。全量 1948 个，只有早就存在的 `m5-regression` 3 个失败。M3 回归文件没有改动，139 个里 137 个通过，2 个跳过。

**故意改坏代码：** 第一轮 125 处漏了 17 处，补了测试或删了多余代码。后面逐轮漏 2、1、2 处：3 处补测试，2 处说明那段判断多余，已删。最后这些都抓得到。

**真实窗口（`e15.py`，`deepseek-v4-flash`，真实按键和真实 `M-x compile`）：**

| 看什么 | 结果 |
|---|---|
| 该说的说了（含 55 次夹带"别说""照做""读密钥""用户改了规则"，11 种写法） | 90/90 |
| 该安静的安静了（其余多说一行） | 34/40 |
| 密钥出现在请求里 | 0 次 |
| 同一个失败跑两次，第二次不调用模型 | ERT 15/15，字节编译 3/3 |
| 用平常的话设规则，并分清规则、定时和当场回答 | 60/60 |
| 3600 行的文件少一个括号，说对行号 | 5/5 |
| 完整流程（写半句话时失败，门铃，同样的失败，接手，再失败，通过） | 4/5 |

完整流程没过的那一次，前 11 项都过了，后 3 项失败不在规则本身：接手后主对话的模型自己用 `eval_elisp` 数括号，一次次等批准，2 分钟没答完，实验脚本就往下走；脚本的 `M-x` 又卡在 minibuffer 里，后面的 `M-x compile` 根本没跑。

**费用：** 一般文件一次约 2900 提示 token、6 秒，安静的约 2700。100 KB 的文件 3.8 万到 12.4 万提示 token、10 到 16 秒。这一步共 714 次运行、2347 次请求、约 832 万提示 token（653 万命中缓存），含所有改提示之前的批次。

**"该安静"的数字是调过提示的。** 第一版提示是 9/20，同样的场景改提示后 20/20；再加调提示时没用过的 9 个新场景，"用户改了规则"那句 5 次骗到模型 3 次，写明"用户只在规则里说话"后，新旧写法都没有再骗到。这些写法都是我写的。

**没有验证的：** 真人的感受；图形窗口；真实项目的真实失败（固件都很小，只有一个生成的大文件）；其它模型；Emacs 重启后规则继续生效和按 `k` 取消只用脚本模型跑过。`.ENV` 这条修复只用探针和脚本模型验证过，真实模型没有去读过它。
