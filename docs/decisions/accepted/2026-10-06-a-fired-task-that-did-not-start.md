# Decision: 到点却没跑起来的工作，要么稍后启动一次，要么明说不知道

Status: accepted — 用户，2026-10-06：对上一片报告里"还没解决的"几项回答"将【还没解决的】解决掉"。用户定的是"这几项要解决"；下面"实现中定下的几点"里的具体数值和做法是实现时定的机制，随本次向用户报告，用户可以改。

## Problem

上一片（`2026-10-06` 的 "A wake that goes wrong"）修了工作记录的唤醒，留下三件事：

1. **定时器任务有同样的窗口。** `superchat-timer-fire` 先写 `timer.fired` 再发送。发送失败，或 Emacs 在两者之间退出，这次到点就算"已触发"，再没有东西会发现它没跑。
2. **不重启就不会重试。** 工作记录的唤醒发送失败后，等待被补回，但只有下次挂载（通常是下次启动）才重扫；这期间记录一直显示"在等一个已经过去的时间"。
3. **执行到一半 Emacs 退出。** 被唤醒的记录已经开始执行，Emacs 退出；重启后主对话里没有回报，记录上看不出被打断过。

查代码时还发现第四件：对话里正有执行在跑时，定时器任务的消息只进了内存里的排队队列，却照样被记成"已启动"。

## Decision

1. **定时器任务把"发送"和"启动"都记到 Tape 上。** 发送前写 `timer.sending`，发送后确认有新的 Run 开始才写 `timer.started`（带 Run 编号）。任务算"启动了"只看 `timer.started`。
2. **有 `timer.fired`、没有 `timer.started` 的任务稍后再启动。** 当场失败的，过一会儿重试；Emacs 退出造成的，下次启动时先处理。同一次到点仍然只有一条 `timer.fired`。
3. **说不清的不重跑。** 重启后看到某任务有 `timer.sending`、没有 `timer.started`，而那段对话在这之后有 Run 开始过：这个 Run 可能就是它。这时写 `timer.unconfirmed`，在对话里留一句"无法确认是否启动过，没有再次启动"，不再发送。没有 Run 开始过的，可以确定没跑，照常再启动。
4. **对话正忙时不发送。** 那段对话里有执行在跑，任务就等着（不写 `timer.sending`、不排队），稍后再试；这不算一次失败。
5. **已触发、还没启动的任务可以取消。** `superchat-timer-cancel`（以及模型的取消工具）对它生效，之后不再重试。
6. **工作记录的唤醒失败后，同一个 Emacs 里也会重试。**
7. **被打断的唤醒执行：记一笔、说一声、不重跑。** 重启后的扫描发现某次唤醒的对话里有 Run 开始过、这个 Emacs 不认识它、主对话没被告知过：
   - Run 在 Tape 上没有正常结束的，给记录写结果 `interrupted`，主对话留一句"那次执行在 Emacs 退出时被打断，没有再次启动"；
   - Run 其实正常结束了、只是没来得及回报的，只补那句回报。
   之后模型看到这条记录时，会看到一句"上次执行被打断，先检查它留下了什么"。
8. **不变的**：不引入持久任务队列或新的调度器；提醒（reminder）不受影响；普通的"可继续"记录仍不自动续跑；外部副作用不承诺"恰好执行一次"。

验收：`scripts/timer-start-fault-regression.el`、`scripts/work-wake-fault-regression.el`。

## 实现中定下的几点

- 重试间隔和次数：失败后 300 秒重试，一个 Emacs 里最多自动重试 3 次（`superchat-timer-retry-seconds`/`-limit`，`superchat-work-wake-retry-seconds`/`-limit`）；超过后留给下次启动。对话忙时 30 秒后再看，不限次数（`superchat-timer-busy-retry-seconds`）。
- 重试计数只在内存里，重启清零：持久的只有事实，计数只是为了不在一个坏掉的环境里无限重试。
- 只有新写的 `timer.fired`（带 `awaits-start`）才参与"没启动就重试"。这次改动之前写下的 `timer.fired` 没有这个标记，一律不动，避免升级后把很久以前的任务重跑一遍。
- 发送失败时，已经插进输入区的任务文字会被删掉，下一次重试不会重复。
- "这个 Emacs 不认识那个 Run"用 `superchat-runtime-status` 返回 nil 判断；正在跑的执行不会被当成被打断的。

## Alternatives considered

**持久任务队列。** 没选：现有的事实（`timer.fired`、`work.woken`、`run.started`）加上两三个新事实已经够回答"启动了没有"，不需要第二套要保持一致的存储。

**说不清时重跑一次。** 没选：任务可能已经改了文件或发了消息，重跑是把"不知道"当成"没执行过"。

**对话忙时照旧排队。** 没选：排队只在内存里，Emacs 退出就丢，而且会被记成已启动。

**自动续跑被打断的执行。** 没选：用户已经决定不自动续跑；被打断的执行可能留下了一半的改动，应由人或下一次明确的请求来接。

## Consequences

- Tape 多了三种事实：`timer.sending`、`timer.started`、`timer.unconfirmed`；工作记录多了一种结果 `interrupted`。
- 定时器任务在对话忙时会晚一点启动，而不是排队。
- 没有覆盖的地方：没有用真实模型跑过；"Emacs 中途退出"是用"不执行发送"和手写事实模拟的，没有真的杀进程；执行被打断后 buffer 里留下的未保存改动不在这次范围内（属于第 4 步）。
