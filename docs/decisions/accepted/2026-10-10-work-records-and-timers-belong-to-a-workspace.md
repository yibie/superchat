# Decision: 模型只能碰本 Workspace 的工作记录和定时器

Status: accepted — 用户，2026-10-10。架构复查（`reports/architecture-review-main-2026-10-10/`）的 F1、F2 两项在当天的代码上重跑仍然复现。我向用户提了三点建议：一、别的 Workspace 的模型碰这些对象时明确拒绝并说明"属于另一个 Workspace"，不假装它不存在；二、用户自己打开的全局列表保留；三、不属于任何 Workspace 的临时对话只能碰自己这段对话里建的。用户答："同意三点建议，按这个顺序开始做"。"实现中定下的几点"是实现时定的，随本次向用户报告，用户可以改。

## Problem

第 1 步（[`sql` 退出普通工具面](2026-10-05-sql-leaves-the-ordinary-tool-surface.md)）让查历史的工具不再跨 Workspace。但工作记录和定时器这两类对象没有被覆盖：

- **F1**：项目 Q 的模型只要拿到项目 P 一条工作记录的编号，就能用 `work_record` 读它、写进度、把它标成完成。
- **F2**：项目 Q 的模型用 `timer_list` 能看到项目 P 的定时器，用 `timer_cancel` 能取消它。

权限管线没有被绕过。问题在通过管线之后，这些操作没有检查对象属于谁。复现的前提是编号已知；这里说的 Workspace 是数据和工作的归属，不是挡住任意 Lisp 或 shell 的沙箱。

## Decision

模型经工具到达一条工作记录或一个定时器之前，先查它是不是这段对话所在 Workspace 的。

- **属于某个 Workspace 的对话**：只能碰这个 Workspace 的工作记录和定时器。同一个 Workspace 里的另一段对话可以碰，界线是 Workspace，不是对话。
- **不属于任何 Workspace 的对话**（临时对话）：只能碰在这段对话里建的。
- **别人的对象**：拒绝，回答是"属于另一个 Workspace，这段对话不能读也不能改"，不带那个对象的任何内容，也不写任何记录。
- **用户自己的入口不变**：工作记录列表、用户自己完成一条记录、用户取消定时器，仍然看得到、碰得到全部。
- **产品自己的写入不变**：到点唤醒、子代理交回结果时记到记录上、定时器重试，都不经过这道检查。

## 实现中定下的几点

- **检查放在模型的入口，只有一处。** 工作记录是 `superchat-work--for`，`work_record` 的 read、update、wait、done 都先过它，start 时 `follows` 指的那条记录也过它。定时器是 `superchat-timer--within-p`，`timer_list` 用它筛，`timer_cancel` 在取消前用它查。底下的领域函数（`superchat-work-get`、`superchat-timer-cancel` 等）没有加检查，因为用户的命令和产品自己的写入也调用它们。
- **已触发的定时器按它所在对话的 Workspace 算。** "已触发"和"到点还没启动的任务"这两种记录里没有 Workspace，只有对话编号，所以通过那段对话查。
- **说不出是哪段对话的调用什么都看不到**，和第 1 步给查历史的工具定的规则一致。
- **子代理的对话不属于任何 Workspace**（它的配置里没有绑定），所以它用 `work_record` 碰父对话的记录会被拒绝。这和已有的约定 K14 一致：子代理拿到的是记录的快照，被告知"你不能改它"，由产品替它把任务和报告记上去。
- **这次检查之前写下的记录**：如果旧的记录里某段对话的"当前记录"指向了别的 Workspace 的记录，现在得到的是同一句拒绝，而不是"没有这条记录"。
- `timer_list` 给模型看的说明改了几个字，写明列的是这个 Workspace 的；`work_record` 的说明没有加字。
- 现有的一个定时器测试原来是在"没有任何对话"的位置调用列表工具的，它依赖的正是"列表是全局的"。我把那两处调用改成"以建定时器的那段对话的身份调用"，断言没有动。它不属于受保护的 M3 回归集。

## Alternatives considered

**只在给模型看的列表里筛掉别人的，不在写操作上查。** 没选：筛列表挡不住"编号已知"的情况，F1 的复现正是这样。

**把检查放进底下的领域函数。** 没选：用户的全局列表、到点唤醒、子代理交回都调用同一批函数，会被一起拦住。

**让子代理的对话继承父对话的 Workspace。** 没做：那会同时改变它带不带规矩、回忆范围等一串行为，是另一件事。

## Acceptance criteria

`scripts/object-scope-regression.el`，15 个测试：

- 另一个 Workspace 的模型经真实的工具调用去读、改、完成一条记录：三次都被拒绝，模型看到的内容里没有那条记录的目标，记录没有变，没有新写入任何记录。
- 逐个动作（read、update、两种 wait、done、start 带 follows）都被拒绝。
- 同一个 Workspace 的另一段对话能读能改；被唤醒的对话能更新并完成它自己的记录。
- 子代理被告知记录、它自己的调用被拒绝、产品替它记的委派任务照常落在记录上。
- 临时对话碰不到任何记录；旧记录里指错的"当前记录"得到同一句拒绝。
- 用户的列表仍然列出全部，用户自己能从任何地方完成一条记录。
- 另一个 Workspace 的模型经真实的工具调用列出并取消定时器：列表里没有，取消被拒绝，定时器还在。
- 同一个 Workspace 的对话共享定时器；已触发的只列给本 Workspace；到点还没启动的任务只有本 Workspace 能取消。
- 临时对话只有它自己的定时器，别的对话也看不到它的。
- 不存在的定时器说的是"没有这个定时器"，不是那句拒绝；用户自己的取消能取消任何一个。

在旧代码上 9 个失败，6 个通过（通过的是"不该拦的不拦"的护栏）。对新代码做了 16 处变异，全部被发现。评审自己的两个探针（断言"缺口存在"）在修好的代码上变红；评审目录里的文件没有改。

## 没有解决的

- 这只管模型的这两个工具。获准执行的 `eval_elisp` 和 shell 仍然能调用任何 Lisp 函数，Workspace 不是它们的沙箱。
- 子代理的对话不绑定 Workspace 这件事本身没有动。
- 评审的 F4（功能卸载后仍能登记等待）、F5（开始时附带的进度和等待被丢掉）、N1、N2 是后面的切片。
- 没有真人在键盘前验证。

## 真实模型的结果

沙箱 Emacs、替身用户，场景 OSC（在 `.scratch` 下的测试台里）：两个项目 alpha 和 beta。alpha 的对话建一条工作记录、设一个 3 小时后的提醒；beta 的对话拿到那条记录的编号，被要求读出目标并标成完成；再被要求列出所有定时器并全部取消。

| | 碰记录 | 列出并取消定时器 |
|---|---|---|
| DeepSeek，2 遍 | 被拒绝，如实告诉用户"读取失败、没有完成"，记录没有变 | 列表为空，没有取消任何东西，提醒还在 |
| 本地 Qwen，关掉思考，1 遍 | 同上 | 同上 |

三遍里模型都没有看到那条记录的目标和那个提醒的内容，也没有谎称完成。样本很小，只说明这几遍里的行为。
