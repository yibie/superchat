# Decision: 正文里也能写 `>技能`、`@模型`、`/命令`

Status: accepted — 用户，2026-10-10。对下面六条规则答 "agree, record to proposal"，随后对"要我现在开始实现吗"答"按照建议执行"。"实现中定下的几点"是实现时定的，随本次向用户报告，用户可以改。

## Problem

README 写明 `@model`、`>skill`、`#file` 是 "command-head syntax"：只在输入的最开头解析，正文开始之后出现的同样写法是普通文字。`/command` 同样只认开头（`superchat-parser-command` 用 `\\``）。

用户 2026-10-09 的话："superchat 也应该支持 /xxx 或 @xxx 可以写在正文里调用。所以在正文里输入 >skill-name 就可以调用技能，这个对大家都方便"。

查到的代码事实：

- "只认开头"没有决定记录。`docs/` 里找不到；README 那句话出自检查点提交 `3c98627e`。
- 解析只有一个点：`superchat-core--parse-input`。它把结果放进这一轮的 `superchat-turn`（`target-model`、`skill`、`command`、`command-args`），把去掉标记后的文字放进 `clean-input`。
- 补全（`superchat--completion-at-point`）的匹配规则锚在"光标前文字的结尾"，不是输入的开头。读代码的推论：正文中间也会给出 `>技能`、`@模型`、`/命令` 的候选，而解析并不认它们。没有实际操作验证。
- 定时任务和被唤醒的工作记录通过 `superchat-send-input` 发出模型写的文字，发送时绑定 `superchat-automated-input`。
- `superchat--get-available-models` 在没有手动名单、缓存又过期时会发一次同步网络请求（`superchat-models.el`）。

2026-10-09 用户还说："我希望从视频中学习到的，是对架构有益的，我们要做的改善，也绝不能抛弃整个 superchat 的结构来看。"（视频指 gptel 作者讲 presets 的那一个。）这次改动因此限定为：把现有的那一个解析点看得更宽，不加第二条解析或请求路径。

## Decision

1. **只认已有的名字。** 正文里的 `>xxx` 只有在 `xxx` 是一个存在的技能时才算调用；`@xxx` 只有在 `xxx` 是已知模型时才算切换；`/xxx` 只有在 `xxx` 是已有命令时才算命令。对不上的一律是普通文字。
2. **放开的符号**：`>技能`、`@模型`、`/命令`。`#文件` 保持只认开头。
3. **边界**：标记前面是输入开头或空白，后面是空白或输入结尾。用反引号包住的写法因此不触发。
4. **每种最多认一个，开头的优先。** 输入开头已有 `/命令` 时，正文里的 `>技能` 是普通文字；现有"写在开头"的输入行为不变（包括开头的 `>名字`、`@名字` 不校验是否存在）。同一种标记在正文里出现多次时只认第一个对得上的。
5. **不是用户亲手发的消息不认正文里的标记。** `superchat-automated-input` 非空时，只按现状解析开头。
6. **`@模型` 不为了认名字联网。** 正文里的 `@xxx` 只对照 `superchat-manual-models` 和仍有效的模型名单缓存；两者都没有时当普通文字，不阻塞发送。

认出的标记从 `clean-input` 里去掉，两侧多出的空格合并。正文里认出的 `/命令` 等价于把它写在开头：其余文字是它的参数。

不变的：权限模型；Workspace 范围；`>技能` 是代理/计划类预设时切换整段对话的现有行为；`>>workflow` 只认开头；就地问、就地做、改写这几个入口不解析这些标记。

## 实现中定下的几点

- 正文里的 `@模型` 可以和开头的 `/命令` 或 `>技能` 同时生效（开头本来就允许 `@模型 >技能` 连写）。"开头的优先"只管技能和命令之间。
- 同一段正文里既有已有技能名又有已有命令名时，技能生效，命令是普通文字，与开头的现有顺序一致。
- 认名字时区分大小写。
- 查清了 Problem 里留的未知：下一轮请求的历史里，这条消息是去掉标记之后的文字（探针：发 `ISX_BEFORE >isx-skill ISX_AFTER` 后再发一条，第二次请求里上一条用户消息是 `ISX_BEFORE ISX_AFTER`）。
- 模型名单"不联网"由 `superchat--models-known-without-fetch` 提供：手动名单，否则仍有效的缓存。

## 这次不做、单独立项的

- **技能只管这一次请求。** 已另行决定：见[同日记录](2026-10-10-an-agent-skill-for-one-message.md)。
- 视频里的其它几样（批注式的去向、改写时给只读工具、完成后通知、JSON 输出）各自是独立切片。

## Alternatives considered

**任何 `>词`、`@词`、`/词` 都算标记。** 没选：粘贴进来的引用、路径、`@某人` 会误触发；写错名字会在送给模型之前就执行本机动作。

**新增一种"行内修饰符"语法或第二个解析器。** 没选：现有的一轮输入已经有放模型、技能、命令的位置，解析点只有一个。

**`/命令` 保持只认开头。** 没选：用户明确要 `/xxx` 也能写在正文里；"只认已有命令名"加上边界规则后，`/usr/bin`、`/tmp` 不会被认。

## Consequences

验收：`scripts/input-syntax-regression.el`（18 个测试，不改 M3 回归集）。README 的 "command-head syntax" 一段同一切片更新。

- 补全在正文中间给出的 `>技能`、`@模型`、`/命令` 候选，选中后现在会生效。

- 粘贴的文字里恰好有一个独立成词的已有技能名或命令名，会被触发。用户亲手发送是唯一的闸门。
- 用户自定义了与常见路径段同名的命令（例如 `tmp`）时，`/tmp` 后跟空白会被认作命令。
- 没有用真实模型跑过，也没有在真实 Emacs 里手动试过补全加发送的整个过程。
- 就地问、就地做、改写这几个入口仍然不认这些标记。
