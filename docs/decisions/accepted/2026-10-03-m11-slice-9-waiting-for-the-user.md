# Decision: M11 第 9 片——等用户回答

Status: accepted — 用户，2026-10-03："开始第九片"；对两个问题的回答："两种都留，分工写清"；用户在这段对话里发下一句话时"自动清掉"。"leader 的选择"一节是 leader 在这些回答之下定的机制，随本片向用户报告。

## Problem

"等用户回答"有两种做法，各有毛病，分工也没说清：

- `ask_user`（[2026-09-20 记录](../implemented/2026-09-20-ask-user-waits-for-the-user-too.md)）：执行不结束，对话窗口里挂一个面板，期间 Run 的总期限停表。面板挂着会占住这段对话；用户关了 Emacs，问题就没了。
- 工作记录上的"等用户"（第 7 片）：执行结束，记录是"在等用户"。用户回答之后没有人清掉它，要靠模型记得去改。

## Decision

两种都留。

- **当场能答的用 `ask_user`**：行为不变，仍按 2026-09-20 的记录停表。
- **可以过一阵再答的登记在记录上**（`work_record`，`wait`，`wait_for user`），然后结束这次执行。
- **回答的信号由产品处理（K3）。** 用户在这段对话里发出一句普通的话时，如果这段对话的当前记录在等用户，产品清掉这个等待，记一条"用户回答了"的事实，然后才拼请求——所以模型看到的记录已经是"可继续"。同一 workspace 的别的对话里说话不清：那里的请求清单会列出"在等用户"的记录，由模型读了再接手。

验收：`scripts/work-record-regression.el` 的回归；一个真实任务——模型做完前半、问用户一个可以晚点答的问题并登记等待；用户下一句话回答后，等待被产品清掉，模型据此做完并标完成。

## leader 的选择

1. **"用户说话"的入口是一个钩子。** `superchat-send-input` 在发出一句普通的话时运行 `superchat-user-input-functions`（参数：对话编号、文字）。命令（`/…`）不算。
2. **不是用户敲的不算。** 定时器的任务和被唤醒的记录也是通过 `superchat-send-input` 发话的；它们绑定 `superchat-automated-input`，钩子不运行。
3. **只清"等用户"**，不清"等时间""等别的 agent"。
4. **`ask_user` 的行为一个字不改**，只在它的说明里加一句：答案可以等、又有当前记录时，改用记录上的等待。

## Alternatives considered

**只用记录上的等待（Holon 的做法）。** 用户没选：当场能答的小问题，结束执行再等下一句话更慢。

**让模型判断用户的话是不是回答。** 用户没选：模型会忘。

## Consequences

- 用户在有"等用户"记录的对话里说任何一句普通的话，等待都会被清掉，哪怕这句话其实没有回答问题；模型看到的是"可继续"的记录和用户的话，由它判断要不要再登记一次。
