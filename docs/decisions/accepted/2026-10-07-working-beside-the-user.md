# Decision: 自动醒来的工作不抢光标；关掉对话窗口不让执行失败；磁盘上变了的文件由 Superchat 先发现并说出来

Status: accepted — 用户，2026-10-07。第 4 步的真实运行报告末尾提了三条建议，用户答"按照建议"。同一份报告里列为"不需要用户决定"的三件事（工作记录显示它的各次执行、本地模型并发出错后执行挂死、两个执行同改一个 buffer 时少一行的原因）也在这里记录。下面"实现中定下的几点"是实现时定的，随本次向用户报告，用户可以改。

## Problem

2026-10-07 在独立沙箱 Emacs 里用真实模型跑了 12 个场景（见 `docs/roadmap.md` "Working beside the user"）。没守住的有：

- 到点醒来的工作记录做完改动后，审阅屏把光标从用户正在写的草稿里拿走（DeepSeek 2/3，Qwen 1/1）。
- 执行途中关掉对话窗口，执行以 "Human input adapter is no longer available" 失败，改动没做完（3/3，1/1）。
- 文件在磁盘上被别的程序改了，模型不知道（8 遍里 0 遍被告知）；buffer 没有未保存内容时，Emacs 在代理编辑中途自己问 "changed on disk; really edit the buffer?"（4/4），这个问题不是 Superchat 问的。
- 工作记录的显示里没有写是哪几次执行做的（0/3）。
- 本地模型同时收到两个请求时回了一个 `{"error": "文字"}` 形状的错误，llm.el 的 OpenAI provider 读它时自己出错，错误回调没被调用，那次执行一直不结束（Qwen 1/1，等了 240 秒）。

## Decision

1. **没有人发起的执行不显示审阅屏，也就不拿光标。** "没有人发起"指两种：到点的定时任务开始的执行，和被唤醒的工作记录的那次执行。回显区那句"有未保存的改动"照旧。用户自己发起的执行保持 2026-09-25 的裁定：审阅屏自己出现并拿到光标。
2. **对话窗口被关掉，执行继续跑。** 它只在需要问用户的那一步失败：`ask_user` 那一次调用返回"用户问不到：这段对话的窗口已关闭。不靠这个答案继续，或者结束时说清你需要知道什么"，执行本身不因此结束。审批问题不受影响，它本来就不依赖对话窗口。
3. **磁盘上的文件变了，由 Superchat 在编辑之前先看。**
   - buffer 没有未保存的改动：从磁盘重新读入 buffer，这次编辑不做，工具回答说明原因并让模型重读后再改。Emacs 那个问题因此不会出现。
   - buffer 有未保存的改动：不动 buffer，编辑照做，工具回答里加一段：磁盘和 buffer 不一样，现在保存会盖掉磁盘上的内容，要告诉用户。
   - `read_buffer` 读到这样的 buffer 时也加一行说明：这是 buffer 的文字，不是文件现在的文字。
   - 两种情况都在回显区告诉用户一句。
4. **打开一条工作记录时，下面列出它的各次执行**：执行编号、所在对话、结局，一行一次，按时间顺序。只给用户看；送给模型的记录文字不变。
5. **服务器回的错误读不了时，当作一条普通错误**，执行按"提供方出错"结束，不再挂着。

不变的：用户发起的执行的审阅屏；保存仍然只由用户做；权限模型；工作记录送给模型的内容；一次等待只启动一次执行。

验收：`scripts/beside-user-regression.el`。

## 实现中定下的几点

- "没有人发起"从这段对话的持久记录里判断（`superchat-changes--unattended-run-p`）：有一条指向这次执行的 `timer.started`，或者对话里有 `work.woken` 而这次执行是对话的第一次。不靠内存标记。被唤醒的记录所在对话里，用户之后自己发的执行仍然显示审阅屏。
- 磁盘是否变了用 Emacs 自己的判断（`verify-visited-file-modtime`）；文件被删掉不算"变了"。
- 没有未保存改动时选择"重读并退回这次编辑"，而不是"重读后照做"：模型的 `old_string` 是照旧文字写的，照做可能改错地方。
- 读不了的错误由一层包在 `llm-provider-chat-extract-error` 外面的保护处理，llm.el 本身没有改。

## Alternatives considered

**自动执行也显示审阅屏，只是不选中它。** 没选：它仍然会占掉用户正在用的窗口。用户可以改成这样。

**关窗口时取消执行。** 没选：用户关的是窗口，没有说要停工作；取消会留下做了一半的改动而没有交代。

**磁盘变了就拒绝一切编辑，直到用户处理。** 没选：有未保存改动时，用户的 buffer 才是他正在用的文字，拒绝会让代理什么也做不了；说清楚并把保存留给用户已经不会丢东西。

**自己问用户"磁盘变了，怎么办"。** 没选：到点自动跑的工作没有人回答。

## Consequences

- 自动执行留下的未保存改动只有回显区一句话提示；用户要看差异得自己打开审阅屏。
- 关掉窗口的执行跑完后，答案在对话记录里，重新打开对话才看得到。
- buffer 没有未保存改动而磁盘变了时，模型要多一个来回（重读、重改）。
- 没有覆盖的地方：间接 buffer 之外的多 buffer 访问同一文件；`eval_elisp` 和 shell 里的编辑不经过这项检查；真人在键盘前的操作。

## 两个执行同改一个 buffer 时少一行：原因

查了两次失败运行里送给 DeepSeek 的请求和它的原始回复（`.scratch/task-sim/runs/TWO-real-s4b1-*`、`TWO-real-s4b2-*` 的 `evidence/http/`）。两次都是少一行的那个执行的最后一个回复只有文字（"`- 乙1` is now the last line. Now the second line, appended after it." 和 "Second line added. Now the third."），`finish_reason` 是 `stop`，没有任何工具调用。没有工具调用的回复就是最终回答，所以执行正常结束。Superchat 没有丢工具调用，也没有丢行。这是模型说了要做却没有做；产品行为没有因此改动。

## 真实模型验证（2026-10-07）

场景和上一轮相同（`.scratch/task-sim/harness-goals/tasks-step4.el`，不在仓库里），在独立沙箱 Emacs 里由替身用户操作，没有人在键盘前。数字是运行次数，都很小。

| 现象 | 改之前 DeepSeek / Qwen | 改之后 DeepSeek / Qwen |
|---|---|---|
| 记录醒来后光标留在用户的草稿里 | 1/3，0/1 | 3/3，1/1（没有出现审阅屏） |
| 关掉对话窗口后执行跑完，重开对话能看到答案 | 0/3，0/1 | 3/3，1/1 |
| 磁盘变了，模型被告知并告诉了用户 | 0/8（两个模型合计） | 6/6，2/2 |
| Emacs 自己问"真的要编辑吗"（buffer 无未保存改动） | 4/4 出现 | 0/3，0/1 出现；别的程序加的那行都保住了 |
| 打开记录能看到重启前那次执行的编号 | 0/3 | 3/3，1/1 |
| 本地模型并发出错后，那次执行结束 | 0/1（挂了 240 秒） | 1/1（以服务器的错误文字结束） |

读这张表要知道的：

- "磁盘变了"两个场景的第一批运行被判为不通过，是测试台把 Superchat 自己在回显区的提示当成了弹出的问题；改正后重跑，表里是重跑的数。其中一次模型写的是"被别的程序改动过"，测试台的关键词没认出来，人读是告知了，算在 6/6 里。
- 重启场景第 3 遍整体判为不通过，原因是模型第一次执行把记录标成了"等待"而不是"可继续"，和这次改动无关；执行列表那一项是通过的。
- 本地模型那一次：另一个执行以 `[API error: The server returned an error: … speculative batch index 4 is not inside the current sub-batch …]` 结束。服务器为什么在并发时出这个错没有查，那是 LM Studio 的事。
