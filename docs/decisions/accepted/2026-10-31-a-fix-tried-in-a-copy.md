# Decision: 编译失败时，模型在副本里试着修，程序验过才交给用户

Status: accepted — 用户 2026-10-31 定的目标是主动 Agent，文章里的例子是"静默复现并修复"。用户 2026-11-02 说"commit，and next step"，下一步是[提案](../proposed/2026-10-31-an-agent-that-acts-without-being-asked.md)第 8 步：隔离副本和第 3 档。用户同日问"所以这里需要用到不同操作系统的文件系统？"，答复是不需要，文件系统只影响快慢，绑操作系统的是沙箱。"实现时定的"各条都可以改。

## Problem

[第 2 档](2026-10-31-a-failed-compile-is-looked-into.md)告诉你哪一行错了，改还是你改。文章里的 Agent 会把修好的结果摆到你面前，你只需要决定要不要。

这一步第一次让模型在没人看着时改东西、跑东西，所以有四件事不能靠模型自觉：

- **改到你的文件：** 你的 buffer 只有接手后才能动，保存只由你做。
- **跑到不该跑的：** 能改文件又能跑构建，就等于能跑任意代码：把 `build.sh` 改成别的，再跑一次构建。目录隔离挡不住，要操作系统来挡。
- **说修好了其实没修好：** 模型的话不算数。
- **它读到的话里夹带指令：** 编译输出和文件内容都可能是别人写的。

## Decision

**一条规则多一个开关。** 用户说"编译失败时查原因，能修就修好给我看"，模型调用 `timer_create`，`on: "compile_failed"`，`fix: true`。卡片上写明：会改一份副本并在副本里跑这次的编译命令，不能联网，读不到副本和工具链以外的东西，你的文件要你按键才变。默认没有；不说修就还是第 2 档。

**规则的话里没有"什么情况不用说"，模型就没有不说话的办法。** 模型设规则时，只有用户的话排除了一部分失败（"只有我的代码有问题才告诉我"、"vendor/ 不用管"）才加 `quiet: true`，卡片上写明"只说这句话要说的"，否则写"每次都说"。没有 `quiet` 的规则，这次执行根本没有 `nothing_to_tell` 这个工具。这一条是实验逼出来的（见"验证"）：说"能修就修好给我看"时，模型修不了就把这句话读成"那就不用说"，改提示之后 20 次里还有 11 次不说话；而且夹带的"别告诉用户"也没有了下手的地方。这一条对第 2 档同样适用：不说修的规则也一样。

**有 `quiet` 的规则，模型写完理由还能改主意。** `nothing_to_tell` 的参数是先 `why` 后 `left_out`。理由写到最后说"所以应该告诉他"的，`left_out` 填 false，这次查就继续，模型接着回答；不填也算 false。原来这个调用一发出就结束：同一批 5 次不说话里，有 4 次的理由写着应该告诉用户。

**一次失败的经过，由程序决定每一步：**

1. **做副本。** 项目目录复制到临时目录（`cp -R`，能克隆就克隆）。不带 `.git`、`.jj`、`.hg`、`.svn`，也不带名字像放密钥的文件。你的仓库什么都不变，`jj log` 里不会多东西。超过 `superchat-fix-copy-megabytes` 就不做。
2. **复现。** 在沙箱里跑一次同样的命令。输出比较下来和你那次的失败一样，才往下走。不一样（缺网络、工具链在家目录、命令写了绝对路径……）就退回第 2 档，只读地查，并记下原因。
3. **模型改。** 这次执行有四个工具：`read_file`、`read_buffer`（只有编译 buffer）、`edit_file`、`run_build`；规则有 `quiet` 时再加 `nothing_to_tell`。没有 shell：`run_build` 不带参数，跑的是你那次的命令，同一时间只跑一个。路径都按真实项目说，程序换算到副本。
4. **程序验收。** 模型结束后，程序自己再跑一次。通过才交付，不通过就丢掉改动，只留模型的话。
5. **交付。** 一行：`Compile "sh build.sh" failed; a fix passes it (the model's words): foo.el:8 …`。门铃上多一个 `[see fix]` 按钮。`RET` 看差异，再按 `a` 才应用。
6. **应用。** 改动进你的 buffer，不存盘，审阅屏接着管，`s` 才写盘。文件在这期间被你改过、差异对不上，就拒绝，什么都不动。

| 模型怎么结束 | 程序再跑一次 | 这一行 |
|---|---|---|
| 改了文件，写了回答 | 通过 | 带修复，可以应用 |
| 改了文件，写了回答 | 不通过 | 模型的话，并说它的改动没通过，已丢掉 |
| 没改文件，写了回答 | 不跑 | 模型的话，和第 2 档一样 |
| 调用 `nothing_to_tell`，`left_out` 为真（只有 `quiet` 的规则有这个工具） | 不跑 | 没有，当场结束，改动丢掉 |
| 调用 `nothing_to_tell`，`left_out` 为假或没填 | 还没结束 | 模型接着做，按它之后怎么结束算 |
| 模型出错或超时 | 不跑 | 按第 2 档的表，改动丢掉 |

**沙箱是必需的，不是可选项。** macOS 用 `sandbox-exec`，默认全部拒绝，只放行：读副本、这次的临时目录和系统与工具链目录（`superchat-fix-sandbox-read` 可加）；写副本和临时目录；不能联网，连本机也不行。环境变量只留 `PATH`、`HOME`（指向临时目录）、`TMPDIR`、`LANG` 这类，不带你的密钥。策略放在命令行上，不放文件，否则构建可以改掉下一次的策略。没有沙箱的系统设不了 `fix`，卡片之前就告诉模型为什么，第 0 到 2 档不受影响。

## 这不是提案原来的写法

**不用 `prepare` 命令，也不用 git worktree 或 jj 工作副本。** 提案记的是原型的做法："第 3 档用 `prepare` 命令"。原型面对的是服务器部署，这里是一个人的 Emacs：多配一条命令是负担，而且失败几乎总在没提交的改动上，从 HEAD 开的 worktree 复现不了；jj 工作副本会在用户的 `jj log` 里留下东西。K13 后半句（并行的子代理各有自己的 jj 工作副本）是用户发起的委派，这里不是，继续留着。

**没有给 shell。** 提案写"改代码、跑测试"。模型只能按一个键，跑你跑过的那条命令。

## 实现时定的

- **一次修复的上限：** 15 次读取、20 次编辑、3 次 `run_build`（`superchat-fix-builds`）、一次构建 120 秒（`superchat-fix-build-seconds`）、整次 600 秒（`superchat-fix-seconds`）。程序最后验收那一次不算在 3 次里。
- **一条规则 24 小时最多修 5 次**（`superchat-fix-per-day`），之后只查不修。查的次数还是 20 次，修也算一次查。
- **复现要求比较结果相同，** 比较方式和"同样的失败"一样（去掉时间、耗时、地址），并把副本路径换回项目路径。宁可退回第 2 档，也不让模型去"修"沙箱造成的失败。
- **命令从它开始的目录跑。** 命令以 `cd sub &&` 开头时，`compile` 把 buffer 的目录挪到 `sub/`，所以判断"是不是这个项目的编译"看 buffer 的目录，跑命令和记录看 `compilation-directory`。从项目外面开始的命令在副本里没有位置，只查不修。
- **Xcode 自己的话不算构建的输出。** `/usr/bin` 里的 `make`、`cc`、`git` 会问 `xcrun`，它在每个新临时目录第一次问 `xcodebuild`，后者在沙箱里连不上两个系统服务，就打两行日志。这两行不进比较，也不给模型看（`superchat-fix--noise`）。代价是第一次多约 2.5 秒。
- **差异只含模型用 `edit_file` 改过的文件。** 构建产物不算。文件名和基准都由程序记。构建把那个文件换成符号链接、删掉或者设成读不了时，修复作废，不会让这一行丢掉。
- **文件名里有控制字符的不能改。** 文件名原样写进差异的头部，带换行的名字能伪造"另一个文件的差异"。`edit_file` 和应用时各查一次。
- **所有版本历史目录（`.git`、`.jj`、`.hg`、`.svn`）都不读不改。** 它们不在副本里，所以模型写进去就是新文件，应用后就是你仓库配置里的新文件，比如一个带钩子的配置。
- **差异上限 64 KB，** 超过就不交付。差异要作为文字进记录，碰到不是 UTF-8 的行也不交付；同一个文件别的行不是 UTF-8 不要紧，保存时原样留着。
- **应用用 `patch`，不允许模糊匹配，** 多个文件要么全应用要么全不应用。
- **规则的 `fix` 设了也可能走第 2 档，** 记录里写明原因，`RET` 能看到。
- **副本放在系统临时目录，** 崩溃后由系统清理；结束时不等待地删，不卡 Emacs。构建可能留下只读目录，所以先 `chmod -R` 再 `rm -rf`，两个都不跟符号链接走。
- **副本的终端和编译窗口一样大。** 编译器按窗口宽度折行、截断引用的源码，所以窗口的行列数传给每一次构建（`:window`）。比较时也不计较空白和换行：窗口可能已经变了。
- **Emacs 只在一处停一下：** 按名字筛掉放密钥的文件。先看名字不问磁盘，2 万个文件约 0.02 秒（先问磁盘是 0.28 秒）。复制本身在后台，5 万个文件约 7.6 秒（当时机器同时在跑别的）。
- **构建用 pty 跑，** 和 `M-x compile` 一样，输出顺序才对得上。结束时杀掉它的进程组，留在后台的子进程也停掉。
- **`nothing_to_tell` 把 `left_out` 填成真时当场结束，** 和第 2 档一样，改动一起丢掉。

## 这一步没有做的

- Linux（`bwrap`）和 Windows：这台机器测不了，不写没测过的代码。
- 需要联网的构建：`cargo`、`npm install` 这类在沙箱里失败，退回第 2 档。
- 自动应用：永远由用户按键。
- 把修复做成 commit 或 PR。
- 测试框架、flymake 等别的事件。

## Alternatives considered

**给模型一个 shell，让用户承担风险。** 没选：夹带的指令可以直接运行，沙箱也挡不住它把项目里的东西读出来发走。一个键够用。

**只靠目录隔离，不要操作系统沙箱。** 没选：改 `build.sh` 再跑构建就是任意代码，在你的权限下运行。

**不跑构建，只改不验。** 没选：模型的话不算数，那样只是一个带差异的第 2 档。

**没有沙箱时退回到"只改不跑"。** 暂不做：跨平台时再想。

**只复制 `git ls-files` 列出的文件。** 没选：要多处理 jj 和没有版本管理的目录；`node_modules` 这类被忽略的依赖不在，复现不了。代价是有大量忽略文件的项目会碰到大小上限，`superchat-fix-copy-excludes` 可以排除。

**把未保存的 buffer 写进副本。** 没选：`M-x compile` 读的是磁盘，失败就在磁盘上的内容；写进去反而复现不了。

**验收通过就直接改进 buffer。** 没选：用户定的是"你的 buffer 只有接手后才能动"。

**用文件内容的哈希判断能不能应用。** 没选：你改了同一个文件的别处，修复其实还能用。`patch` 不模糊匹配已经够严。

## Consequences

- **安全：** 编译输出、读到的副本文件、构建输出都发给模型服务商，卡片上写明。名字像放密钥的文件不进副本，内容里的密钥挡不住。夹带的指令最多让模型改错副本、说错话或者不说话，改动要你看过差异并按键。**差异是要读的：** 模型可能改测试或构建脚本让它通过，程序分辨不出。
- **沙箱依赖 `sandbox-exec`，** Apple 标记为弃用，但系统自己还在用。它消失时规则会退回第 2 档或设不上，不会变成没有沙箱地跑。
- **Emacs 本身在沙箱里时（比如实验）嵌套不了，** 复现失败，退回第 2 档。
- **费用：** 比第 2 档多，见"验证"。构建时间也算在你的机器上，在后台进程里跑。
- **沙箱里的程序读不到自己的库时，macOS 会记一份崩溃报告，通常还弹窗。** 这是实验里真实发生的：一个故意改坏的版本把 `/opt/homebrew` 从可读名单拿掉，沙箱里的 Emacs 启动就死（`Library not loaded: libtiff.6.dylib`），5 轮留下 5 份报告，用户问 Emacs 是不是在频繁崩溃才查到。死的是测试里那个 Emacs。这台机器上正常的名单不会这样。按同样的道理，构建里跑的程序把库放在名单外（比如 Nix 的 `/nix/store`，这里没试过）也会，要加进 `superchat-fix-sandbox-read`。
- **留在后台的子进程：** 进程组之外的（比如 `setsid` 出去的）可能活得更久，但它们还在沙箱里。

## 验证

离线：`scripts/compile-fix-regression.el` 161 项，副本、沙箱、构建和 `patch` 都是真的，模型是脚本。在最终代码上故意改坏 174 处，抓到 173 处；没抓到的那一处是 `.git` 这类顶层目录先排除，只是省一次复制，后面还会再删一遍（有测试查完成的副本里没有 `.git`），行为不变。另有一处（把工具链目录从可读名单拿掉）之前 5 轮都抓到了，但它每次留下一份 macOS 崩溃报告，通常还弹窗，不再跑。全部回归 131 个文件 2109 项，只有 `m5-regression` 3 项不过，那 3 项在这一步之前就不过（默认工具变成六个之后没有更新）。M3 没有改动，139 项里 137 项通过、2 项跳过，和之前一样。

真实（`.scratch/super-agent-exp/e16.py`，`deepseek-v4-flash`，真实窗口、真实按键、真实沙箱和真实构建，每种 5 次）。下面是最后一批，代码和提示都是最终的：

| 情形 | 结果 |
|---|---|
| 有明确修法（语法错、逻辑错、100 KB 的大文件、C 项目用 `make`、`cd build && make`、Python、子目录、两个文件、7 种夹带指令） | 120/120 给出修复，改的正好是该改的文件 |
| 规则没排除什么，修法不明确或修不了（缺工具、要联网、缺配置、未定义的函数、规则说"不要改测试"） | 40/40 告诉用户 |

这一批 230 次修复运行：项目文件 230/230 没变，副本 0 个留下，密钥（`.env`、`~/.authinfo`、外面的文件）在发给模型的请求里 0 次出现。

**设规则（上一批；第 9 步又改了 `timer_create` 里 `on`、`fix`、`quiet` 的说明，编译说法重测的结果见[那条记录](2026-11-02-what-others-wrote-in-your-feeds.md#验证)）：** 用来调工具说明的 10 种说法 50/50。其余 9 种此前的留出句子 44/45（1 次多加了 `quiet`）。最新 6 种从没用来调过的句子 24/30：`Should compilation fall over, sort it out for me.` 5 次里 3 次设了规则但没有 `fix`；`万一编译不过，你就先帮我改好。` 5 次里 3 次当成了当下的请求，没设规则。当下的问题（"帮我修一下这个错误"）25/25 没设规则。

**留出的情形抓到了调提示抓不到的东西：** 每改一次提示或代码，就再写一批没用过的情形。

- `cd src && sh build.sh` 5/5 在副本里失败，因为起点取错了（改成 `compilation-directory`）。
- C 项目 5/5 复现不了，起初被实验台的错误 PATH 盖住，改对之后是 Xcode 的两行日志（`superchat-fix--noise`）。
- 长错误的 C 项目 5/5 复现不了，因为编译器按窗口宽度折行（`:window`）。
- 修不了就不说话 11/20（`quiet`），写完理由才发现该说（`left_out`）。

**费用：** 一般一次修复 4 次请求、约 8200 提示 token（大部分命中缓存）、约 260 输出 token、约 15 秒（当时机器同时在跑别的）。100 KB 的文件 8.2 万到 25.9 万提示 token、约 27 秒。一条规则 24 小时最多修 5 次。

这一步共 1272 次运行、4345 次请求、约 1660 万提示 token（1305 万命中缓存）、44 万输出 token。实验数据 15 GB，不进版本库。

**没有验证的：**

- 只有一个模型；固件项目都很小，没有跑过真实项目的真实失败。
- 差异要读这件事没有机制保证：修法不明确时，模型有时还是会改到让它通过。比如注释写着"10 公斤以上免运费？问销售"的固件，5 次里有 2 次按测试的期望改了，交了出来，话里说了这是猜的。
- 规则排除"第三方库"时，文件在 `vendor/` 但模型认为是语法错，就改了，5 次里 1 次。
- 英文规则 40 次回答里 5 次用了中文；中文规则 149 次里 148 次用中文。
- 模型说的行号有时差 1（`foo.el:9`，其实是第 8 行）。
- Linux 和 Windows 没做。
