# Decision: 就着回答里的某一段接话：引用那一段，写一句短话，发出去的是一整条消息

Status: proposed — 2026-10-28 用户看了 Claude Code 的 follow up 功能（引用助手回答里的一段或它问的一个问题，底下写一句短答，发出去时变成一条完整指令），问 Superchat 能不能复用这部分体验；我报告"零件都有，缺一个入口"，用户说"先作为 proposal 记录"。用户尚未决定做不做

## Problem

模型答了一长段，里面有三四个点和一个反问。用户只想对其中一点说一句"改成独立的行"。今天在对话里只有一条路：把要回应的那一点自己重新打一遍，再写意见，模型才知道说的是哪里。打不全就对不上，打全了就是重复劳动。

Claude Code 的做法（截图，2026-10-27）：选中回答里的一段，或它用粗体问的一个问题，在它下面写一句短话；发出去的那条消息是一条完整的、能独立读懂的指令。引用和短话怎么合成一条消息，截图看不出来，这里不假定。

Superchat 里已经有的（代码事实，2026-10-27 查）：

| 零件 | 在哪 | 做什么 |
|---|---|---|
| 回答的边界 | `superchat--response-region-close`（`superchat-render.el`）在每一轮关闭时给这一轮的回答打 `superchat-role` = `assistant` 文本属性，工具轮和最后一轮都打；流式写入的 `superchat--response-region-stream` 不打。用户输入打 `user` | 光标所在是谁说的能判断，一段回答的起止能取。没有"第几轮"的属性 |
| 工作中照样发 | `superchat-send-input`（`superchat-dispatcher.el`） | 本会话有 Run 在跑时，输入排队而不是打断 |
| `ask_user` 的问题 | `superchat.el`，"An approval question is shown the way `ask_user' shows its question" 一段 | 模型用工具问的问题在对话里是一块原生按钮面板，就地答，见 [审批在问的地方答](../accepted/2026-10-12-an-approval-is-answered-where-it-is-asked.md) |
| 批注 | `superchat-annotate` | 模型的意见以 overlay 挂在原文上，不改 buffer，见 [挂在原文上的批注](../accepted/2026-10-10-remarks-hung-on-the-text.md) |
| 就地追问 | `superchat-inline-reply`（`superchat-inline.el`） | 同一个 overlay、同一个 Session 追问，历史自动带上，第一次问的引用范围重发 |

对话视图是 [M4](../../roadmap.md#m4--surfaces-as-plugins-composition-by-profile-done) 的 `chat` 插件行所拥有的界面；这个提案只加一个命令，不加插件行。

缺的只有一块：**在对话视图里，把"助手回答里的一段"和"用户的一句短话"合成一条消息，走对话自己的提交路径**。`ask_user` 问的问题已经能就地答；模型在正文里用自然语言问的问题（截图里的粗体行）不是 `ask_user`，没有面板，和普通的一段一样要靠这个入口。

## Proposal

一个新命令，暂名 `superchat-reply-to-passage`，只在对话视图里有效：

1. **取引用。** 有选区时取选区；没有时取光标所在的那一段（段落边界：空行，且不越过 `superchat-role` 从 `assistant` 变成别的值的位置）。选区或光标不在助手回答里时报错，不发任何东西。
2. **问一句短话。** minibuffer 读一行。空的不发。
3. **合成并提交。** 草稿区（`superchat--prompt-start` 之后）必须是空的；里面已有文字时报错，什么都不动，用户先发掉或清掉那半句。合成的文本写进草稿区，然后调用 `superchat-send-input`。不加第二条请求路径：解析、排队、权限、记录都照旧。这是[来源、这一轮、去向](2026-10-10-source-turn-destination.md)里原则 1 的又一个实例。
4. **合成的样子（草案）。** 引用作为 Org 引用块，短话跟在后面：

   ```
   #+begin_quote
   <引用的那一段>
   #+end_quote
   <短话>
   ```

   引用块对模型是一段普通的用户消息，不需要新的提示词或收集器。是否在引用前加一句"针对你上面这段"这类固定话，做原型时看效果定。

5. **不做的。** 不做"选中引用后由模型把短话改写成完整指令"：那是第二次模型调用，而且发出去的消息和用户写的不再是同一句话，记录里要多一层"谁写的"。先用纯拼接；不够好再提。

### 和已有东西的边界

- `ask_user` 的面板不变。面板能答的问题走面板；这个命令只管正文里的段落。
- `superchat-inline-reply` 不变。它管源码 buffer 里的 overlay 对话；这个命令管对话视图。
- 排队语义不变：Run 在跑时，合成的消息和手打的消息一样排队。

## Alternatives considered

**在草稿区手动写引用。** 今天就能做：复制那一段，粘进草稿区，自己加引用块。用户要的正是省掉这三步。它是这个提案的下限，不是替代。

**把短话附在一轮输入的位置上（`superchat-turn` 加一个 `:quote` 字段）。** 更符合"选择挂在这一轮输入上"的字面，但解析点要认一个新字段，记录和重建都要跟着改，而纯文本引用块已经能被同一个解析点原样认出。收益不抵改动。等有第二个需要引用结构的消费者（比如记录里按引用回溯）再提。

**像 `ask_user` 一样给每段回答画按钮。** 每段一个"回复"按钮会把对话视图填满控件，而且段落边界在流式输出时还在变。一个按键加一个命令够用。

**用 overlay 把短话挂在那一段下面（像批注）再发。** 批注是模型对原文说话，这里是用户对模型说话，方向相反；挂在那一段下面的短话发出去之后没有去处，对话视图里会留一个和记录对不上的 overlay。

## Acceptance criteria

- 光标在一段助手回答里，调用命令，输入"改成独立的行"：对话里出现一条用户消息，内容是那一段的引用块加这句话；模型收到的用户消息和对话里显示的一致；Tape 上这条消息和手打的一样，没有新的事件种类。
- 有选区时引用的是选区；选区跨出助手回答时报错，草稿区不变。
- 光标在用户自己的消息里或草稿区时报错，草稿区不变。
- 本会话有 Run 在跑时，合成的消息排队，和手打排队的行为一致。
- 短话为空时不发，草稿区不变。
- 草稿区已有文字时报错，草稿区的文字原样保留。
- 以上各条在脚本化传输下有测试；对真实模型只要求一轮完成，不比对回答文字。

## Risks

- **段落边界。** 回答渲染成 Org 后，列表项、代码块、标题之间不一定有空行；"光标所在的一段"在这些地方可能取多或取少。选区是兜底，做原型时定段落规则。
- **引用块里嵌引用块。** 用户引用的那一段本身含 `#+begin_quote` 时，拼出来的 Org 不合法。做原型时决定是转义、改用行首 `> ` 还是报错。[接手](../accepted/2026-10-31-bringing-a-conclusion-into-your-message.md)选了行首 `> `：这样的行里 `/命令` 等不触发，而 `#+begin_quote` 块里的文字今天仍会触发。开头要有一句普通的话：以 `> ` 开头的消息不是技能，但以 `>` 紧跟名字开头的是。
- **流式中的回答。** 一轮还在流时，这一轮的文字还没有 `superchat-role` 属性（属性在这一轮关闭时打上），命令会报"不在助手回答里"；已经关闭的前几轮（工具轮）有属性，能引用。这是对的，但提示要说清"这一段还没写完"。
- **只验证了零件，没验证拼起来的效果。** 截图里的体验好不好，一半在模型怎么理解引用块。这份记录没有跑过任何模型。
