# Decision: 来源、这一轮、去向：选择挂在一轮输入上，去向用包一层来组合

Status: proposed — 2026-10-10 向用户报告了下面三条原则和建议的顺序；用户答"按照建议执行"，已实现的只有顺序里的第 1 项（见 accepted 里的同日记录）。三条原则本身和其余各项尚未经用户逐项决定，没有原型

## Problem

用户让对比 gptel 作者讲 presets 的视频（"source | gptel | destination"）和 Superchat，并说："我希望从视频中学习到的，是对架构有益的，我们要做的改善，也绝不能抛弃整个 superchat 的结构来看。"

视频的三段在 Superchat 里各有一个现成的接口（代码事实）：

| 段 | 接口 | 现在由谁选 |
|---|---|---|
| 来源 | `collect-context` 事件：一组收集器各自往请求里加内容 | 入口。就地问的选区内容靠入口在请求上放 `:inline-reference-text`，对应收集器才出声 |
| 这一轮 | `superchat-turn` 上的位置：模型、技能、命令、文件 | 用户，写在消息里 |
| 去向 | `superchat-sink`：一组回调（流式、状态、完成、出错、失联） | 入口。对话、就地问、就地做、改写、workflow 各造一个，共 5 处 `superchat-sink-create` |

差别不在缺机制，在于由谁来选：Superchat 由入口替用户选好，视频里每一次请求自己选。

另外的代码事实：

- `superchat-preset-apply` 的参数是（预设，这一轮），它改的是这一轮；把整段对话切到该预设是分发处在技能调用之后另做的一步。
- 改写的请求明确不带工具（`:tools 'none`）。代码里没有找到现成的"只读工具集"。
- 传输层会转发"回答格式"参数（`superchat-llm.el` 里的 `:response-format`）；一轮输入上没有放它的位置。
- 请求能从记录里重建是现行保证；预设目前是数据，只有 `:pre` 一个钩子。

## Proposal

三条原则：

1. **选择挂在这一轮输入上，解析只在一个点。** 来源开关、去向选择、一次性预设都进 `superchat-turn`，由 `superchat-core--parse-input` 认出。不为任何一项加第二条请求路径。
2. **修饰符不能绕过权限和 Workspace 范围。** 任何会在本机执行东西的写法都走工具和审批，不在发送前直接执行。
3. **去向用"包一层"来组合，不用"换一个"。** 原来的显示和记录始终保留，新去向是附加的。

按这三条看各项，建议的顺序：

1. 正文里的 `>技能`、`@模型`、`/命令`。已决定并实现。
2. 技能只管这一次请求。已决定并实现：代理技能写在消息中间时只管那一条，见 [accepted 里的记录](../accepted/2026-10-10-an-agent-skill-for-one-message.md)。内置的 `/code`、`/research` 这类模式没有"只管一条"的写法，未决定。
3. 完成后通知：套在现有 Sink 外面的一层，先用在自动醒来的工作上。
4. 批注式去向：一个新的 Sink，加上把答案拆成逐条并定位到原文。只读，不改文件。先在 DeepSeek 和本地 Qwen 上测定位准不准，再决定做不做。
5. 改写带只读工具：先定义哪些工具算只读；改写会从一问一答变成多轮执行，要过权限和审批。
6. JSON 输出：一轮输入上加一个位置，传到传输层。用处窄。

不建议做：

- 发送前在本机展开 `$(命令)`：违反原则 2。替代是模型在权限之内调用 shell 工具。
- 预设的每一项都可以是函数：预设保持为数据；需要动态时用 `:pre`，在一个点上算完并记下来。
- 同一任务交给两个代理比较：需要并行子代理各有独立工作副本，用户已说这一轮不做。

## Alternatives considered

**照视频的样子做一套"来源预设 / 去向预设"。** 没选：会在现有的收集器和 Sink 之外再建一层同义的东西。

**新去向直接替换入口原来的 Sink。** 没选：对话里的显示和"谁改了什么"的记录会因为换了去向而缺一块。

## Acceptance criteria

每一项单独立决定记录和回归测试。本记录只在用户接受三条原则时移到 accepted。

## Risks

- "Sink 包一层"和"一轮输入上的开关打开收集器"是读接口得出的做法，没有原型。
- 批注式去向依赖模型稳定地给出位置，弱模型上可能做不到。
