# Decision: 不用人开口，superchat 也能在 Emacs 里主动做事，并且不打扰手上的工作

Status: proposed — 目标是用户 2026-10-31 定的："我希望 superchat 在 emacs 的环境里也能做到这一点"，"这一点"指 DeepSeek 文章里的主动 Agent。用户同日又说："类似以前 cursor 那种，一边开着 buffer，一边是对话 agent 的场景也很有必要"，并问"怎么样的交互让用户不必头痛这两种 agent 形态的切换"。同日用户对四个问题的回答：主动工作"不进主对话"，放到哪里"需要讨论"，并提出了旁路投影和管家两个想法；审阅屏只在没离开时拿光标"是"；写死命令、批准一次"是"；没有结论时是否留标记"具体分析一下"。用户要求先跑实验，结果在[研究页的"实验"一节](../../research/super-agent.md#实验)，本文已按结果修改。之后用户对五个问题的回答：先修四个缺陷"是"；审阅屏"弹出来，光标不动"；管家按收窄的权限、从没有模型的第一阶段做起"是"；门铃放"正文"；"没有结论时"那张表"是"。这些之外的部分仍是建议，第 4 步之后的实现都还没有开始。2026-11-01 用户说"这也有点烦，一定要在第五步才能执行简单的任务"，所以第 5 步里的第 0 档提前做了。已实现的：[后台委派](../accepted/2026-10-31-a-sub-agent-that-works-in-the-background.md)、[光标和输入区](../accepted/2026-10-31-the-cursor-stays-where-you-went.md)、[没人开口的工作有自己的地方](../accepted/2026-10-31-work-nobody-asked-for-has-its-own-place.md)、[写死一条命令，批准一次，以后程序自己跑](../accepted/2026-10-31-a-command-that-runs-by-itself.md)、[接手](../accepted/2026-10-31-bringing-a-conclusion-into-your-message.md)、[简报：说不说由程序决定，模型只写那几句话](../accepted/2026-10-31-the-program-decides-the-model-writes.md)。下面的验收标准，第一到第六条都已在真实运行里通过（[数字](../../research/super-agent.md#接手)），提案还开着的是顺序里没做的部分。

## Problem

用户要两种用法：不用开口，它自己检查项目、定期给简报；以及边开着 buffer 边对话，自己把控细节。第二种已经有了（[M10](../implemented/2026-09-24-editor-mode-agent-mode-and-review-screen.md)）。第一种只有定时任务和工作记录唤醒。

[审查](../../research/super-agent.md)用探针查明：头疼的来源不是形态太多，而是主动工作和手上的工作共用了四样东西：

- **输入区：** 到点的定时任务把用户写了一半的话一起发了出去（P1）。
- **对话：** 简报进了正在写代码的对话，之后每次请求都带着它（P2）。
- **审批：** 简报卡在没人回答的审批上，用户的问题在后面排队（P2）。
- **光标：** 后台报告和用户走开后才结束的任务，都会让审阅屏拿走光标（P3、P4）。

现有的工作记录唤醒已经避开了其中三样：新开对话、不抢光标、留标记（[2026-10-07](../accepted/2026-10-07-working-beside-the-user.md)）。

## Proposal

不做第三种模式，也不让用户切换形态。编辑模式和 agent 模式仍然只管布局，由 `C-c C-w` 切换。主动与否不是模式，由事实决定：

1. **你发完话手没动，就算你在等。** 已实现，见[记录](../accepted/2026-10-31-what-you-type-lands-where-you-type.md)。
2. **没人开口的工作不碰你的东西。** 它有自己的对话，不写输入区，不进你正在用的对话，不成为主对话，不进别的对话的自动召回，不问人，不改窗口布局，不改 buffer。
3. **结果按"要不要你"分三种。** 没有结论：见下面"没有结论时"。有结论：模式行加一，管家 buffer 和列表里各一行。要你决定：排在列表最前面，不阻塞别的。
4. **只有一张表。** `superchat-pending`。模式行点开的也是它，不再是另一张 `superchat-changes-notices`。
5. **切换只有一个动作：接手。** 按 `RET` 看，按 `t` 或者点门铃上的 `[bring in]`，把这条结论放进你正在用的对话的输入区，作为引用，你接着写问题。权限是你的。反方向不需要动作：走开就行，执行继续（已有）。已实现，见[记录](../accepted/2026-10-31-bringing-a-conclusion-into-your-message.md)。

`t` 不用 `superchat-runtime-inject`：放进输入区的 5 次都答对，inject 在门铃实验里 5 次只有 3 次答对，而且之后每次请求都带着它（探针 B2）。放进输入区时用户看得见要发的内容，也能改，它就是一条普通消息。用户也可以在 `RET` 打开的那段对话里接着说，和原型一样。推荐带回主对话，因为从项目 buffer 发起的就地命令总是回到主对话（`superchat-conversation-session-id`），另开一条线要用户自己记。

### 管家和门铃（用户 2026-10-31 定）

想法 2 的管家是主动工作的家，想法 1 的投影做门铃。

**管家。** 一段固定的 Session 和常开的 buffer `*superchat butler*`，不绑定任何 Workspace：绑定了它就会变成主对话，也会进别的对话的召回（探针 B4）。主动工作的结果由程序写进这里，不经过模型。第一版只有你对它说话时才调用模型，所以平时不花钱，外部内容也不能自己触发它。真正干活的是各条规则自己的后台对话，管家不干活。这和原型的主 Session 同一种分工：只读状态、不做实现，执行者读不到它。

**门铃。** 用户定的：一行字插进你正在用的对话的正文，不写 Tape，不进请求，重开对话后消失。别的窗口只有模式行的计数。正文里的字模型多半看不到，它会说不知道（实验 3/5），偶尔自己读 buffer 找到（2/5），模型没有编造过（0/10）。插入不再动光标（[记录](../accepted/2026-10-31-what-you-type-lands-where-you-type.md)）。

**权限。**

| 能力 | 管家 | 其它 agent |
|---|---|---|
| 读各 agent 的状态和记录 | 能 | 不能 |
| 读别的对话内容 | 能，按需 | 不能 |
| 停止一次执行 | 能，每次你确认 | 不能 |
| 给一个 agent 发消息 | 能，每次你确认，显示原文，标明来自管家 | 只通过 `work_record` 汇报和最后的回答 |
| 改 buffer、`eval_elisp`、shell | 不能 | 按自己的级别 |
| 替你回答审批、改权限级别 | 不能 | 不能 |
| 建规则 | 提议，你批准 | 不能 |

写操作每次确认，是因为管家读的内容可能夹带指令。如果它能自动给有 `eval_elisp` 的 agent 发消息，别人写的一段文字就能借管家的手让那个 agent 动手。

**"其它 agent 读写不了"能做到哪一步。** `edit_buffer` 已经拒绝（探针 B3）。`read_buffer` 现在读得到，要加拒绝。`eval_elisp` 拦不住：它和管家在同一个 Lisp 进程里。默认级别下每次都问你，你就是这道关；`auto` 和 `danger-full-access` 下没有这道关。

**和 R1 的关系。** 用户要它管所有 agent，所以它跨 Workspace 读。R1 管的是"所有 Workspace 都带上的规矩或记忆"：管家的内容只有你确认后才流向别处，所以不违反。`superchat-pending` 和用户的 `/recall` 已经是跨 Workspace 的先例。

**分阶段。** 第一阶段没有模型：buffer、程序写入的行、门铃、接手。第二阶段加只读问答。第三阶段加确认后的停止和发消息。每阶段单独验收。

### 没有结论时（用户 2026-10-31 定）

"不出声"只指不进模式行和列表，Tape 上照样有记录，规则那一行能看到上次检查的时间、次数和费用。

| 情况 | 例子 | 建议 | 理由 |
|---|---|---|---|
| 程序比较，没有变化 | star 数没变 | 不出声 | 没花钱，也没有东西可看 |
| 规则写明"没变化也说" | "每天给我简报" | 一行 | 写规则时定，批准时能看到 |
| 模型查完明确说没事 | 编译失败，查下来不是代码问题 | 不出声 | 原型的 `dropped` 也是这样 |
| 模型结束但没有汇报 | 回答了一段话，没调用工具 | 一行，写最后的回答 | 否则模型忘了调用就吞掉了结论；原型也这样兜底 |
| 你亲自设的一次性任务 | "明早查一下 X" | 总显示 | 你在等答案 |
| 偶发失败 | 断网一次 | 不出声 | 原型连续 3 次才报（`FAILURES_BEFORE_ERROR`） |
| 连续 3 次失败 | `gh` 登录过期 | 一行，恢复后消失 | 否则"没消息"分不清是查过没事还是根本没查 |
| 留下了改动 | 有未保存的 buffer | 绝不静默 | 已有 "Unsaved" 行 |
| 要你决定 | 需要批准 | 排最前面 | |

这样 [2026-10-10 的裁定](../accepted/2026-10-10-a-notice-for-work-nobody-watched.md)不用改：定时任务和被唤醒的工作记录都是你设的，照旧留标记；新的只有规则启动的执行。这张表需要一个"没事可做"的动作，产品不解析回答文字：第 7 步做成了工具 `nothing_to_tell`，不是 `work_record` 的动作。

实验（原型，DeepSeek，每个场景 5 次）：该说的 55 次全部写了结论，其中 30 次带着"别告诉用户"或"运行危险命令"的夹带文字；该安静的 25 次，17 次 `dropped`，8 次多一行。出错的方向是多说。"多吵"只有 star 这一种真实数据：最近 30 天 1 天有变化，所以第 0 档能挡掉约 97% 的日子，不花一次模型调用。

### 主动工作的四档

每条规则写明最高到哪一档，默认最低。

| 档 | 做什么 | 例子 | 模型 |
|---|---|---|---|
| 0 | 只跑规则里写好的命令，和上次比较，变了才进列表 | star 数、CI 状态、`git status` | 不调用 |
| 1 | 把命令的输出交给模型写几句，模型没有工具（`:tools 'none`，改写和批注已经这样） | 每日简报 | 调用，没有工具可用 |
| 2 | 模型能读文件和 buffer 查原因（`read-only` 加 `never`），没有 `eval_elisp` 和 shell | 编译失败查原因 | 调用，只读 |
| 3 | 在隔离副本里改代码、跑那条失败的命令，程序验过才经审阅屏交付 | 静默修复 | 调用，只在副本里写，构建由操作系统限制 |

用户的 buffer 不属于任何一档，只有接手后才能动。

### 规则怎么来

用户在对话里说"每天早上告诉我 star 变化"。模型登记一条规则：时间、要跑的命令、最高档。产品把这条命令原样显示出来，用户批准一次。到点时产品跑这条写死的命令，模型改不了它。同一条规则一段对话，不是每次新开，所以历史就是往期简报。

### 和原型实现的对应

[实现对照](../../research/super-agent.md#实现对照)：程序过滤对应 `gate`（第 5 步）；四档对应 `Mandate`；规则 2 用隔离达到 `WorkerSlots` 给人多留名额的目的；"没有结论"需要 `dropped` 这样的汇报状态才能判断，没汇报时按"有结论"显示，宁可多一行也不漏；第 9 步的重启补做对应 `Effects` 和幂等投递；第 3 档没有用原型的 `prepare` 命令，也没有 worktree，见[记录](../accepted/2026-10-31-a-fix-tried-in-a-copy.md)。

### 顺序

每步各写记录，先写红测试。

1. 已完成：后台委派。真实模型在没明说时 43 次一次都没选 `background`，它只服务于用户明说"不想等"的情况。
2. 已完成：输入区里有话时任务等着。
3. 已完成：规则 1，覆盖 P3、P4。实验查明这条规则还不够，见 3a。
3a. 已完成：四个现有缺陷，见[记录](../accepted/2026-10-31-what-you-type-lands-where-you-type.md)。这些不依赖主动 Agent。
4. 已完成：没人开口的工作统一入口，见[记录](../accepted/2026-10-31-work-nobody-asked-for-has-its-own-place.md)。定时任务并入唤醒的做法；后台对话不当主对话、不进召回（B4）；管家第一阶段和门铃；模式行指向列表。任务默认只读、K10 改由管家和门铃来说、模式行算等批准的问题，用户 2026-11-01 同意，已做（见那条记录）。
5. **规则和第 0、1 档：** 第 0 档已完成，见[记录](../accepted/2026-10-31-a-command-that-runs-by-itself.md)：一个带命令的定时器就是一条规则。第 1 档和规则那一行的统计已完成，见[记录](../accepted/2026-10-31-the-program-decides-the-model-writes.md)：说不说由程序决定，模型只写那几句话。次数上限的数字没有定，现在的上限是重复周期（每天的规则一天最多一次模型调用）。`dropped` 动作移到第 7 步：第 0、1 档没有模型工具，现在没有谁能用它。
6. 已完成：接手，见[记录](../accepted/2026-10-31-bringing-a-conclusion-into-your-message.md)。先于第 5 步的其余部分做，因为它是验收标准里最后没满足的一条，也是用户问的"怎么切换"的答案。
7. 已完成：编译失败和第 2 档，见[记录](../accepted/2026-10-31-a-failed-compile-is-looked-into.md)。这个工作区一条规则，编译失败时模型只读地查项目。`dropped` 没有做成 `work_record` 的动作，而是这种执行才有的工具 `nothing_to_tell`：这里没有工作记录，前台模型也不该多一个"不告诉用户"的动作。第 2 档的上限定为一条规则 24 小时 20 次。测试框架、flymake 等别的事件没有做。
8. 已完成：隔离副本和第 3 档，见[记录](../accepted/2026-10-31-a-fix-tried-in-a-copy.md)。一条规则可以带 `fix`：副本里复现同样的失败，模型改副本、跑那条命令，程序再跑一次，通过才交给用户，按 `a` 进 buffer，审阅屏接着管。只有 macOS，构建由 `sandbox-exec` 限制。这一步还定了：规则的话里没排除什么，模型就没有不说话的工具。
9. 已完成一部分：别人写的内容先接 RSS，见[记录](../accepted/2026-11-02-what-others-wrote-in-your-feeds.md)。elfeed 来了新文章，没有工具的模型挑出你要的，标题和链接由程序用 elfeed 自己的。邮件、群聊没有做。重启后补事件、进展检查查下来已有的够用，没有新代码，见[记录](../accepted/2026-11-02-what-a-restart-and-a-runaway-already-have.md)。

Router 不在顺序里，等真实使用里出现列表和主对话解决不了的问题再说。前台自动转后台（原型的做法）也不在里面：主动工作由产品启动，不依赖模型选择，它只影响"你开口但不想等"，等 `background` 有真实使用数据再定。

## 和已有裁定的关系

需要用户改的：

- **T3（定时任务留在主对话，[工作记录契约](../accepted/2026-10-01-workspace-work-record-session-rules.md)里用户答"A"）。** 用户 2026-10-31 改为"不进主对话"。T2（纯提醒）不变。同一份契约的 S3 引用了用户的话："也不允许所有 agent ， subagent 共享 session，这非常容易造成上下文污染"，探针 P2 正是这种污染。
- **K10（唤醒的结果在主对话留一行）。** 已改：由管家和门铃来说，主对话不写，"后台对话不当主对话"保证它的身份。
- **完整控制类工具每次都问（[2026-09-17](../implemented/2026-09-17-permissions-the-dsh-way.md)）。** 用户 2026-10-31 同意：第 0、1 档的命令批准一次，以后同一条不再问。
- **你亲自设的定时任务能不能改文件。** 已改：默认只读。要改东西，在它自己的对话里用 `/permissions`，或者设 `superchat-timer-task-level`。"设的时候写明，批准时能看到"这个写法还没做。

不变的：K7（没做完的记录等用户发话）；保存只由用户做；用户发起的执行和就地命令；编辑模式和 agent 模式的切换。

## 安全

主动工作读的是环境里的内容，其中可能夹带指令，而 `eval_elisp` 能在用户的 Emacs 里运行任意代码。因此：

- 第 0、1 档的模型手里没有工具，夹带的指令没有手可用。输出当作数据。
- 第 2 档不提供完整控制类工具。
- 规则的命令是批准时的原文，不拼接模型的输出，也不拼接命令上一次的输出。批准时用户要读这条命令，登记时模型可能已经读过不可信内容。
- 别人能写入内容的来源，现在只有 RSS，模型没有工具，看到的标题和链接是程序给的（第 9 步）。邮件、群聊接入前要另行验证。

## Alternatives considered

**一个显式的"主动模式"开关。** 没选：用户要记住现在在哪个模式，而且主动工作本来就该在用户编辑时继续跑。

**现在就设一个只路由的主 Session。** 没选：原型的主 Session 是一个仓库一个，按 Workspace 设并不违反 R1，但它解决的是很多人、很多线索之间的路由，一个人用不上。文章自己也把人机协作形态列为开放问题（8.2 节）。

**按当前 buffer 猜用户想要哪种形态。** 没选：2026-09-24 已否决按打开位置猜模式，人常常正好在某个文件里。这里只用"发话后有没有走开"这一个事实。

**审阅屏只看选中窗口是不是对话窗口。** 没选：`superchat-act` 从代码 buffer 发起时，用户没走开，但选中的不是对话窗口。

**主动工作只给 `read-only` 就够了。** 没选：star 简报要跑 `gh`，`read-only` 下被拒（P5）。

**接手就是打开那段对话接着说（原型的做法）。** 不作默认：可以用，但就地命令会把侧窗口切回主对话，用户手上就有两条线。

**先修事件入口，再修撞车。** 没选：事件越多，撞车越多。输入区的缺陷现在就存在。

## Acceptance criteria

整体目标在下面的真实任务通过时才算达到，由真实模型运行，不只是脚本模型：

- 用户在主对话里写着半句话，到点的简报不动这半句话，也不进这段对话的历史。
- 简报的命令结果没变时，没有任何模型请求，也没有任何标记。
- 结果变了时，模式行加一，列表一行写着结论；期间用户的光标、窗口、buffer 都没变。
- 用户在主对话发问不受正在运行的主动工作影响，也不被它的审批挡住。
- 主动工作运行期间，从项目文件发起的就地命令仍然进用户的主对话。
- 按 `t` 接手后，用户下一句话里模型知道这条结论。

## Risks

- 费用：第 1 档以上的主动工作在用户没开口时花钱。每条规则要有次数上限，数字未定。第 1 档的上限目前是重复周期，第 2 档以上需要真正的上限。
- 打扰：有结论的行太多，用户会把功能关掉。要记录有多少结论被打开或接手。
- 批准一次的命令是新的权限概念：用户可能没读就批准。第 0、1 档的命令也能做任何 shell 能做的事。
- 管家是注入攻击价值最高的目标：它读所有 agent 的输出，又能影响它们。所以第一版不让外部内容触发它的模型，写操作每次确认。
- 又多一个界面。审查数过，找回一件事要开 3 到 4 个界面。管家要替代入口，不是再加一个：模式行、`superchat-changes-notices` 都指向它。
- 主动对话的 buffer 会增多。[方向 B](../../../reports/architecture-options-2026-10-11/REPORT.md)（执行不依赖对话 buffer）能解决，但动主干，这里每条规则一段对话先把数量压住。
- 文章的证据有限：合成负载，每种方案 5 次，针对团队群聊。对单人 Emacs 的效果要自己测。
