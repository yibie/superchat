# Decision: 批准提问开着的时候，Run 总期限不走

Status: implemented（2026-09-20；同日 accepted——用户在亲手试过"到点收回提问"之后裁定："用户不回复，提问也应当保持着"；在三个做法里选定 (a)：提问开着时期限不走，其余照旧）

## 一句话

Superchat 停下来问你"允许这次调用吗？"的那段时间，不计入 Run 的总期限（`superchat-runtime-default-deadline`，默认 1800 秒）。提问一直等到你回答或 `C-g`，你的回答永远有效；回答之后期限从剩下的时间接着走。

## 为什么

三件事不能同时成立：等待计入期限；提问保持到用户回答；用户的回答有效。2026-09-19 的裁定选了第一、第三件，于是 Run 到点时提问被收回（同日的"提问不比它的 Run 活得久"）。用户亲手试了之后改判：提问就应该等人——它是模态的，开着的时候 Emacs 本来就只能回答、`?` 或 `C-g`，让它等不会在后台耗掉什么，和任何一个 `y-or-n-p` 一样。无进展计时已经是这个语义（提问期间停表）；600 秒累计上限默认已关；只剩总期限还在提问期间走。

本决定**取代** 2026-09-19"人的等待应当计入上限"的裁定中关于总期限的部分。

## 契约

1. Run 有未决的批准提问（`approval.requested` 之后、决定之前）期间，总期限停表：期限定时器取消，记下停表时刻。
2. 最后一个未决提问结清时续表：Run 的期限顺延停表的时长，定时器按新的期限重新启动。同一个 Run 的期限检查（包括 `ask_user` 继续之前的同步检查）读到的都是顺延后的期限。
3. 期限只是被顺延，没有被关掉：没有提问时照常 1800 秒到点；回答之后剩多少还是多少。无人值守的 Run（默认回答者在 batch 里算"没有人"，提问瞬间结清）不受影响，仍有完整的期限兜底。
4. **随之不再可能发生**的事：总期限在提问开着时到点。所以"Run 结束时收回提问"（2026-09-19）不会再因为总期限而触发；它保留给 Run 确实已经不存在的情况——在别处被取消、出错失败、或用户自己设了累计上限且它到点。
5. **不变的**：`superchat-response-timeout-hard-limit` 若被用户设为数值，仍按其文档在提问期间照常消耗；`ask_user`（模型主动向用户提问）期间总期限的行为不变——它不是模态的，是否同样顺延是另一个决定；提问出现之前的输入不能回答它；键盘宏不算人；Run 的终态规则不变。

## 验收

1. 真实执行管线：期限 2 秒，回答者读 4 秒后允许 → 工具执行，Run `completed`，没有超时，没有"Run ended"提示。
2. 同样读 4 秒后允许，随后模型沉默 → Run 在回答之后按**剩余**期限超时（`Runtime deadline exceeded`），证明期限是顺延而不是关闭。
3. 守护：没有提问、模型沉默 → 照常在 2 秒左右因期限超时。
4. 守护：提问期间 Run 在别处被取消 → 提问仍被收回并告知（2026-09-19 的测试保留）。
5. 2026-09-19 的 `approval-wait/a-deadline-with-the-question-open-dismisses-it` 描述的情形按本契约不再存在，改写为第 1 条。

1、2 在实现前必须是红的。其余套件、canonical smoke、Kernel 检查不变；受保护的 M3 封口测试里用"总期限在提问期间到点"来制造 `timed-out` 的那一支需要换制造方式，由 leader 修改并记录。

## 交付记录（2026-09-20）

- 实现（`superchat-runtime.el`）：`superchat-runtime--deadline-wait-for-question` 挂在已有的未决工作记账上（`approval-entered`／`approval-settled`）：第一个提问打开时取消期限定时器并记下时刻；最后一个结清时把 `:deadline` 顺延停表的时长并重新启动定时器。没有新选项、新事件或新状态名。
- 回归（`scripts/approval-wait-regression.el`，10 个）：新增三个——期限 2 秒、读 4 秒后允许 → 工具执行、Run 完成、没有任何"Run ended"提示；读 3 秒后允许、随后模型沉默 → 回答之后约 2 秒因期限超时；没有提问时 2 秒照常超时（守护）。前两个实现前是红的（Run 在 2 秒 `audit-incomplete`，提问被收回）。前一天的 `a-deadline-with-the-question-open-dismisses-it` 所描述的情形按本契约不再存在，已由第一个新测试取代；"在别处取消时收回提问"的测试保留。
- 变异体：等待仍被计入（期限不顺延）→ 两个新测试红；回答后期限不再启动 → "按剩余期限超时"红。
- 端到端（交互式 Emacs，伪终端，零模型调用，期限 15 秒）：第一个提问开着 40 秒，屏幕上没有任何收回或提示，随后的 `y` 照常生效；apply、undo 两个 Run 都 `completed`（`runs/try-deadline-waits-pty-01`）。
- **受保护回归集的 leader 修改（第二次，同一个测试）**：封口测试的 `timed-out` 一支原来靠"期限在提问期间到点"制造结局，现在不可能了；改为在提问开着时用 `superchat-runtime--finish … 'timed-out` 请求这个结局，与另外三种结局的做法一致。断言未改；证据记在 `.scratch/m3-verification/REGRESSION-SET.md`。
