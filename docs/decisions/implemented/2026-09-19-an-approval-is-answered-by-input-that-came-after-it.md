# Decision: 批准只能由提问之后的输入回答

Status: implemented（2026-09-19；同日 accepted——用户裁定："问题出现之前积压的输入，不得构成批准"；倾向清除积压输入而不是固定等待；边界四条见下）

## 一句话

每次批准提问都重新划一条输入边界：先呈现这一次的工具和参数，再接受针对它的新输入。提问出现之前已经在输入队列里的按键——上一题多按的 `y`、手快按早的键、你在别的 Buffer 里正打着的字——不能回答它。

## 为什么

有人值守的验收 `m7-attended-act-01-deepseek`（2026-09-19）里，放行 `(with-current-buffer "init.el" (save-buffer))` 的那次提问，记录到的等待是 **0.000 秒**（相邻几次是 1.4、3.9、3.0 秒）：它被队列里已有的一个 `y` 回答了，提问内容没有被任何人看到。那恰好是该次验收唯一不通过项的放行点。

代码事实：默认回答者 `superchat-approval-confirm` 用 `read-multiple-choice` 读键，读之前不清输入队列。可复现：队列里先放一个 `y` 再提问，0.004 秒得到"允许"（`.scratch/m6-permissions/issues/02-…`）。

M6 契约承诺"每次调用都问；你的回答只对你看到的那组参数有效"。被排队的键回答时，"你看到的"是空的。

不选"显示满一小段时间才接受按键"：固定等待不能证明人看到了参数，可能只是让旧按键晚一点被消费，还引入延迟和计时测试。要定的是**输入归属于哪一个问题**。

## 契约

1. **输入边界**：默认人工回答者在呈现提问之前丢弃此前积压的全部输入（键盘缓冲与 `unread-command-events`）。每次提问各自建立边界：上一题多按的 `y` 不能批准下一题。被丢弃的输入不会在提问结束后"回来"执行到别处。
2. **取消语义不变**：`C-g` 不经输入队列（它置 quit 标志），提问期间的 `C-g` 照旧作为 quit 传播，记为 `cancelled`／`user-quit`；丢弃积压输入不会把任何东西变成批准；没有有效答复永远不是批准。
3. **键盘宏不能充当人工批准**：键盘宏执行期间（`executing-kbd-macro`），默认人工回答者算"没有人"——批准链得到 `unavailable`（模型读到 `[Tool call refused: no approval provider is available]`），不读取、不消费宏里的任何键；直接调用 `superchat-approval-confirm` 也一样不读键并返回拒绝。需要自动批准的场景用明确的策略（`never`／`danger-full-access`）或专用回答者（`superchat-approval-function`、`approval/request` listener），那些不受本条影响。
4. **已接受的副作用**：丢弃输入沿用 Emacs 自己在危险提问前的做法（`userlock.el` 的 `discard-input`），它同时会结束**正在录制**的键盘宏定义。批准的回答本来也不应该被录进宏里。
5. **不夸大**：这项保证的是"旧输入不能越界批准"，不是"证明人读过参数"。提问出现**之后**才到达的按键——包括你没注意到提问、继续在打的字——仍然会回答它。
6. **范围**：只涉及默认人工回答者（minibuffer 的 `y`/`n`/`?`）。Tape 事件、批准策略、`?` 查看参数、批准等待期间停表、其他回答者都不变。

## 验收

新回归 `scripts/approval-input-regression.el`。输入队列在 batch Emacs 里不存在（提问读的是 stdin），所以每个场景都由测试通过伪终端启动一个**交互式**子 Emacs 来跑，真实按键经终端送入：

1. 提问前队列里已有 `y`：提问保持打开；随后的新输入 `n` → 拒绝。
2. 连续两题，第一题时一次按下 `yy`：第一题允许；第二题**不被**多余的 `y` 回答，保持打开；新输入 `n` → 拒绝。
3. 新输入 `y` → 允许；新输入 `n` → 拒绝（守护）。
4. 队列里有旧 `y`，提问打开后 `C-g` → quit，不是批准；没有旧输入时 `C-g` 同样是 quit（守护）。
5. 键盘宏 `<某命令> y`：批准链没有人工回答者，直接调用回答者也返回拒绝；宏里的 `y` 没有被提问消费（它作为普通按键落进了当前 Buffer）。

1、2、4（有旧输入的一半）、5 在修复前必须是红的，且红在"旧输入／宏里的键回答了提问"上。其余套件、canonical smoke、Kernel 检查不变。

## 交付记录（2026-09-19）

- 实现（`superchat-approval.el`，两处）：`superchat-approval-confirm` 在提问前 `(discard-input)`，键盘宏执行期间不读键、返回拒绝；`superchat-approval--fallback-answerer` 在键盘宏执行期间把默认回答者当作"没有人"（与 batch 同一条分支），批准链得到 `unavailable`。先核实过的语义：`discard-input` 清空键盘缓冲与 `unread-command-events`，不动 quit 标志（`C-g` 不受影响），不影响**正在执行**的宏（所以宏单独处理），会结束**正在录制**的宏定义（契约第 4 条）。
- 回归 `scripts/approval-input-regression.el`（5 个测试）＋ 子进程脚本 `scripts/approval-input-child.el`：每个场景由测试经伪终端启动一个交互式子 Emacs，真实按键从终端送入；场景从计时器里发起提问，与产品里工具调用到达提问的方式一致。整套约 40 秒。
- 修复前 4 红 1 绿，红的都红成同一个样子——"提问被没有人在这一题上按过的键回答为允许"：旧 `y` → allowed；`yy` 的第二个 → 第二题 allowed；旧 `y` 在先、随后 `C-g` → allowed 而不是 quit；宏里的 `y` → 批准链有人、直接回答 allowed、`y` 被提问吃掉没有落进 Buffer。"新输入照常回答"前后都绿。测试自身的两处错误在看到红之前已排除（`skip-unless` 不能用在辅助函数里；子进程已退出时发送按键会先报错）。
- 变异体（各自让对应测试变红）：不丢弃旧输入（原缺陷）；批准链仍把执行中的宏当人；回答者仍读宏里的键；过修——什么都批准不了（连"新输入照常回答"一起变红）。
- 验收脚本回归：修复后用伪终端扮演人排练 act 入口（`runs/m7-rehearse-after-input-fix-act`），提问出现之后才按的键照常生效，两阶段 `complete=true`。
- 其余全部套件、canonical smoke（无基线变化）、Kernel 检查、加载通过；编译警告与基线一致。

之后重跑 act 入口的有人值守验收；那次运行的产品包含本修复与此前两项修复，是对完整产品链路的验收，不再是原快照上的纯模型对照。
