# Decision: earlier turns reach the model as real messages, tool calls included

Status: implemented — accepted by the user on 2026-09-25 ("A") on the attended run `history-messages-attended-act-agent-01`, with three answer statements contradicted by observations kept on record ([acceptance report](../../reports/2026-09-25-earlier-turns-as-messages-acceptance.md)). Decided — user, 2026-09-25: direction "A" ("学 DeepSeek Harness：之前几轮也按真正的工具调用格式交给模型"), then "按照你的建议" on both details (the history header leaves the model's view; the input wrapper's default becomes the input as typed); implementation state is in [the roadmap](../../roadmap.md); then "都按建议" on the two questions built along the way (no switch leaves the earlier turns out of one request; the smoke baselines as below).

## Problem

In M10 slice 1b's attended acceptance, run `m10-1b-attended-act-agent-01`, the act entry's undo Run made two real reads and then replied with text only: seven tool records in the form `# Tool: NAME(ARGS) -> [ok] Result: …`, none of them executed, then "Assistant: 已经撤销了。". superchat takes a reply without tool calls as final, so the Run completed with nothing undone and the user was told otherwise (issue `.scratch/issues/2026-09-25-a-reply-with-invented-tool-records-ends-the-run.md`; the run's `REVIEW.md`).

What the model was sent: tool calls of the current Run are real assistant `tool_calls` and `tool` messages, but earlier turns arrive as text inside the new user message — the Context View's prompt ([context contract](../../design/context-continuity-contract-v0.md), section 10): a `[Context v0 | …]` header, `User: …` lines, one `Tool: NAME(ARGS) -> [ok] Result: …` line per call ([the tool-results record](../accepted/2026-09-23-the-next-turn-sees-previous-tool-results.md), item 2), `Assistant: …` lines and the note "(Tool lines are past observations …)", followed by the input wrapped as "You are a helpful assistant. Please provide a clear and comprehensive answer to the user's question: …". The model sees two forms of a tool call, and the invented records resemble the text form. That form was also in the undo requests of two passing runs (`m8-attended-both-deepseek-02`, `m10-1b-attended-chat-editor-02`), so its role is a candidate, not shown.

## Decision

1. **Earlier turns are real messages**, placed before the current user message, in Tape order (user: "A"). For each earlier Turn the Context View selected: its user message; for each Step of its Runs that requested tools, one assistant message carrying that Step's calls, followed by one tool message per call; Step material the model saw as a user message at its place; the Turn's final assistant text as an assistant message. Intermediate assistant text beside tool calls is not stored and is not invented: those assistant messages carry only their calls.
2. **The history header leaves the model's view** (user: "按照你的建议", detail 1a). The View's disclosure — covered, represented, omitted, recallable — stays in the envelope, the request evidence and the inspector.
3. **The input goes as typed** (detail 2a): `superchat-general-answer-prompt` defaults to `$input`; the option stays for a template.
4. **The text transcript leaves every conversation request**: no `User:`/`Tool:`/`Assistant:` lines, no tool-observation note, in chat, act and inline ask.

## How a Turn becomes messages

- **Calls and results.** A call's wire id is its Tape `:execution-id`, on the assistant message's call and on its tool message, so ids match and are the same in every request that carries them. The tool message carries the stored `:result-text`; a result that was cut ends with ` … [cut: N more characters]` from the stored original length.
- **Arguments.** A call is sent with its arguments as a JSON object keyed by parameter name. New `tool.requested` rows store `:arguments-text` in that form: the positional arguments named by the tool's parameter list at the time of the call. Rows stored earlier hold a positional JSON array, named at assembly by the tool's current parameter list. A call whose stored arguments do not read as a complete array or object (cut, dropped for size, or from a tool no longer defined) is sent with empty arguments, and its tool message begins with `(Arguments not kept in full: TEXT)`, TEXT being the stored text with its cut mark, or `none` when nothing was stored.
- **Step material** (a steer, an injection, a finish-check note) is a user message carrying `[Injected material] TEXT`, the line the contract's Step-material amendment already defines, so it is not taken for typed input.
- **A compaction Anchor** covering earlier rows is one user message at the start that says it is a model's summary of the earlier conversation — as DeepSeek Harness replaces a compacted span with a `user/message` carrying the summary.
- **Selection and accounting are unchanged**: the Context View's budget, whole items, newest-first contiguous suffix and exclusions; an item still costs its canonical rendered line; a call is never separated from its result. The form the provider receives does not change what is selected. Storing named arguments does, slightly: a call stored after this change renders a longer canonical line (`Tool: read_buffer({"buffer":"init.el"})` against `Tool: read_buffer("init.el")`), so a fixed budget may select fewer items for such calls than for the same calls stored before. Seen while building: in the recovery test's Session, at a 400-character budget, compaction folded one more question into its summary (2026-09-25).
- **Assembled once per Turn**, as today: adjacent requests of one Run keep a byte-identical prefix; the system text and tool definitions are unchanged.
- **Compaction's own request**, which asks a model to summarize a span, keeps the text rendering: it is material to summarize, not a conversation to continue.
- **Recovery after a request that is too long.** When compaction resumes the Run (the provider refused the request as too long, or the estimate before sending said it would be), the resumed request's earlier-turn messages are replaced by the messages of the View assembled after compaction; the current Turn's own messages stay as they were. Until now the new View's text replaced the old View's text inside the user message; with the history sent as messages that text is not there, so the replacement found nothing and the Run failed (found while building, 2026-09-25). Amended 2026-09-25 for two issues found while building, both older than this change (`.scratch/issues/2026-09-25-a-recovered-request-repeats-the-question.md`, `.scratch/issues/2026-09-25-a-resumed-request-evidence-names-the-old-history.md`):
  - *The rebuilt View leaves out the resumed Run's own rows.* The View built at a Turn's start is assembled before that Turn's question is on the Tape; the View rebuilt for the resume is assembled later, when the question and the tool calls the Run already made are there, and it selected them. The resumed request therefore carried the question twice (once as an earlier turn, once as its own input) and each call the Run had made twice. The rebuilt View now leaves out every row the resumed Run wrote — its question, its tool calls and results, its admitted Step material, which the request already carries as the current Turn's messages — as well as the rows the Session replaced (`turn.superseded`), which the View built at a Turn's start leaves out too. The recovery event names the Run (`:run-id`) so the handler can find its rows. When those rows or the replaced rows cannot be read, the recovery fails with the rebuild-failed message: the View is never assembled without its exclusions.
  - *The Runtime learns the rebuilt View.* Each attempt's `request.message-list` names the items of the Run's View; after a resume they still named the View from before compaction, and the evidence rebuilt that old history while reporting it reproduced. When the resume puts the rebuilt View in the request, the Runtime adopts it as the Run's View, so the resumed attempt and every later attempt of the Run record its items and receipt, and the Run's earlier-turn messages are its messages: evidence and request come from the same View.
  - *The replaced messages are the earlier turns themselves, wherever they are in the list; the system text stays.* Found after acceptance (2026-09-25, by the worker fixing the two items above, reproduced by the leader on the accepted commit): after the first request llm.el keeps the system text as the first entry of the prompt's message list, and the replacement counted the earlier turns from the front of that list, so every resumed request went without its system text and sent the last earlier-turn message a second time. A defect of this change's implementation, not of the rule; the same holds for a rewrite of the request before a later attempt, which skips the earlier turns.
- **The request inspector** shows the earlier-turn messages read-only, between the system text and the editable prompt, and its Copy includes them. They are not part of the editable prompt, so editing the prompt neither removes nor changes them; until now an edited prompt was sent without the saved selection and therefore without any earlier turn (found while building, 2026-09-25). No switch leaves them out of one request (user: "都按建议", 2026-09-25): as in Pi (`/new`, `/tree`, `/fork`) and DeepSeek Harness (a new Session, a fork), a request without the earlier turns is a new Session (`superchat-new-session`) or a branch after an earlier Turn (`superchat-branch-session`).
- **Evidence.** The request evidence names the same items; `superchat-tape-request-evidence` rebuilds the messages above, and the inspector shows them. Found after acceptance (2026-09-25): a compaction summary named in a recorded message list was rebuilt last, unframed, as kind `anchor`, while the provider received it first as `[Summary of the earlier conversation …]`, and the evidence still reported `reproduced`; the item's class is read back from the Tape as a string and was compared with a symbol. The rebuild treats the class by its name.

## What DeepSeek Harness does

- Every earlier turn is sent as real messages: assistant messages carrying `tool_calls`, then one `role: 'tool'` message per result (`packages/llm/llm-deepseek/src/serialize.ts:218-267`, commit `c389f96`). There is no text transcript of earlier turns.
- The session "surface" is that ordered list of events; compaction cuts it only where no tool call waits for its result (`packages/compaction/compaction/src/tool-pairing.ts`), and the summary replaces the span as an ordinary `user/message` (`packages/compaction/compaction/src/types.ts:3-4`).
- Its request assembly (`packages/llm/llm/src/assembler.ts`, the DeepSeek serializer) has no line telling the model how much history was left out and no wrapper around the user's input; the one "omitted" there drops an interrupted tool call rather than invent its result.

## Alternatives considered

**B: a text-only reply that contains tool-record lines is not final** (a finish-check trigger, or sent back to the model as an error, as a broken Lisp edit is). The leader's recommendation, not chosen; it stays available if the invented records recur. It guards the harm directly but only against that shape.

**Keep the text lines, fenced as data** (a quoted block marked "not a script"). Keeps two forms of a tool call in one request, which is the candidate cause.

**Name the arguments at assembly for every row** instead of storing new rows named. No change to what the Tape stores, but a tool whose parameter list changed between the call and a later turn would be shown with the wrong names; storing the names with the call records what was sent.

**Send the whole Tape as the surface, as DeepSeek Harness does**, dropping the per-request budget selection for compaction under token pressure. A larger change of the Context View's selection model, not needed to remove the text form.

**A switch in the inspector to send one request without its earlier turns.** The leader's first recommendation, withdrawn after checking the references: neither Pi (`~/Documents/reference-code/pi`, `3e4bc26`: each request sends the whole path from the start to the current entry, `buildSessionContext`; history is chosen by where one continues) nor DeepSeek Harness (its prompt request carries only the content and a queue/steer mode) has one, and superchat already has both of their ways. A switch would add a request state to record and test. The cost: a part of the history can no longer be deleted for one request, which neither reference offers either (Pi only through an extension's `context` hook).

**Keep one header line when something was left out** (detail 1b). Not chosen: DeepSeek Harness has none, and the disclosure stays where people read it.

## Consequences

- The [context contract](../../design/context-continuity-contract-v0.md) gains an amendment that replaces section 10's rendering for provider requests and the tool-observation rendering of its 2026-09-23 amendment; [the tool-results record](../accepted/2026-09-23-the-next-turn-sees-previous-tool-results.md) item 2 is superseded by this record.
- `tool.requested` rows written after this change carry `:arguments-text` as a named JSON object; readers accept both forms.
- The canonical smoke baselines, approved by the user ("都按建议", 2026-09-25): case A's prompt text loses the wrapper sentence (`A.txt`, `A.full.txt`, regenerated; the diff is that sentence and nothing else). Cases S and T looked for the sentence to tell whether a turn applied the general template; since the default template is the input as typed, they now bind a marked template (`smoke--general-template`) and look for its mark, so they still check that skill and agent turns apply the template and a user command template replaces it. Their baselines are unchanged; with the mark, a template never applied fails S and an ignored command template fails T (`.scratch/history-messages/smoke-mutants/`).
- Suites that pin the text rendering (`tool-observation`, `tool-compaction`, `step-material`) and the ones that check history in the provider input or the inspector (`m5-history-material`, `m5-request-context`) are rewritten to pin the messages; none loses a guarantee without a replacement. The new behaviour gets its own test file. (`context-header` pins the disclosure in the View's text, which is kept, and the `Tool:` line in `m6-permissions` is the approval prompt's own label; neither changes.)
- More tokens per earlier call were expected (message wrappers and ids around the same bounded texts). Measured 2026-09-25 on a recorded Session, the undo request of `m10-1b-attended-act-agent-01` (11 selected items, 9 of them calls): the old history text was 10,176 characters as sent (JSON-escaped); the same items as messages, serialized by llm.el, 9,681 characters. About 5% fewer by superchat's own estimate (serialized characters), because the header, the role labels and the doubly escaped newlines are gone; the provider's own token count was not measured.
- The invented records may recur, since the text form's role is not shown; the issue stays open until the user decides, and B is the next step if they do. An attended DeepSeek run of the act entry's apply/undo on the built product is the acceptance; one run cannot show that they no longer happen.
