# Decision: 600 秒的累计传输上限默认关闭

Status: implemented（2026-09-19；同日 accepted——用户裁定："这 600 秒没有必要"；去掉的方式选定为"先关掉，拆除另立项"）

## 一句话

`superchat-response-timeout-hard-limit` 的默认值从 600 改为 nil：默认不再有"一次工具会话累计最多 600 秒"这道计时。想要的人仍可自己设一个秒数。把这个选项和它背后的时钟机制彻底拆掉，是另一个独立事项，本决定不做。

## 为什么

一个 Run 现在有四道防线：每次请求的无进展计时（120／180 秒，批准提问期间已停表）、工具轮数（12 轮后问用户）、Run 总期限（1800 秒墙钟，人的等待计入）、以及这道累计上限。前三道各有独占的职责；累计上限独占的场景——模型一直有输出、不卡死也不多调工具、就是不停——Run 总期限同样兜得住，差别只是 600 还是 1800。

它却是最容易误伤认真用户的一道：默认档位下每次 `eval_elisp` 都问人，人读代码的时间计入它（用户 2026-09-19 裁定：等待**应当**计入上限——所以不改成"提问期间冻结"）；一个十几轮的任务，每次认真看 30–60 秒，等待本身就能吃掉 600 秒，Run 在提问还开着的时候结束（实测见 `.scratch/m5-config-acceptance/issues/01-…`）。M5 的有人值守验收为此一直在测试 Emacs 里把它挪开。

## 契约

1. 选项默认值 nil，类型为"nil 或正整数"。nil 表示没有累计上限：不设累计定时器，时钟状态保持已有的"关闭"（`disabled`）。
2. 无进展计时不受影响：nil 时照常按每次请求启动、按进展刷新、批准提问期间停表。
3. `ask_user` 的"暂停／继续"在 nil 时仍然成立：提问期间无进展计时停下，回答后下一次发送重新启动；不会因为"预算耗尽"结束 Run（没有预算）。
4. 大 prompt 的无进展窗口按 token 数放宽（每 256 token 加 1 秒）时，原来以累计上限封顶；nil 时不封顶，由 Run 总期限兜底。
5. 设成正整数时，行为与今天完全相同（含 `ask_user` 冻结剩余预算、批准等待照常消耗）。
6. 人的等待仍然计入 Run 总期限（1800 秒）。到点时若批准提问还开着如何收场，是另一个决定。
7. **如实记录的遗留**：选项、`hard-*` 时钟状态、`input-arm-hard`／`input-freeze-clock` 等机制仍在代码里，默认不启用。彻底拆除（删选项、删定时器、把 `ask_user` 的暂停改成只管无进展计时）单独立项、单独写契约；在那之前不得把现状写成"已删除"。

## 验收

新回归 `scripts/no-cumulative-limit-regression.el`（复用 M5 执行回归的虚拟时钟夹具）：

1. 默认值是 nil；类型接受 nil 和正整数，拒绝 0。
2. nil 时，一个持续有进展、超过 600 秒的会话不会被结束；owner 上没有累计定时器，状态为 `disabled`。
3. nil 时，没有进展照旧超时（`no progress`）。
4. nil 时，`ask_user` 暂停后状态不是 `exhausted`／`paused`，无进展计时已停；继续后新的请求重新启动无进展计时，Run 不因预算结束。
5. nil 时大 prompt 的窗口不封顶；设为数值时照旧封顶。
6. 设为数值时原有行为不变——由现有 `m5-execution/wait/*` 测试保证（它们显式绑定数值）。

1、2、4、5 在实现前必须是红的。其余套件、canonical smoke、Kernel 检查不变。

M5 验收脚本里"把累计上限挪到 3600"的测试 Emacs 配置随之删除。
