# 来回为什么多：从机制逐步检查（2026-10-03）

用户在第 6 片的两次实测之后要求："从根本原因出发，第一性原理的角度来思考……详细回顾机制当中的每一步，检验是否足够 solid"。这页逐步检查一次请求的机制，以及第 6 片背后的每个前提。数据来自 `.scratch/task-sim/runs` 里 63 次不用脚本的真实运行（DeepSeek `deepseek-v4-flash`，601 次请求，批次 `m11-slice2` 到 `m11-6-old`），以及第 6 片的三组对比。

## 一次来回是怎么发生的

1. superchat 拼好请求：系统文字（指引、规矩、操作说明）、全部工具的说明、此前的对话、这次请求的来源和窗口摆法，发给模型。
2. 模型要么给出答复，要么要求调用一个或几个工具。
3. superchat 逐个执行（权限、审批、记账），把结果接在对话后面，把整段对话再发一次。
4. 重复，直到模型给出答复。

## 逐个检查前提

| 前提 | 数据 | 结论 |
|---|---|---|
| 一次来回贵，因为整段上下文要重发 | 输入 token 有 91% 命中缓存；一次请求的耗时中位数 2.3 秒，第 90 百分位 2.9 秒，几乎不随请求变大而变长；任务总时间的 84% 花在等模型回应 | 贵的是**次数**，不是每次的大小。重发的内容大多已缓存 |
| 工具太多让请求变重 | 工具说明占发送字节的 56%（中位数），但它们在请求的固定前缀里，属于被缓存的部分 | 字节上是真的，时间和费用上影响小 |
| 来回多，是因为模型把本可一气呵成的调用拆成了很多步 | 每次请求的用途：向 Emacs 打听情况 32%、用 `eval_elisp` 动手 26%、用工具动手 19%、读东西 9%、最后答复 13%。下一步做什么取决于上一步看到的结果，而且要模型判断，不是机械的连续调用。请求达到 15 次以上的 11 次运行全是 T6（摆窗口） | 不成立。来回主要花在模型**弄清现状**上，脚本合并不了"看了再想" |
| 受限的 Emacs Lisp 能把"计算"和"动手"分开 | Emacs 里改名、关窗口、选窗口都是普通函数。放宽后仍有 24/73 个脚本被拒，被拒的多是模型想直接动手（`rename-file`、`delete-window`、`select-window`、`goto-char`）；每次被拒多一个来回 | 在 Emacs 里不成立。Pi 的界线天然存在：JavaScript 沙盒本身碰不到外界，只能打工具 |
| Pi 证明了 codemode 能减少来回 | Pi 的例子是对一个 MCP 服务器做 331 次同类调用再过滤；Pi 默认**不开** codemode，核心工具只有 read、bash、edit、write 四个 | Pi 的用武之地是大批同类调用和大结果过滤，不是日常的"看一看、改一改" |

## 有证据的杠杆

1. **把模型要打听的现状直接放进请求。** 第 5 片的窗口摆法就是这样。T6 每次运行里用 `eval_elisp` 打听情况的次数中位数：没有窗口一段时 9 次，有了以后 5 次（另一组 6 次）；请求中位数从 13.5 降到 8（另一组 10）；通过从 4/10 升到 7/10（另一组 5/5）。打听最多的是窗口（`window-list` 103 次、`window-buffer` 96 次、`window-parameter` 58 次），其次是文件路径（`expand-file-name` 64 次、`file-exists-p` 37 次、`directory-files` 34 次）和时间（`format-time-string` 32 次）。
2. **一次把几个问题问完。** 发出工具调用的请求里，只有 21% 一次调了不止一个工具；平均每次 1.21 个。
3. **少失败。** 13% 的工具调用以失败告终，每次失败至少多一个来回。

脚本适合"大批同类调用"的工作。现有的任务里没有这样的。
